## Goal
`GET /api/v1/books` answers the reader's catalogue, every edition they hold a
copy of once, with its copies on their bookshelves, and the backend serves the
whole of `v0.7.0`. T044 orders that one query and T045 pages it, and the
frontend of T046 onwards reads it.

## Rules in play
- D04 — the pin moves from `v0.6.2` to `v0.7.0`, nothing else of the contract;
  the lookup's and the add's cases stay green with their bodies unchanged.
- D07 — the pin bump is the first red, the controller its green; `S3 The
  catalogue is empty` is un-skipped, nothing else of `CatalogueScenarios`
  changes; the read is proven by a JDBC slice against PostgreSQL; no
  hand-written web test, the contract covers the edge.
- D02 — the library asks, the bibliography knows nothing of it; the
  controller calls a use case, never the port.
- D12 — the read spans the copies, the bookshelves and the editions, which
  the repositories cannot serve in a few queries: a query port in
  `library.domain.catalogue` answers a read model built from one query; no
  `Edition` nor `Bookshelf` is rebuilt from the join.
- D10 — the use case is named by its sentence and exposes only `operator fun
  invoke`; the port keeps its own verb; no visibility widens.
- D11 — `next` is serialised as `null`; a wrong-type `after` is the
  existing `ProblemAdvice` answer, `/problems/validation`, no `detail`.

## Test plan
One step is one case is one commit; `./gradlew detekt` before each commit; a
step is committed before its guard's mutation is checked. `./gradlew test
--tests '*ApiContractTest'` lists the contract cases one by one. Assertions of
the JDBC slice ignore order (`shouldContainExactlyInAnyOrder`), the catalogue's
and each edition's copies alike: the order is T044's.

1. **red — the pin.** `ApiContractTest` loads `…/v0.7.0/openapi.yaml`. The red
   cases are the two of `GET /api/v1/books`; the commit body lists them. A
   case of the lookup or the add going red is not this task's to fix: stop
   and report `blocked` with the case.
2. **red then green — the reader's copies, none of another's.**
   `JdbcCatalogueTest`: Léa owns bookshelf A, Tom owns C; edition X has a copy
   on A and one on C, edition Y a copy on C only. Léa's catalogue is X alone,
   with its values as inserted and the one copy on A, with A's id and name.
   One whole-value comparison of the entry proves every field. Creates the
   port, its read model and `JdbcCatalogue`, one query: the reader's
   memberships, their bookshelves, the copies on them, their editions, with
   the edition's series and its contributions and their authors.
3. **red then green — an edition on two bookshelves, once.** Léa owns A and
   views Tom's B, a bookshelf built with Tom `OWNER` and Léa `VIEWER`; one
   edition of two authors has a copy on A and one on B. Léa's catalogue is
   that one edition, both copies, each with its own bookshelf, and the two
   authors once each. The join yields one row per copy and author: the rows
   are grouped by edition.
4. **guard — an empty catalogue.** Léa's bookshelf holds nothing, Tom's holds
   a copy: Léa's catalogue is empty. Mutation: drop the condition on the
   reader of the membership.
5. **green — the operation.** `CatalogueController`, `GET /api/v1/books`,
   calls `listCatalogue(reader.id)` and answers `BookPageResponse(books,
   next = null)`. `ListCatalogue` is created: it answers the port's editions
   for the reader. Every web-slice `@MockitoBean` list gains `ListCatalogue`;
   `ApiContractTest` stubs the contracteer reader with one edition of one
   author in a series, with one copy on the fixed default bookshelf, so the
   verifier reads every field of a `Book`. The generated case goes green; the
   wrong-type case stays red, answered `200`.
6. **green — the wrong-type `after`.** The operation takes `after` as a
   nullable `UUID` query parameter, which it does not read yet: a text that
   is not a uuid is the `TypeMismatchException` the advice answers.
   `ApiContractTest` is green.
7. **green — the scenario.** Remove `@Disabled("T043")` from `S3 The
   catalogue is empty`; a red is the run's code at fault.
8. **Tidy on green**, the gate run plainly, then the documents: the task line
   ticked, a `PROGRESS.md` entry, `GOTCHAS.md` (below), then the pull request.

**Not to be written:** a unit test of `ListCatalogue`, which forwards the

proves structure; S1 proves the values in T044); a case on order, on

## Risks and decisions
**A query port, not a use case read.** The catalogue is every edition over
every copy on every bookshelf the reader belongs to: through the
repositories, a query per bookshelf and per edition, which grows with the
catalogue; T044's order and T045's keyset must also live in one query. So
D12's query port: `Catalogue` in `library.domain.catalogue`, the library
asking. *Rejected:* `ListCatalogue` reading `CopyRepository`,
`BookshelfRepository` and `EditionRepository` — no ordered keyset over three
reads. *Rejected:* the port in the bibliography — it would know bookshelves.

**The read model holds the domain's values, not the aggregates.**
`CatalogueEdition` carries `Isbn?`, `Kind`, `Contributions`, `SeriesEntry?`,
so the authors come in the house's order as the lookup answers them, and the
edge maps them as `IsbnController` does. `CatalogueCopy` repeats
`CopyOnBookshelf`'s shape in the domain, since the domain may not see the
application. *Rejected:* an `Edition` in the read model — an aggregate
rebuilt from a join (D12). *Rejected:* moving `CopyOnBookshelf` to the domain
— a change to the lookup this task does not need.

**Names.** Port `Catalogue` with `editionsHeldBy`, read model
`CatalogueEdition` and `CatalogueCopy`, use case `ListCatalogue`, adapter
`JdbcCatalogue`, controller `CatalogueController`: PRD §3 avoids *book* for
the domain entity, and §4.1 calls the whole the reader's catalogue. The web
classes take the contract's names, `BookPageResponse` and `BookResponse`, as
`CopyResponse` does. *Rejected:* `BookController` — the avoided word for
what is an edition.

**The use case answers a list; the controller writes `next`.** Nothing pages
yet, so a page type with a `next` always null would be speculative; T045
gives the use case its page when `after` has a meaning. *Rejected:* a
`CataloguePage` now — a field no case reads.

**`after` is declared and not read.** Without it Spring ignores the query
parameter and the wrong-type case answers `200`. detekt's `UnusedParameter`
fails an unread parameter (checked on this tree) and accepts the name
`ignored`: the parameter is `@RequestParam("after") ignored: UUID?`, renamed
by T045 when it reads it. *Rejected:* `@Suppress("UnusedParameter")` — a
suppression where the tree's own idiom for an unread value exists.
*Rejected:* passing `after` to the use case and the port — an unread
parameter moved one layer down, and a signature before its case.

**The contract stub is a full `Book`.** The operation has no example, so the
verifier generates the request and checks the answer's shape only; an empty
page would leave `Book` unserialised. One edition with an author, a series
and a copy makes every property of `Book` and `Copy` present. The nullable
fields may stay null.
