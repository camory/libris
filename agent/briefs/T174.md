## Goal
Whatever order Libris answers in, the screen lists the answer to the
latest search asked and nothing of an earlier one, its first page or a
next page. A reader typing on while Libris is slow then never sees the
rows of words they have already replaced.

## Risks and decisions
**The composable drops the answer, not the client.** Which search is the
latest is known where the query and the cursor are kept, in
`useSearchCatalogue`; an answer arriving for an earlier one changes
nothing there, not the state, not the query kept, not the cursor.
Rejected: aborting the fetch (a signal on the port, the fake and the
client, none of which a scenario asks for; an answer already on its way
must be dropped anyway); dropping in the view (the view does not hold
the cursor, D05).

**Every `search(text)` call is a later search, the ones that ask nothing
included.** S6 shows the whole catalogue under two characters and after
the cross; a search left pending that landed afterwards would list rows
under an emptied box. Rejected: counting only the calls that ask.

**A next page belongs to the search whose rows it extends.** Asked
before a later search or while one is coming, it never joins that later
search's books, which step 5 holds to. Whether such a next page is still
asked is the implementer's: the steps read the state, not `asked`.
Rejected: a next page joining whatever search is shown when it arrives.

**The same words asked again are a later search.** The search key on an
unchanged text asks again (S6); the earlier answer counts no more than
any other. Rejected: comparing queries, which step 6 guards against.
