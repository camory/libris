## Goal
The backend stops sorting the last two lists it sorted for the screen: an
edition's authors (on the card and on a catalogue row) and the card's
copies by bookshelf come in whatever order the sources and the
repositories answer, and T086's screens sort them. `ContributionRole.order`
leaves with its one reader, and `Contributions` stays one value whatever
the order it was given.

## Test plan
Suite: `cd backend && ./gradlew check`; during the cycles
`./gradlew test --tests …` on the classes named, then `./gradlew detekt`
before each commit. Each step one commit, in this order.

1. **Guard, `ContributionsTest`** (`Contributions`, its equality).
   *Contributions given in another order are the same contributions*:
   `Contributions.of` over two contributions of different roles and names,
   and over the same two reversed, answer equal values. Green on arrival,
   the sort making both one list. Mutation: the `sortedWith` line dropped
   alone — red, a `Contributions` over a list compares in order. This is
   what keeps `JdbcEditionRepositoryTest` (an edition read back, its rows
   in the join's order) and `BnfSourceTest` (a record's authors against a
   list written in another order) true once the sort leaves.
2. **Removal, `Contributions`.** No case is added, so no red: an order
   leaves. `Contributions.of` keeps one contribution per author and role
   and orders nothing, and the guard of step 1 stays green: equal whatever
   the order given (see *Risks*). *The contributions are ordered by role,
   then by name* leaves `ContributionsTest`; *an author holds several
   roles* keeps its title and asserts both contributions in any order
   (`shouldContainExactlyInAnyOrder`, as `JdbcEditionRepositoryTest`
   does). `ContributionRole` loses `order`, its entries left bare. Proof:
   `ContributionsTest`, `JdbcEditionRepositoryTest`, `BnfSourceTest`,
   `OpenLibrarySourceTest`, `EditionPreviewTest` and the scenario classes,
   green unedited.
3. **Removal, `LookupIsbnForReader`.** No red, likewise. The copies are
   those on the bookshelves the reader is a member of, each with its
   bookshelf's id and name, unsorted. *The copies on the reader's
   bookshelves come with the edition, by the name of their bookshelf*
   becomes *…, with the name of their bookshelf*, its two
   `CopyOnBookshelf` asserted in any order; the case still proves the copy
   on a bookshelf the reader only views. Proof: `LookupIsbnForReaderTest`,
   `BookshelfScenarios` and `FastEntryScenarios`, green unedited.
4. Tidy, gate plainly, the gotcha, tick T087, PROGRESS entry, PR.

## Risks and decisions
**Fit.** One run: three production files lose a sort or a field, two test
classes lose or loosen an order case and gain one guard; no web, no
migration. Measured before writing: with both sorts dropped, 5 of 392
tests fail, the two order cases, `an author holds several roles`, the
copies' case and, through `Contributions`' equality, one case each of
`JdbcEditionRepositoryTest` and `BnfSourceTest`. Rejected: a split (each
part is a few lines).

**The launch condition — T086 deployed — is Tophe's, and this run cannot
see it.** As for T026 and T064: D04 lets the backend drop a promise only
once the frontend that no longer relies on it runs, and no run can read
which revision `libris.amory.fr` serves. The brief is written on the
condition being met, since Tophe launches the loop; the implementer does
not deploy or release, and says in the PR body that merging is not
deploying. Evidence to the contrary in the tree stops it with `blocked`.

**`Contributions` stays equal whatever the order it was given.** Today its
equality ignores the order only because `of` sorts; dropping the sort alone
makes two editions with the same authors unequal by the join's row order,
which fails `JdbcEditionRepositoryTest` and `BnfSourceTest` and would make
any comparison of editions depend on the database's plan. Step 1's guard
holds the equality before the sort leaves. Measured: `Contributions`
holding its contributions as a `Set` built from the distinct list fails
only the two order cases of steps 2 and 3, and passes every other test
unedited; the inside is the implementer's. Rejected: loosening the two
tests to compare in any order (a value whose equality depends on row
order is a trap for every later test); sorting in `JdbcEditionRepository`
(an order nobody promises, moved).

**`an author holds several roles` is loosened, not removed.** It proves the
rule of D12 that stays, one contribution per author *and role*; only its
order goes. Likewise the copies' case of `LookupIsbnForReaderTest`, which
alone proves a copy on a bookshelf the reader only views. Rejected:
deleting them with the order cases (the rules they hold would go
unproven).

**The removals are steps without a red.** As in T085: the only red would be
a case asserting some order, which D11 refuses. Each removal is its own
commit, proven by the cases that remain and the unedited scenarios.

**The scenario classes compare authors in order, and are not edited.**
`FastEntryScenarios`' *S5 Merged answer, from Open Library alone* expects
`Baba, Stéphane Lapuss', Tartuff`, and the `Card` and catalogue rows of
`BookshelfScenarios`, `CatalogueScenarios` and `CoversScenarios` compare
`authors` as lists. All pass with no sort (measured): the sources' order
and the join's follow the order written. D07 forbids a task to edit them,
so the implementer adds one item to `agent/PROPOSED.md`, for Tophe: those
comparisons rely on an order D11 no longer promises. If one of them goes
red, the implementer stops with `blocked`: it is a spec conversation, not
this task's.
