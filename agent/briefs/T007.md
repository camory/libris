# T007 — Frontend API client for the current reader

**Backlog line:** Frontend API client for the current reader. `src/domain`: the
reader type, pure TypeScript (`id`, `username`, `displayName`, `email`, and the
role `READER | ADMIN`); `src/application`: the `MeApi` port, one method
answering that type; `src/infra/api`: the hand-written type of the
`CurrentReader` response and the fetch client implementing the port, taking its
base URL as a constructor argument and sending `Accept: application/json` (D04,
D05, D06). No code generation, and `api/openapi.yaml` does not change. A Vitest
global setup starts `contracteer mock api/openapi.yaml -p <port>` before the
suite and stops it after; the spec passes that base URL to the client (D04,
D07). Test: one spec beside the client, the single operation the contract
declares, every response it declares (`200` only) and none it does not; the
contract carries no examples, so the mock answers generated values and the spec
asserts the shape, not the values. `frontend/README.md` says the gate now needs
the `contracteer` binary on the PATH (D08); the CI `frontend` job already
installs it. Nothing imports the client yet: the home view is T010.

**Serves:** PRD §4.10 (Libris knows the reader Authelia sent) and §5
(the API is described by an OpenAPI document verified on both sides);
decisions D04 (contract first, the frontend developed against
`contracteer mock`, no code generation), D05 (the frontend hexagon and its
layers), D06 (`Accept: application/json` on every request), D07 (`npm test`
is the gate, `infra/api` runs against the mock, one spec per operation),
D08 (the environment provides the `contracteer` binary), D10 (exact versions,
`save-exact`).

## Goal
When this task is done the frontend owns the three layers the `/me` operation
needs — the `Reader` type in `domain`, the `MeApi` port in `application`, and a
fetch client in `infra/api` — and `npm test` proves the client against a real
Contracteer mock of `api/openapi.yaml`, started and stopped by a Vitest global
setup. It matters now because it is the first frontend code that touches the
contract: it establishes how every later client is written (by hand) and how
every later `infra/api` spec is run (against the mock, never against a stub of
`fetch`), and T010 needs the port to inject.

## Test plan
Green suite: `cd frontend && npm test`, run plainly — nothing piped or chained
after it, or the sandbox hook refuses the call and silently drops any file write
made in the same call. While iterating, `npx vitest run src/infra` is enough.

1. **The mock must be up before the first red means anything.** Write
   `vitest.global-setup.ts`, register it in `vite.config.ts`, add it to the
   `include` of `tsconfig.json` and `"node"` to that file's `types`, and install
   `@types/node`. A throwaway spec asserting the mock answers 200 may be written
   here while learning and is deleted before the pull request (D07).
2. **Red — `src/infra/api/FetchMeApi.spec.ts`.** One case,
   `answers the reader the API describes`, laid out Given / When / Then (D07):
   given `new FetchMeApi(inject("mockBaseUrl"))`, when `currentReader()`, then
   each of the five properties is a string and `role` is `READER` or `ADMIN`.
   It is red on `Failed to resolve import "./FetchMeApi"` — the mock answering
   is what makes that the only reason it is red.
3. **Green.** `domain/Reader.ts`, then `application/MeApi.ts`, then
   `infra/api/FetchMeApi.ts`, in that order: each file only exists because the
   next one up needs it.
4. **Refactor on green**, then the README line, then the full gate.

The spec asserts the shape and never a value: the contract declares no example,
so the mock generates the body and `role` changes between calls (measured:
`{"id":"93b7…","username":"wprlgKiA0O",…,"role":"ADMIN"}`, then `READER` on the
next call). `expect(reader.id).toEqual(expect.any(String))` is the form used.

Not to be written: a spec for a 401, a 404 or a 500 — the contract declares only
the 200, and D07 says a client is tested against every response the contract
declares *and none it does not*. A spec that stubs `fetch` proves nothing about
the contract and is what this setup exists to avoid.

## Risks and decisions
- **Names, decided locally** (small, reversible, and no document fixes them):
  the type is `Reader` and its file `Reader.ts`, the port `MeApi` in `MeApi.ts`
  with the method `currentReader()`, the adapter `FetchMeApi` in
  `FetchMeApi.ts`. Two precedents: on the frontend a file is named after its
  single export (`router.ts`, `i18n.ts`, `AppFooter.vue`); on the backend an
  adapter is its technology followed by its port (`JdbcReaderRepository` for
  `ReaderRepository`), so the `fetch` implementation of `MeApi` is `FetchMeApi`.
  If a document later fixes a scheme, one rename covers all three.
- **`role` belongs to the frontend `Reader`, not to the backend one.** The
  backend keeps roles out of the entity (D06: authorities, never stored), but
  the task line puts the role in the frontend type, and the frontend only ever
  sees the `CurrentReader` payload, where the role is a property. Keep it.
- **`@types/node` is a real new dependency and must be justified in the PR
  body** (CLAUDE.md). Without it `vue-tsc` fails the gate with
  `error TS2591: Cannot find name 'node:child_process'` and
  `Cannot find name 'Buffer'`, because the global setup spawns a process and
  `tsconfig.json` restricts `types` to `vite/client`. Measured: with
  `@types/node` installed and `"node"` added to `types`, the gate is green.
  Nothing under `src/` may import a node module — this is the one file outside
  the browser bundle.
- **Where the global setup lives.** `frontend/vitest.global-setup.ts`, beside
  `vite.config.ts`: it belongs to no hexagon layer, so it stays out of `src/`
  (the ESLint boundaries elements only cover `src/**`), and `frontend/` is
  already where this project keeps its build and test configuration. It must be
  added to the `include` of `tsconfig.json`, or `vue-tsc` will not see it — and
  the `declare module "vitest"` augmentation it carries is what types
  `inject("mockBaseUrl")` in the spec.
- **How the spec learns the base URL.** Vitest's own channel:
  `project.provide("mockBaseUrl", …)` in the setup, `inject("mockBaseUrl")` in
  the spec (measured green on Vitest 5). Not an environment variable, whose
  propagation to the worker is not guaranteed, and not a constant duplicated in
  two files. D05's rule that a module receives its configuration as an argument
  is what the spec does with it: it passes the URL to the constructor.
- **Port 9099, fixed.** Contracteer needs a port; nothing in the environment
  hands one out. 9099 is what `agent/PROGRESS.md` already measured and it
  collides with no service of D08. If it is busy the mock exits at once and the
  setup rejects with `contracteer mock exited with <code>`, which is a clear
  failure, not a hang.
- **A missing `contracteer` binary fails loudly, not silently** (measured):
  `spawn contracteer ENOENT` is thrown as an unhandled `error` event and the run
  dies naming the binary. Do not add an `error` handler to prettify it: that is
  an untested branch, and the README line this task adds is where a human is
  told the gate needs the binary.
- **Never `pkill -f contracteer`.** The pattern matches the tool call's own
  command line and kills it (exit 144, seen twice, once in this planning run).
  The teardown returned by the global setup is what stops the mock, and
  `mock.kill()` was measured to leave nothing behind.
- **Measured shape of the finished task** on this tree, with all the files
  above in a scratch copy of `frontend/`: `npm test` green in about 9 s
  (3 test files, 3 tests, the mock adding roughly 2 s of start-up),
  `npm run build` green in 330 ms, eight files touched, one new devDependency.
