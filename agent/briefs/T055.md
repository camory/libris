## Goal
Scanning an ouvrage the house already holds answers its id and, once its
picture is stored, that picture as the one candidate, `Libris`, at the
address the catalogue answers for it; nothing is asked of the sources. The
frontend's *Already there* state (T063) reads this answer.

## Rules in play
- D02 — `LookupEditionByIsbn` (bibliography's application) answers what the
  house holds, the stored cover's name included; the address of the cover
  operation stays the web edge's knowledge, in `library.infrastructure.web`,
  which reaches no class of `bibliography.infrastructure.web`;
  `ArchitectureTest` unchanged and green
- D04 — no contract edit, no pin bump: the pin stays `v0.9.0`, which already
  declares `covers` and `coverUrl`; the number of `ApiContractTest` cases is

  un-skip is the first cycle, the last test to go green; the value is
  tested where it is computed (the use case, plain JUnit over fakes); no
  test of a controller or of a response type; every case of two or more

- D10 — each response is built by `from` on its companion from the
  application's type, the controller maps nothing; no visibility widened;

  hand in the files touched
- D11 — absent values are `null`, never omitted: a held edition with no
  stored cover answers `covers: []` and `coverUrl: null`
- D12 — the cover's name is the `Edition`'s (`coverName`), read by the use

## Risks and decisions
**The use case answers the stored cover's name; the web answers it as the
`Libris` candidate.** The use case already reads the held `Edition`, which
holds `coverName`, so `Held` carries it and asks nothing more. The candidate
is how the contract represents the house's cover: its address is the cover
operation's path, which the web edge alone knows (T065 built the catalogue's
there), and its name `Libris` is a word of the contract that no side reads
back (S10: "no side reads it"). *Rejected:* a `CoverSource.LIBRIS` entry,
since `CoverSource.of("Libris")` must answer `null` (T053: the house's own
name on an add means no chosen source) and T057's cascade iterates the
sources; the use case building the address, which would carry the web's
path into the application.

**`coverUrl` derived once from the candidates.** The contract defines it as
the first candidate's url; deriving it in the code both `from`s share keeps
the held answer true by the rule *S1 Typed ISBN, found* already proves, since
no test reads a held answer's `coverUrl` and S10 is not edited. *Rejected:*
setting it beside the candidate in `from(held, …)`, a second copy of the rule
no test sees.

**The address written once in `library.infrastructure.web`.** T065 wrote it
in `BookResponse.from` and rejected a helper "for T055, which has no caller
yet"; this task is that caller. Its form (a function beside the responses,
or a member of one) is the implementer's, found in step 3's refactor.
*Rejected:* a constant in `shared.infrastructure.web`, which would name a
bibliography operation in a package that knows no context (T065's reason);
two copies of the path.

**`ApiContractTest`'s held stub holds a stored cover.** As T067 gave the
catalogue's edition a stored cover so the verifier checks its `coverUrl`,
the held answer then carries a candidate and a `coverUrl`, checked against
`CoverCandidate` and the nullable string. The case count does not change: a
stub's answer creates no case. *Rejected:* `null`, which leaves the new
branch of the answer unseen by the verifier.

**No unit test of `IsbnResponse`.** D07 allows a hand-written web test only
for what the web decides from the request; the candidate is decided from the
use case's answer, and the exact values are S10's to prove, which the
scenario does (`["Libris"]`, the catalogue's address, no source asked).
