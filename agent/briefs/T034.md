## Goal
When this task is done, the backend can store an edition — what an ISBN
identifies as the house holds it, with its kind, at most one series entry with
a volume number and its contributions each with a role — and find one back
whole by its ISBN-13, the series and author names it carries landing on rows
shared by every edition that names them, whatever the capitalisation. It
matters now because T035 creates an edition when the house lacks the ISBN and
T036 answers the one the house holds: both need this storage and neither can
be written without it.

Nothing else moves. No use case, no controller, no answer of the API, no
contract pin, no scenario test: the proof of this task is one JDBC slice test
class and the green gate.

## Risks and decisions

**The aggregate lives in `bibliography.domain.edition`, not at the root of
`bibliography.domain`.** The backlog line writes `bibliography.domain`, which
names the layer, as it writes `bibliography.infrastructure.persistence` for
the other side; D02 states the sub-package convention explicitly — a concern
lives in a sub-package, and `library.domain.reader` and
`library.domain.bookshelf` hold one aggregate each with its repository port.
An aggregate and its port at the root, beside the values `domain.lookup` and
`domain.edition` share, would be the only one of its kind in the tree. The
shared values (`Isbn`, `Kind`, `Contribution`, `ContributionRole`,
`SeriesEntry`) stay at the root, where both sub-packages reach them, and no
file moves.

**`Edition.isbn` is nullable and `edition.isbn13` is a nullable unique
column.** PRD §3: an edition may have one ISBN, old or self-published books
have none; T035's line requires an edition without one ("without an `isbn13`
there is nothing to match, so the house gets a new edition every time"). D11
forbids editing a merged migration, so the column must be right the first
time: a `not null` here would cost T035 a migration of its own. The case of
step 5 is what motivates the nullability now rather than leaving a column no
test exercises. PostgreSQL's unique constraint counts no null, so several
editions without an ISBN sit side by side while two editions cannot share an
ISBN-13 — which is PRD §3's "matched by ISBN, never a second one" said in the
schema.

**The series entry is two columns on `edition`, not a child table.** The
edition has at most one series entry, so `series_id` and `volume_number` on
the row say it without a table, a unique index or a rule to enforce
"at most one". `series` itself is the shared name table D12 asks for. No CHECK
ties `volume_number` to `series_id`: the domain cannot represent a volume
number without a series (`SeriesEntry` requires a name), and D11 keeps the
schema to what a key can say.

**`contribution` carries a `position`.** The list of contributions is ordered —
the card shows the authors in the order the lookup gave them — and an
aggregate read back must equal the one stored. Ordering by the author's name
or by the role would silently reorder the list; `position`, written from the
index in the list and read back with an `order by`, keeps it. Its primary key
stays `(edition_id, author_id, role)`, which is PRD §3's "an author is linked
to an edition once per role".

**A `series` or an `author` row keeps the spelling that created it.** The
second edition's names land on the first's rows, so that edition reads back
with the first's capitalisation, not with what was inserted — the round trip
is the identity only for the first spelling. That is the meaning of "matched
by name whatever the capitalisation" and D12's "there is no renaming"; the
third case of the test plan asserts it, so the behaviour is pinned rather than
discovered later. A shape that works for the insert-or-match, one round trip
and no doubling, is
`insert into author (id, name) values (:id, :name) on conflict (lower(name))
do update set name = author.name returning id`, the `do update` being what
makes `returning` answer the existing row; a `do nothing` followed by a
`select` is equally acceptable. The uuid the adapter mints for such a row
comes from the same generator the id value classes use; `series` and `author`
are not aggregates, so they get no value class and no type of the domain
addresses them.

**No CHECK on `kind` or on `role`.** D11 was amended on 2026-09-21: an
enumeration column carries no CHECK, the Kotlin enum is the one source of
truth, and a row is read through `valueOf`. The T033 backlog line, written
before the amendment, still says "with a CHECK" for the membership role;
`V002` on `main` has none. This task writes none either.

**The search columns of D03 are not written here.** D03 gives `edition` a
`search_text` written by the adapter on every insert and update, and a
generated `search_vector` indexed with GIN over two text search
configurations built on `unaccent`, plus a `pg_trgm` index — and says the
search migration creates the extensions. Search is PRD §4.2, which
`agent/TASKS.md` lists as having no spec and no task; a column, an index and
two configurations no test exercises are exactly what `CLAUDE.md` forbids, and
D03 already puts the extensions in a migration of their own. The decision for
this task: `V003__edition.sql` creates no search column and no extension, and
the search migration adds them to the table when the first search task
arrives. The implementer says so in the pull request body so the reviewer
does not read it as a D03 violation; nothing of D03 changes.

**The slice annotation moves to the shared fixture package.**
`JdbcSliceTest` sits in `library.infrastructure.persistence` because the
library was its only user; D07 puts shared test helpers in the `fixture`
package, where `FreshSchema` and `WebSliceTest` already are. The bibliography
slice would otherwise import a library test class across a boundary the
ArchUnit rules only leave alone because tests are excluded from them. The move
is one file and two import lines, done first and alone (step 1), so the rest
of the task reads as the work it is.

**Editing `V003` after a gate run costs the database.** Flyway validates and
migrates while the context loads, so a migration whose bytes change after it
has been applied fails every database-backed class whole with
`Failed to load ApplicationContext`, and running one slice class alone does
not rescue it (`agent/GOTCHAS.md`). Write the migration whole in the cycle of
step 2. If it must change afterwards, restoring the file's bytes is the cheap
fix while the edited version never ran; otherwise the sandbox PostgreSQL has
to be recreated. The price of the trap is that the unique constraint and the
foreign keys cannot be mutation-checked once the migration has run: write the
case before the constraint within the same cycle, or accept the constraint is
proven only by the case passing.

**`findByIsbn` takes the domain's `Isbn`, not a string.** The value class is
already the thirteen normalised digits and refuses anything else, so the port
reads `findByIsbn(isbn: Isbn): Edition?` where the backlog line says "finds
one by its ISBN-13"; the column is `isbn13`, the name the contract and D11 use
for the stored form. A local naming choice, recorded here so it is not read as
a drift from the line.

**`Edition` declares no invariant of its own.** Nothing in S2, S3 or S4
refuses an edition: its values already guard themselves (`Isbn.of`,
`Contribution.of`, `SeriesEntry.of` answer `null`, their constructors
`require`), and D12's `init` block is for a rule that reads the constructor's
parameters — the edition has none until a task's test wants one. An `init` no
test motivates is production code without a test.
