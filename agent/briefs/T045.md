# T045 — The catalogue in pages of fifty

**Backlog line:**
> - [ ] T045 Backend: the catalogue in pages of fifty.
>       The answer of T043 comes fifty editions at a time and names the next
>       page by the id of the last edition answered; from that id as `after`
>       the following page starts just after it, with no gap or repeat, and
>       the last page names no next. The order of T044 is made total, the id
>       its last key, so two editions equal in it neither repeat nor skip;
>       an edition added between two pages lands in its place without
>       shifting them. An `after` naming an edition of the house that the
>       reader's catalogue no longer holds continues after its place; an
>       `after` naming no edition answers an empty page naming no next (D11).
>       Tests against PostgreSQL: fifty-one editions read as fifty then one;
>       editions of the same series, tome and title split across a page
>       boundary; an edition added between the two pages; an `after` of an
>       edition the reader's catalogue no longer holds; an `after` of no
>       edition.
>       Realises S2; un-skips the backend test of S2.

**Serves:** spec `catalogue` S2 (the backend); PRD §3 (*Edition*), §4.1;
decisions D02, D04, D07, D10, D11, D12
**First of its kind:** the first paged answer: a keyset page (`after` in,
`next` out) cut by a use case over an order the aggregate declares, and the
first use case taking an optional value type.

## Goal
`GET /api/v1/books` answers the reader's catalogue fifty editions at a time,
`next` naming the page that follows, and `S2 The catalogue comes in pages`
passes end to end. T046 moves the frontend pin once this is deployed, and
T049 walks the pages from `next` to `after`.

## Rules in play
- D11 — keyset pages: `after` optional, the id of the last edition
  received; `next` the `after` of the following page, `null` on the last;
  fifty per page, fixed by Libris; the order total, the id its last key; an
  `after` the reader no longer sees continues after its place, one naming no
  edition answers an empty page naming no next; a non-id `after` stays the
  `/problems/validation` T043 answers.
- D12 — the order is `Edition`'s: the id becomes the last key of
  `BY_SERIES_AND_VOLUME`, not a key the use case adds; the page is a rule
  `BrowseCatalogue` applies (Tophe's T043 review); `CataloguePage` is a data
  class with no rule, beside the use case, like `HeldEdition`.
- D02 — the controller turns the `UUID` it reads into an `EditionId` and
  hands the use case the value, never the text; the controller calls the use
  case alone; no repository method, no migration.
- D07 — the values are proven in `EditionTest` and `BrowseCatalogueTest` over
  the fakes; no JDBC slice case and no hand-written web test; `S2 The
  catalogue comes in pages` is un-skipped and nothing else of
  `CatalogueScenarios` changes; the contract test's stub follows the new
  signature, and nothing else of it.
- D04 — the contract and its pin are untouched: `v0.7.0` already declares
  `after` and `next`.
- D10 — `invoke(readerId, after)` is the only public member of the use case;
  the parameter is `after`, as the contract names it, and `ignored` goes;
  no visibility widens; no `shelf` in a name.

## Test plan
One step is one case is one commit; `./gradlew detekt` before each commit.
Each case is laid out Given, When, Then with the three comments (D07), and
asserts the whole list of titles or editions with `shouldBe`, so a page that
repeats, skips or reorders is red. The titles of a case run against the key
it proves: a case that some other key already passes proves nothing.

0. **The outer red.** Remove `@Disabled("T045")` from S2 and run `./gradlew
   test --tests '*CatalogueScenarios'`: read the red on `$.books.length()`
   (51 for 50). A red on anything else is not this task's: stop and report
   `blocked` with the failure. Leave the file modified, uncommitted, until
   step 9.
1. **red then green — the id, last key.** `EditionTest`: two editions of
   `One piece` tome 1 *Romance dawn*, fixed ids
   (`00000000-0000-7000-8000-000000000001` and `…0002`), given the second
   first: sorted, the first comes first. Red while the order ties and keeps
   the input. The helper `edition(...)` gains `id: EditionId` (default
   `EditionId.new()`).
2. **red then green — the first page.** `BrowseCatalogueTest`: Léa's
   bookshelf holds fifty-one editions without a series, *Roman 01* to
   *Roman 51*, their copies inserted in reverse; `browseCatalogue(lea,
   null)` answers *Roman 01* to *Roman 50* and `next` the id of *Roman 50*.
   Red while it answers all fifty-one. `invoke` gains `after: EditionId?` and
   answers a `CataloguePage`; in the same cycle the three existing cases pass
   `null` and read `.held`, their claims unchanged, the controller passes
   `null` and maps `held` (its `after` still unread), and `ApiContractTest`'s
   stub answers `CataloguePage(listOf(ONE_PIECE_1_HELD), null)`.
3. **red then green — the page after.** The same fifty-one, `after` the id of
   *Roman 50*: *Roman 51* alone, `next` null. Red while `after` is unread.
4. **red then green — exactly fifty.** *Roman 01* to *Roman 50*, `after`
   null: all fifty, `next` null. Red if step 2's `next` is named whenever the
   page is full; if step 2's green already asks whether an edition follows,
   this is a **guard**: mutation, name the next whenever fifty are answered;
   red on `next`.
5. **red then green — an `after` no longer held.** *Roman 01*, *Roman 03*
   and *Roman 04* on Léa's bookshelf, *Roman 02* on Tom's alone; `after` the
   id of *Roman 02*: *Roman 03*, *Roman 04*. Red while `after` is looked for
   among the reader's editions only. If step 3's green already finds the
   place from the edition's values, a **guard**: mutation, look for `after`
   among the reader's editions and answer from the start when it is not
   there; red on *Roman 01*.
6. **red then green — an `after` of no edition.** Léa holds *Roman 01*;
   `after` a fresh `EditionId.new()` the house never stored: no edition,
   `next` null. Red while such an `after` answers the first page or throws;
   if already green, a **guard**: mutation, answer the first page when
   `after` names nothing.
7. **guard — twins across a page.** Forty-nine editions *Roman 01* to
   *Roman 49*, then two *Roman 50* equal on every key but their fixed ids,
   the copy of the greater id inserted first: the first page ends with the
   *Roman 50* of the lesser id, the page after it is the other one alone.
   Mutation: remove the id key from `BY_SERIES_AND_VOLUME`; red, the pages
   then follow the copies or skip the twin.
8. **guard — an edition added between two pages.** The fifty-one of step 2;
   read the first page; then a copy of *Roman 00* joins Léa's bookshelf; the
   page after the first page's `next` is *Roman 51* alone. Mutation: start
   the page after the fifty first editions of the order instead of after
   `after`; red on *Roman 50* coming again.
9. **green — the scenario.** `CatalogueController` reads `after` as
   `UUID?`, hands `browseCatalogue` its `EditionId`, and answers `next` as the
   id's text; `ApiContractTest`'s stub answers whatever `after` the
   verifier's generated case sends (a random uuid). Run S2, green, and
   `ApiContractTest`, green; commit the removed `@Disabled("T045")` and its
   import with the controller.
10. **Tidy on green**, the gate run plainly, then the documents: the task
    line ticked, a `PROGRESS.md` entry, `GOTCHAS.md` for a trap met, the pull
    request, whose body lists the guards and their mutations.

**Not to be written:** a JDBC slice case, an `ORDER BY`, a repository method,
a migration or an index; a web-slice test; a case on a non-id `after` (T043
proves it through the contract); any edit of `CatalogueScenarios` but the
`@Disabled` and its import.

## Risks and decisions
**The page is cut by `BrowseCatalogue` over the edition's order, not by
SQL.** Tophe's T043 review settled it: *T044's order and T045's page are
rules the use case applies over this DTO*. The backlog line's *tests against
PostgreSQL* was written before that review and is superseded as T044's was;
its five cases stand as use-case cases. The T044 reviewer asked whether
D12's last bullet (the series name row *is what a filter or a sort by the
name reads*) still holds: it does, since the name the order reads is
`SeriesEntry.name`, which `JdbcEditionRepository` reads from that row, one
spelling for all the editions of a series. The implementer quotes this in
the PR body so Tophe can amend D12 if it means where the sort runs. Each page
reads the whole catalogue in three statements; the house holds under fifty
ouvrages, and a catalogue past a few thousand is a follow-up for
`agent/PROPOSED.md`, not this task. *Rejected:* `ORDER BY` and a keyset
`WHERE` in `EditionRepository` — PostgreSQL's collation would order text
where the `Collator` of T044 does, two orders to keep equal.

**The id is the last key of `BY_SERIES_AND_VOLUME`.** The aggregate holds the
id, so the order that makes pages total is its; the only caller is the
catalogue, and a total order breaks no test of T044 (their editions differ
before the id). *Rejected:* `.thenBy` in `BrowseCatalogue` — a rule the
aggregate can answer. *Rejected:* a second comparator with the id — two
orders whose only difference nobody wants.

**The place of an `after` is found from the edition it names.** An `after`
the reader's catalogue no longer holds continues after its place, so the
place comes from that edition's values, read through the existing
`EditionRepository.findByIds`; an `after` it answers nothing for is an empty
page. Nothing of that edition is answered, so an `after` of an edition on
another reader's bookshelf reveals nothing. *Rejected:* a `findById` on the
port — a second finder where the list one serves.

**`next` is named only when an edition follows.** The use case holds the
whole order, so it knows: a catalogue of exactly fifty is one page with no
next, and the frontend never asks for an empty last page. *Rejected:* `next`
whenever a page is full — an extra request and an empty page by design.

**`CataloguePage(held, next)` in `library.application.catalogue`.** A
projection beside its use case, as `HeldEdition` is; `held` as the tests
already name the list. *Rejected:* `BookPage` — the contract's word, and
PRD §3 keeps *book* off the domain.

**The contract test's stub.** From step 9 the controller hands on the random
`after` of the verifier's generated case, so the stub must answer any
`after`. `agent/GOTCHAS.md` knows only Mockito over Kotlin call syntax with
value classes; if a matcher on the `ReaderId` or `EditionId` argument fails
(`eq` and `any` answer `null`, which a value class may not unbox), the form
that works goes to `agent/GOTCHAS.md` as one item.
