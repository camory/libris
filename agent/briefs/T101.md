## Goal
The backend pins `v0.13.0`: the series list answers each series' `id`, and
`GET /api/v1/series/{id}` is served through a use case that answers no such
series to any reader, so both cases of S5 hold and Contracteer verifies the
operation's shape. T102 fills the answer behind the same use case,
controller and response, which this task fixes.

## Rules in play
- D04 — the pin moves from `v0.12.1` to `v0.13.0` and nothing else of the
  contract changes; every case of the earlier operations stays green.
- D07 — the pin bump is the first red and the controller its green; the
  two S5 methods of `SeriesPageScenarios` are un-skipped and nothing else
  in that file changes, `S1` staying skipped; no hand-written web test;
  each stub of the contract test answers a value filling every field the
  contract constrains.
- D02 — `/api/v1/series/{id}` is served from `web.series`, by
  `SeriesController`, which calls a use case, never a repository;
  `SeriesWithBooksResponse` imports `BookResponse` from `web.catalogue`,
  the sub-package that declares it.
- D10 — the use case is named by its sentence, `operator fun invoke` its one
  public member, held in a variable of its name; the responses map
  themselves through `from`, the controller maps nothing; the `when` arrows
  aligned; no rationale and no `D##` in code.
- D11 — an outcome of the use case (no such series) is a result the
  controller answers as a problem, not an exception; an id that is not a
  uuid is answered by `ProblemAdvice`, as for a bookshelf; ids are strings
  in JSON.
- D12 — the use case answers a sealed result of its `application`
  sub-package carrying data classes with no rule; the series list's `id` is
  the `SeriesId` of the series `SeriesRepository` answers.

## Risks and decisions
**Fit.** One run: one pin, one route, a use case answering a constant, its
result type, two responses, one field on the list, five test files touched.
Rejected: a split, since the bump reds both the list's id and the new
operation, and neither half is green without the other.

**`FindCatalogueSeries` in `library.application.catalogue`.** The spec
calls it "a series of the reader's catalogue", and T102 applies the
catalogue's rule beside `ListCatalogueSeries` and reuses its count, kind and
cover. The call reads `findCatalogueSeries(reader.id, SeriesId(id))`.
Rejected: `FindSeries` (a read of the bibliography's series alone, which
this is not); `OpenSeries` (the act is the reader's, the use case finds).

**`FindCatalogueSeriesResult`, `Found` and `NoSuchSeries`**, as
`FindBookshelfResult`: no such series is an outcome the controller
answers. Rejected: a nullable answer — the tree answers a find by a sealed
result, and T102 may need no other variant but keeps the form.

**`Found(series: CatalogueSeries, books: List<HeldEdition>)`.** The
contract's `SeriesWithBooks` is `Series` plus `books`, and T102's line
wants the name, count, cover and kind the series list answers, by the same
rules: `CatalogueSeries` is that answer, `HeldEdition` the catalogue's
`Book`, so `SeriesWithBooksResponse` reuses `BookResponse.from`. Rejected:
a flat data class of six fields, which repeats `CatalogueSeries`.

**The `Found` stub is part of step 3's green, not a guard.** The verifier
sends a generated `200` with a random id, and Mockito answers `null` to an
unstubbed call, seen as `403`: the stub is what makes that case green. The
keyed `404` then needs its own exact stub, as `findingABookshelfAnswers`
pairs `Found` and `NoSuchBookshelf`.

**The list's `id` arrives in step 5, after the operation.** S5's second
case takes its id from the series list, so it stays red until the list
answers one; `ListCatalogueSeriesTest` proves the id where it is chosen,
and `SeriesResponse.id` is a copy with no step of its own. Rejected: adding
the id before the bump — no red would motivate it.

**`CatalogueSeries.id`, not `seriesId`.** The type is the series as the
catalogue answers it, so its own id is `id`, as `ReaderBookshelf.id`.
