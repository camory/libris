edition and not an aggregate, that the domain names and the API answers:
`SeriesId`, minted by persistence, with no `new()`.

## Goal
Both S5 cases hold over HTTP on `v0.13.0`, through the use case, result,
controller and responses behind which T102 finds the series.

## Rules in play
- D04 — the pin moves from `v0.12.1` to `v0.13.0`, nothing else of the
  contract; every earlier case but the series list stays green unchanged.
- D07 — the pin bump is the first red, the controller its green; the two
  S5 methods of `SeriesPageScenarios` are un-skipped and nothing else in
  that file changes; the contract test's stubs answer a found series
  filling every constrained field, and no hand-written web test exists.
- D02 — the controller calls use cases only; the existing
  `SeriesController` serves the resource; `BookResponse` is imported from
  `web.catalogue`.
- D10 — `FindCatalogueSeries` is named by its sentence and exposes
  `operator fun invoke` alone; responses map themselves through `from`, the
  controller maps nothing; the `when` arrows aligned; SQL keywords upper
  case; Given, When, Then; fixtures below the class and its helpers.
- D11 — ids are strings in JSON; the series' id is the uuid of its row;
  the not-found answer is a problem with `type` and no `detail`; an outcome
  of the use case, never an exception; the port's answer promises no order.
- D12 — a series stays a value of the edition: `SeriesEntry` and `Edition`
  are unchanged; the row's id no repository can read comes through the
  catalogue's query port, in the `domain` of the context that asks.

## Risks and decisions
**Fit.** One run: a pin, a finder with two slice cases, a unit case, a
constant use case, two responses, two scenarios. Rejected: a split; the
bump reds the list's `id` and the new operation at once (D04).

**`SeriesId` in `bibliography.domain`, without `new()`.** The `series` row
is the bibliography's (`JdbcEditionRepository` writes it), so its id sits
beside `SeriesEntry`, a value class as every id of D11; persistence mints
it (`nameIdOf`), never a use case, hence no `new()`. Rejected: a bare `UUID` past the controller; `SeriesEntry`
carrying the id (D12 names it name and tome, built by sources that know no
row); an aggregate `Series` (the spec keeps it a value of the edition).

**The id through `CatalogueEditions.findSeriesIds`.** No aggregate carries
the row's id, so no repository can answer it: D12's query port of the
context that asks, beside the catalogue's other read of `series`, answering
ids, no aggregate rebuilt. The reader's holdings bound it, as
`findFirstOfEachSeries`, and the answer is keyed by edition, so the use
case attaches the id to the editions it already groups. Rejected:
`findFirstOfEachSeries` answering the ids too (six slice cases rewritten,
two rules in one statement); a map keyed by name (a matching of names in
Kotlin beside the database's `LOWER(name)`); a port of the bibliography
(D12 places it in the asking context). Whether T102 reads the series'
editions through it is T102's brief's call.

**`FindCatalogueSeries` and `FindCatalogueSeriesResult`.** The series are
the catalogue's (`ListCatalogueSeries`), and a find by id with its outcome
follows `FindBookshelf`: `Found`, `NoSuchSeries` (S5's words). `Found`
holds a `CatalogueSeries`, since the page's name, count, cover and kind
are the list's, and the books as `HeldEdition`, which `BookResponse.from`
takes. Rejected: `FindSeries` (the catalogue's word dropped, unlike its
sibling); a `Found` of editions alone (the list's values computed twice).

**`Found` before anything produces it.** The generated `200` needs it now;
the stub produces it, as T092's did; last, since it requires the `id`.

**The id that is not one.** Taken as a `UUID` path variable,
`ProblemAdvice`'s `TypeMismatchException` handler answers it `400`
`/problems/validation` before the controller, proven by the contract's
`auto:` case; no code of its own. Rejected: a text path variable checked
in the controller (a check the framework already makes, and answers).
