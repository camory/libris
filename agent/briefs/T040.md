# T040 — The add Libris does not answer

**Backlog line:** Frontend: the add Libris does not answer. When Libris does
not answer the add, *Erreur lors de l'ajout, veuillez réessayer plus tard.* as
a message in `danger` under the button, which is back, and the card as it was,
no copy added; a new lookup replaces the message with the rest (U04, U05,
U08). The add leaves the view for the first composable,
`useAddBookToBookshelf(meApi, bookshelfApi)` in `application/`, that exposes
its state and `add(edition)`; the view renders that state (D05, D10). The
lookup stays in the view. Composable tests over the fakes with no component
mounted, the failure among them; view test of the not-added state; the
scenario with the API failing. Realises S5; un-skips `S5 Libris unavailable
during the add`.

**Serves:** spec `bookshelf` S5 and the *Screen* state *Not added*; PRD §4.1,
§4.3; decisions D05, D07, D10; screen rules U04, U05, U08. The TASKS question
*A refused add on the card* stands answered by the line for this task: every
failure, a problem as a rejection, reads as S5.

**First of its kind:** the **first composable of `application/`**, the first
frontend use case in D10's form, with the first spec of a use case run over

## Goal
When this task is done, a tap on *Ajouter à ma bibliothèque* that Libris does
not answer leaves the card as it was, gives the button back and says under it
to try again later, instead of a button busy forever and an unhandled
rejection. The add lives in `useAddBookToBookshelf`, which the lookup's own
composable will follow.

## Risks and decisions
**The state is one union, `AddState`, discriminated by `status`.** The view
renders exactly one of four states, the spec's *Adding*, *Added*, *Not added*
and the ready card, and `notAdded` takes the spec's name; the copy exists only
in `added`. The key is `status`, not the ports' `outcome`, since `ready` and
`adding` are no answers.
- Rejected: three refs (`adding`, `copy`, `failed`) — they allow states no
  spec describes, busy and failed at once.

**A fresh add for every card.** D10 gives the composable one function, so it
cannot be told that a new lookup forgot the previous card. The view builds a
new add with each lookup's answer, calling `useAddBookToBookshelf` again, and
renders the current one. The composable therefore holds refs only, no
lifecycle hook and no `inject`, since it is called outside `setup`. An add
still running when a newer card lands now changes an add the view no longer
renders; no case proves it, since the spec does not say what that screen
shows: the implementer rewrites T039's PROPOSED item on the late answer to
what is true after this task, not a case.
- Rejected: a `reset()` beside `add` — a second function against D10.
- Rejected: the state keyed by the edition — the fakes answer the same object
  on every lookup, and T039's *offers the add again on the next card* would
  red.
- Rejected: the composable taking the edition as a reactive argument — the
  line fixes its signature to the two ports.

**Every failure is S5.** A problem answer, a rejected add and a rejected
reader all end in `notAdded` and the one sentence, as the TASKS question
records; the composable does not read the problem's `type`.

**The reader stays asked on the tap**, as T039 decided, now inside the
composable: its rejection is Libris not answering the add.

**The file is named after what it exports**, `useAddBookToBookshelf.ts`,
as `createLibrisApp.ts` and `bootstrap.ts` are; `application/` stays flat,
beside the ports.

**The message sits in the card's block, 8 under the button**, U04's and
U05's spacing for what belongs to a control, not the lookup's message 20
under the card, which stays as it is. Its key is `isbn.addError`, beside
the lookup's `isbn.error`.

**The step 7 double is written in the case**, a `MeApi` literal, not a
change to `FakeMeApi`: one case needs it, and the shared fake stays as the
scenarios use it.
