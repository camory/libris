## Goal
`series_name_unique` ignores case, accents and the spaces at a name's ends,
and `JdbcSeriesRepository.findOrInsert` resolves its conflict on that index,
so *asterix* followed by a space lands on the stored *Astérix*, whose
spelling stays. The form of T121–T127 sends the series the reader types;
this is what keeps the house from doubling a series on it.

## Rules in play
- D12 — the series' name rule spans every series: the schema's unique
  index is its one implementation, resolved inside `findOrInsert`'s one
  statement; `HoldEdition` keeps what the repository answers; no folding,
  trimming or lookup of the name in Kotlin, in `Series`, `SeriesEntry`,
  `NewBookRequest` or a use case.
- D02 — the schema changes through a Flyway SQL file, never `ddl-auto`;
  the statement stays hand-written SQL over `JdbcClient` in
  `JdbcSeriesRepository`.
- D11 — the migration is `V014__short_description.sql`, three digits;
  `V003` and every merged migration stay byte for byte as they are.
- D07 — the second S5 method of `EditionFormScenarios` is un-skipped and
  nothing else in that file changes but its now unused `Disabled` import;
  the rule is proven in the JDBC slice, the class that owns the statement;
  every database-backed class starts each case, and now each context, from
  a schema cleaned and migrated by Flyway; no web test.
- D08 — the tests migrate the given database through Flyway's `clean` and
  `migrate`; nothing drops or recreates the database.
- D10 — SQL keywords and functions upper case (`BTRIM`, `COLLATE`),
  identifiers snake_case; no rationale and no `D##` in code or SQL.

## Risks and decisions
**Fit.** One run: one migration of two statements, one SQL constant, one
test fixture moved, two slice cases, one un-skip; about nine files.
Rejected: a split of the fixture into a task of its own (with no `V014` it
changes nothing a test can see, and `V014` cannot go green without it).

**The collation of `V005`, under `BTRIM`.** `ignoring_case_and_accents`
already orders the catalogue, so the index matches names as the screen
sorts them; `BTRIM` removes the spaces at the ends, which the collation
counts. Measured in the sandbox PostgreSQL on 2026-11-01: *asterix *,
*  ASTERIX* and *ASTÉRIX* answer the stored *Astérix* row, *Œuvres* and
*oeuvres* one row, *Øre* and *ore* one row (unlike `BookshelfName.isSameAs`;
the index is the rule), *Aste rix* and *Astérix-* rows of their own.
Rejected: `unaccent` (D03's search migration brings the extension, not
this task; a second folding beside the collation); `LOWER` with a Kotlin
fold before the insert (the rule out of the index, D12).

**The conflict target's form.** Measured: `ON CONFLICT ((BTRIM(name))
COLLATE ignoring_case_and_accents)` infers the index, and so does
`((BTRIM(name)))`; `((BTRIM(name) COLLATE ignoring_case_and_accents))`,
the collation inside the expression, matches no index (*there is no unique
or exclusion constraint matching the ON CONFLICT specification*). The
implementer writes the first; a new gotcha item records the trap.

**Rows already stored.** Tophe checked, for #320, that neither staging nor
production holds two series that differ only by case, accents or the
spaces at their ends, with this collation; so `V014` merges nothing.
Should a pair appear before the deploy, `CREATE UNIQUE INDEX` fails,
PostgreSQL rolls the migration back whole, the start is refused, and the
previous tag runs on the untouched schema. Rejected: a merge in `V014`
(which spelling stays and where the editions go is a product question
no document answers).

**`CleanSchema` at every database-backed context's start.** Measured on
2026-11-01 with a throwaway `V014`: a JDBC slice context, which resolves no
`V013` bean, fails Flyway's start validation on a database where a
scenario applied `V013` (*Detected applied migration not resolved
locally: 013*), every slice class red; with the slices fixed alone, a
scenario context starting on a database a slice migrated fails on *resolved
migration not applied to database: 013*. With `CleanSchema` imported by
both annotations the whole `test` task ran green (488 cases), in both
orders. It is D07's fresh schema, taken at the start as well as before
each case, and the fixture `LibrisApplicationTest` already used.
Rejected: `spring.flyway.ignore-migration-patterns` on each annotation
(two patterns for two directions, and a slice that can stop seeing a
migration it should); the `V013` bean in the slice (it needs the BnF
lookup and its configuration); `validate-on-migrate=false` (it hides an
edited migration everywhere).
