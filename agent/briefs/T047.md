# T047 — The catalogue listed

**Backlog line:** Frontend: the catalogue listed — one block on `surface`,
a row per edition in the order of the answer: cover or stand-in, série ·
tome, title, authors, the bookshelves in `muted` with *· 2 exemplaires*; a
row leads nowhere. Realises S1 on the frontend and un-skips its test (full
text in `agent/TASKS.md`).

**Serves:** spec `catalogue` S1 and the *Screen* state *Listed* (first page
only); PRD §3 (*Edition*, *Series*, *Volume number*, *Author*), §4.1; D05,
D07, D10; U01, U02, U03, U05, U06, U07, U08.

**First of its kind:** the first **list of ouvrages** on a screen: a
`CatalogueRow`, one `listitem` per edition and the compact form of an
ouvrage beside U06's card. Also the first token of U02's **row title** step in
`style.css`, and the first **shared fixture of `Book`s** (`src/fixture/Books.ts`).

## Goal
When this task is done, `/catalogue` lists the books of the first page it
receives, one row each, in the order of the answer. S1 now passes on the
frontend. The next page (T049) and the failed page (T048) build on this list.

## Risks and decisions
**The overline says *tome* for every kind.** `specs/kind.md` gives the
lookup card *Astérix · album 1* for a BD. The catalogue spec writes
*série · tome*, its mockup shows *ASTÉRIX · TOME 1*, and the skipped S1,
which the task may not edit, expects *Astérix · tome 1* for a BD. The row
follows the catalogue spec, with its own entry, `catalogue.series`.
PROPOSED and the PR body ask Tophe whether the catalogue should follow the
kind the way the card does.
- Rejected: reusing `isbn.card.series.${kind}`, which reds S1.
- Rejected: blocking, since the spec and its scenario agree and are explicit.

**Each author is named once.** A contribution is one author in one role, and
One Piece's sources answer Eiichirō Oda as both `WRITER` and `ARTIST`
(`src/fixture/SourceEditions.ts`). The spec's "names alone… whatever their
roles" means persons: a name keeps the place of its first contribution, as
on the card.
- Rejected: one name per contribution, which would read *Eiichirō Oda,
  Eiichirō Oda* on the Done check's One Piece row.

**The stand-in icon is `IconBook` at 22.** U07 gives no size for a row's
cover. The mockup draws it at about 20 inside the 48 by 74 block. 22 is the
nearest size U07 already lists, and 48, the card's size, would fill the
block's width. The PR body proposes adding this job to U07.
- Rejected: 24, a size U07 does not list.

**The cover behaves as the card's does**: U06's stand-in for no cover and
for a failed one; the image named *Couverture de <title>* (`catalogue.cover`)
so a test finds it by role.
- Rejected: `alt=""`, which leaves no role to read; reusing
  `isbn.card.cover`, a key of another screen.

**`CatalogueState` gains `{status: "listed", books: Book[]}`**; `next` stays
out until T049 reads it.
- Rejected: carrying `next` now, which no case reads.

**The row's cases live in `CatalogueRow.spec.ts`**, not the view spec the
backlog line names: D07 tests a component with props. The view's cases cover
the list: its rows, their order, their inertness.

**A shared fixture, `src/fixture/Books.ts`**, values like `SourceEditions.ts`,
named after the titles so they never clash with `onePiece1`. The scenario
file keeps its own books.

**The text of a row.** S1 reads the `listitem`'s `textContent` with its
whitespace collapsed. Vue drops the whitespace between two elements on
separate lines (GOTCHAS), so the parts glue together. Step 15 makes that
red on the component, and how to fix it is the implementer's choice. Neither
the compiler options nor `vite.config.ts` change.
