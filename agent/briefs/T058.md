# T058 — A failed fetch waits a day

**Backlog line:**
> - [ ] T058 Backend: a failed fetch waits a day.
>       A fetch that gets no answer, an error, or what is not a picture, and a
>       cascade that finds no picture, leaves the edition without one and
>       dates the attempt on its awaited cover from the application's clock; a
>       run within a day passes it by, a run a day later tries again.
>       A fetch gives up after five seconds or five megabytes.
>       Tests of the limits over a stubbed source; the scenario tests advance
>       the clock. Realises S8; un-skips the backend tests of S8, its three
>       cases.

**Serves:** spec `covers` S8 (its three cases), and S7's "the attempt is
dated and tried again a day later"; PRD §4.7; decisions D02, D04, D07, D08,
D10, D11, D12
**First of its kind:** the first **clock of the backend**, a `java.time.Clock`
bean the application declares and a use case reads (no production code reads
the time today), with the first bean the scenario harness puts `@Primary`
over one of the application's; and the first `timestamptz` column.

## Goal
An awaited cover whose attempt brought no picture is dated, and the worker
passes it by until a day has gone, so that a source that is down or has no
picture is asked once a day, not at every add. A picture fetch never waits
more than five seconds nor reads more than five megabytes.

## Rules in play
- D02 — the five seconds are the fetch's bound, the adapter's:
  `libris.sources.timeout` (`LIBRIS_SOURCE_TIMEOUT`, `5s` by default),
  already given to every source's client; no new setting. The use case
  never sees that bound; the date of an attempt is another matter (D11)
- D04 — no contract change, no pin moves
- D07 — the three S8 cases are un-skipped and nothing else in
  `CoversScenarios` changes; `ScenarioTest.kt`, the harness, gains one
  annotation; the use case in plain JUnit over fakes and a `MutableClock`,
  the repository in the JDBC slice, the fetch over WireMock; Given / When /
  Then on every case of two statements or more
- D08 — no new environment variable
- D10 — names from PRD §3; no private member widened; SQL keywords upper
  case; Kotlin layout by hand; no comment saying why
- D11 — the date is an `Instant` in a `timestamptz` column, set by the use
  case; one migration, `V009__awaited_cover_attempted_at.sql`, no earlier
  one touched; the port gains `update`, one SQL statement
- D12 — "due again a day after the last attempt" is `AwaitedCover`'s rule,
  answered by the aggregate, never written in the use case or in SQL

## Risks and decisions
**The attempt is dated as it starts, not after it fails.** Each add wakes
its own run on `applicationTaskExecutor`, and runs overlap until T059. In
S8's first case the fetch waits out the one-second timeout while the test,
having seen the request arrive, adds the second edition: a run dating the
failure afterwards would leave the first wait undated when the second run
reads it, and ask it again. Dated before the fetch, the date is committed
before the request leaves, so every run that follows passes it by; a stored
picture still ends the wait. *Rejected:* dating after the failure, racy in
S8; making runs exclusive here, T059's.

**The rule is `AwaitedCover.isDueAt(now)`.** It reads the aggregate's own
date (D12); the use case filters the awaited covers through it with the
clock's instant. A day is 24 hours of `Instant`s, the boundary due, so the
scenario's 25 hours and the domain test's exact day both try again.
*Rejected:* a `WHERE attempted_at <` in `findAll`, the rule in SQL;
`findDue(now)` on the port, a second reading of one rule.

**`attemptedAt` defaults to `null`.** An add creates a wait never attempted;
the default keeps `AddBookToBookshelf` and its sixteen test constructions as
they are. *Rejected:* an explicit `null` everywhere, a wide diff for no case.

**The clock is a bean of `LibrisApplication`, `systemClock`, UTC.** It is
the application's, not the bibliography's: the library's dates will read
it. The harness's bean keeps its name, `clock`, and becomes `@Primary`, so
every scenario context reads `MutableClock` and `LibrisApplicationTest` the
system's. *Rejected:* a bean named `clock` too, refused by Boot's
no-overriding default; `@ConditionalOnMissingBean` outside an
auto-configuration, order-dependent; relying on the parameter name to pick
between two beans, implicit. Tophe settles the place of an
application-wide bean when reviewing.

**`attempted_at` is read and written as `OffsetDateTime` at UTC**, the type
pgjdbc documents for `timestamptz`, mapped to `Instant` at the repository's
edge.

**Five megabytes are 5 × 1024 × 1024 bytes, read as a stream.** `pictureAt`
stops reading at the limit plus one byte and answers no cover past it; the
whole body read into memory first would pass step 12 and miss the limit's
point, which the reviewer checks. Five seconds need no code: the
`JdkClientHttpRequestFactory` timeout already closes the body stream when it
runs out (Spring 7.0.9's `TimeoutHandler`), hence step 14 is a guard.
