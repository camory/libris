## Goal

web-slice classes take the mocks they stub through their constructors
without listing them. A controller's new use case then joins one list, and
the classes without a configuration of their own share one context because
they carry one annotation, not because three lists happen to agree.

## Risks and decisions
**"Every slice test shares one context" is read as: the mocks no longer
tell the contexts apart.** `ProblemAdviceTest` and `SecurityConfigTest`
share one today only because their lists agree; after the move they share
it because they carry one annotation. `ApiContractTest` keeps a context of
its own, as on `main`, because its `@Import` of `FixedReaderHeaders` is a
different configuration, which D06 requires and which would add a reader
to every header-less request `SecurityConfigTest` expects refused. Six
contexts before and after. Rejected: `FixedReaderHeaders` in
`WebSliceConfiguration` (breaks `SecurityConfigTest`'s refusals); a filter
adding the headers only on some marker (changes a test configuration
beyond the line).

**The meta-annotation is measured, not assumed.** While planning, with
Spring Framework 7.0.9 (Boot 4.1.1), the list on `@WebSliceTest` alone
kept the three classes green at 50, 2 and 9 cases with two web contexts;
with the list on the annotation and still on `ProblemAdviceTest`, that
class failed at load with `Duplicate BeanOverrideHandler`. Hence one step.
Rejected: a base class carrying the mocks (the line names the slice's own
annotation, and it would be a second way to make a web-slice test).

**The list keeps today's order.** It is the order the controllers' use
cases arrived in, identical in the three files, so the move is a cut and a
paste a reviewer reads at a glance. Rejected: alphabetical order (every
line of the list rewritten for no reader).
