# T069 — The add wakes the worker

**Backlog line:**
> - [ ] T069 Backend: the add wakes the worker.
>       The add answers the copy, then wakes the worker, one piece behind an
>       application port the tests call the same way (D02), which runs T066's
>       use case away from the request; the catalogue then answers the cover's
>       address. Realises S3, S4; un-skips the backend tests of S3, S4.

**Serves:** spec `covers` S3 (second *Then*: "Libris answers the copy before
asking any source for a picture"), S4 (whole, the worker woken by the add),
and the spec's note "The worker is one piece of the backend's infrastructure
behind a port of the application, which the add and the tests call the same
way"; PRD §4.7; decisions D02, D07, D10, D12
**First of its kind:** the first port declared in an `application` package
(`CoverWorker`, in `bibliography.application.cover`), implemented in
infrastructure; the first infrastructure sub-package beyond `web`,
`persistence` and `lookup` (`bibliography.infrastructure.worker`); the
first work run off the request's thread, on Spring Boot's autoconfigured
`applicationTaskExecutor`; the first infrastructure piece outside `web` that
calls a use case.

## Goal
An add that answers a copy wakes the worker, which runs `FetchAwaitedCovers`
on another thread, so the copy is answered at once and the cover of an
edition whose chosen source is inventaire.io shows in the catalogue a moment
later. This is the first time a stored cover reaches a reader. T054 to T059
build on it.

## Rules in play
- D02 — `CoverWorker` is the port the spec names "a port of the
  application": an interface of `bibliography.application.cover`, beside
  `FetchAwaitedCovers`, the bibliography's since the worker runs a use case
  of the bibliography; `ExecutorCoverWorker` implements it in
  `bibliography.infrastructure.worker` and depends on `application` only;
  `AddBookToBookshelf` (library) depends on the bibliography's port, never
  the reverse; `ArchitectureTest` stays as it is and green
- D07 — *S3* and *S4* of `CoversScenarios` lose their `@Disabled("covers")`
  and nothing else in the file changes; the use case is proven in plain
  JUnit over fakes, the worker in plain JUnit over an executor the test
  holds; no Spring test of the wiring, the scenarios prove it; every case
  of two or more statements carries Given / When / Then
- D10 — the port is named for what it is, its verb `wake()`; the variable
  holding a use case is its class name in lower camel case
  (`fetchAwaitedCovers()`); no visibility widened; constructor layout and
  the top-down order of a file kept by hand; members imported, not
  qualified
- D12 — the add's transaction ends before the worker is woken: the worker
  is woken outside the `TransactionOperations` block, so a run on another
  thread finds the awaited cover committed
- D08 — no dependency and no configuration property added: the executor is
  the one Spring Boot already builds
- D04 — no contract edit, no pin bump: the add's answer does not change

## Test plan
One step is one case is one commit; `./gradlew detekt` before each commit;
a step is committed before its guard's mutation is checked. A step marked
red that is green on arrival becomes a guard: its commit body names the
mutation that reds it, checked and reverted, and the PR body lists it.

**The worker** — `ExecutorCoverWorkerTest` (new,
`bibliography.infrastructure.worker`, plain JUnit), over a real
`FetchAwaitedCovers` built on `EditionsInMemory`, `AwaitedCoversInMemory`,
`CoversInMemory`, `CoverFetchAnswering` and `withoutTransaction()`, with the
edition `9782723488525` stored and awaited with `INVENTAIRE`, as
`FetchAwaitedCoversTest` sets it up.
1. **red then green — a waking runs the fetch of the awaited covers.**
   After `coverWorker.wake()`, the fetch was asked `9782723488525`.
   Creates `CoverWorker`
   (`fun wake()`) and `ExecutorCoverWorker`, a `@Component` implementing it
   and taking `FetchAwaitedCovers`.
2. **red then green — a waking leaves the run to the executor.** The
   executor of the test keeps what it is handed and runs nothing; after
   `wake()` the fetch was asked nothing. `ExecutorCoverWorker` gains
   `java.util.concurrent.Executor`, Spring Boot's `applicationTaskExecutor`
   in the application; the case of step 1 gives it an executor it runs
   by hand. Red while the run is called on the caller's thread.

**The add** — `AddBookToBookshelfTest`. `AddBookToBookshelf` gains the
`CoverWorker` (six parameters, `LongParameterList`'s limit); the test's
fake is `CoverWorkerObserving<S>(observe: () -> S)` (new,
`bibliography.fixture`), which records at each waking what `observe`
answers, in `wakings: List<S>`, as `TransactionsObserving` records its
transactions. The existing cases take it with no observation.
3. **red then green — an added ouvrage wakes the worker.** Léa adds One
   Piece to her bookshelf; `coverWorker.wakings` has one entry.
4. **guard — the worker is woken after the add's transaction.** The use case
   built over a `TransactionsObserving`, the worker observing
   `transactions.recorded.size`; after the add, `wakings` is `[1]`.
   Mutation: wake inside the transaction's block (`[0]`).
5. **guard — a refused add wakes no worker.** A viewer of the bookshelf adds
   to it, `NotAnOwner`; `wakings` is empty. Mutation: wake first in
   `invoke`, before the bookshelf is read.

**The scenarios** — `CoversScenarios`, only `@Disabled("covers")` removed
6. **guard — S4 The worker fetches the chosen cover.** Green on un-skip:
   the add of step 3 wakes the bean of step 2. Mutation: remove the call to
   `wake()` from `AddBookToBookshelf` (the case fails with *still not true
   after 5s*).
7. **guard — S3 The add carries the cover's source.** Green on un-skip.
   Mutation: `ExecutorCoverWorker.wake` calls `fetchAwaitedCovers()` itself.
   The scenarios' source timeout is one second, and S3 allows two, so the
   mutation may leave S3 green: run it, and the PR body says what it

8. **Tidy on green**, the gate run plainly, then the documents: the task

**gotchas/backend.md:** add one item: an add wakes the worker on
`applicationTaskExecutor`, so a scenario add whose chosen source is

## Risks and decisions
**`CoverWorker.wake()` in `bibliography.application.cover`.** The spec puts
the worker "behind a port of the application"; the port is the
bibliography's because the run is (`FetchAwaitedCovers`), and the library
already depends on the bibliography's application (`LookupIsbnForReader`).
Named for what it is, as D10 names a port, its verb what the backlog line
says. *Rejected:* a port in `library.application`, which the bibliography's
infrastructure could not implement (D02's rule 4); a port in `domain`, which
would carry a use case of the application.

**`ExecutorCoverWorker` in `bibliography.infrastructure.worker`.** The worker
is no client of a source, no store and no edge of the API, so none of the
three existing sub-packages fits; T059 adds the worker's schedule there.
Named after what it runs on, as `JdbcEditionRepository` and
`FileCoverStore` are. The PR body proposes the D02 bullet: "
`bibliography.infrastructure.worker` — the worker, which runs
`FetchAwaitedCovers` away from the request, behind the application's
`CoverWorker`". *Rejected:* `infrastructure.lookup`, whose classes are the
sources' clients.

**Spring Boot's `applicationTaskExecutor`, injected as `Executor`.** Already
built by Boot, no dependency, no property; the test hands its own executor,
time and threads being a boundary the test holds. If the injection by type
is ambiguous, the implementer qualifies it by that bean's name and says so.
*Rejected:* a single-thread executor of the worker's own, which serialises
the runs, T059's rule; `@Async`, which needs `@EnableAsync` and hides the
thread from the test.

**Every add answering a copy wakes the worker,** a held edition's too. S9
wakes the worker when "an ouvrage is added", and S8 counts on another add's
waking; a run with nothing to take asks no source. *Rejected:* waking only
when an awaited cover was inserted, a branch no scenario reads.

**The race between a run and the next case.** A run started by S3 can still
be waiting on its picture when the next case resets the sources and the
schema; it then stores nothing, the picture never coming. Should a case
show a request it never made, the run of an earlier case reached its
journal: report it in the PR and `agent/PROPOSED.md`, and change no
scenario file.
