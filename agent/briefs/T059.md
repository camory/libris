**First of its kind:** the first **scheduled work** of the backend
(`@EnableScheduling`, a `@Scheduled` method, its period a setting read by a
placeholder in the annotation rather than bound to a properties class); the
first **log line** written by Libris code (an SLF4J logger in
infrastructure); the first **executor a piece of infrastructure owns**
instead of Spring Boot's; the first **identity column**, an order of the
persistence that the domain never sees.

## Goal
The worker runs at start, once a day and after each add, every run on one
thread of its own, so runs queue instead of overlapping, and each run takes
the awaited covers in the order they arrived. The backend can then be
deployed: the editions stored before covers get theirs at the first start,
and the covers volume is writable.

## Risks and decisions
**One thread of the worker's own, built in `WorkerConfig`.** Every waking,
from an add or the schedule, goes through `wake()` to that one thread, so
two runs never fetch at once and the add still answers at once. Built in a
`@Configuration` as `LookupConfig` builds the sources, so no qualifier picks
between `Executor` beans once `@EnableScheduling` adds a scheduler. The
thread must not keep the JVM alive (a virtual thread, as
`LookupEditionByIsbn` uses, or a daemon), since nothing shuts it down.
*Rejected:* a lock inside the run, which parks a pool thread per waking
and needs a test of threads; `applicationTaskExecutor` sized to one
thread, a setting that would serialise every other use of it.

**The order is an identity column, `awaited_cover.arrival`.** It answers
"in the order they were added" from the awaited cover's own table, as
`edition.search_text` is persistence's alone (D03). `V010` numbers the
existing rows in the table's order, which on the first deploy is the order
`V008` inserted them, all awaiting since that deploy. *Rejected:* ordering
by `edition.id` through a join, which D12 forbids a repository; an
`awaitedSince` instant on `AwaitedCover`, a seventh parameter for
`AddBookToBookshelf` (`LongParameterList`) and an audit date D11 refuses;
`ORDER BY isbn13`, not the order added.

**At start and every day through one `@Scheduled` on `wake`.** A fixed delay
with `initialDelay = 0` is the run at start and the daily run in one
annotation, and goes through the same thread as the add's. The period
`libris.worker.every`, `P1D` unless `LIBRIS_WORKER_PERIOD` says otherwise;
the variable does not carry the setting's environment form (gotcha of
`LIBRIS_COVERS_DIR`). *Rejected:* a cron and an `ApplicationReadyEvent`
listener, two triggers for one schedule; a `@ConfigurationProperties`
class, which `@Scheduled` reads only through SpEL.

**One INFO line per run, in `ExecutorCoverWorker`.** The backlog line checks
the schedule in the log, and no line of Libris shows a run today. The
logger lives in infrastructure, since `ArchitectureTest` keeps SLF4J out of
`application`. *Rejected:* a line in `FetchAwaitedCovers` (D02, rule 2).

**`LibrisApplicationTest` starts on a cleaned schema.** The run at start
fires in every context that boots the whole application. The boot test
uses the real sources' addresses, so a row a scenario left awaiting would
be fetched from the internet, dated with the system clock and maybe
written over a later scenario's row of the same ISBN. Cleaning before
migrating, in that test's context only, leaves it nothing to take. The
scenario contexts ask the stubs, which answer at once, before the first
case's `FreshSchema`. *Rejected:* a setting that turns the run at start
off, production code for a test.

**For the PR body.** Propose for D02's `infrastructure` list:
"`bibliography.infrastructure.worker` — the worker, which runs
`FetchAwaitedCovers` on one thread of its own, woken by the add, at start
and every `libris.worker.every`"; and for D09: "the backend image creates
`/var/lib/libris/covers` for its user, where the `covers` volume is
mounted".
