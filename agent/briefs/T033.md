## Goal
When this task is done, the first visit of a reader Libris has never seen
stores the reader, a bookshelf named *Bibliothèque de* their name which they
own, and the link from the reader to that bookshelf as their default, all in
one transaction; a reader Libris already knows is answered exactly as today.
It matters now because T037 makes `defaultBookshelf` a required field of the
`me` answer and T035 puts copies on a bookshelf: both need a bookshelf to
exist for every reader before they can serve anything.

Nothing of the API changes in this task. `me` keeps the body it has, the
scenario tests keep waiting for T037, and the proof of the inside is unit and
slice tests.

## Risks and decisions

**The default bookshelf is a column on `reader`, not a flag on the member
row.** PRD §3 gives a reader one default bookshelf, so the fact belongs to the
reader. A `is_default` flag on `bookshelf_member` would need a partial unique
index to say "one per reader" and would put reader-scoped state on the
`Bookshelf` aggregate. The column is nullable in SQL because the bookshelf row
must exist before the reader can point at it, and in the domain because a
reader that has just been constructed has none yet — this is a real state of
the aggregate, not a fallback hiding a missing value, which is why it may
carry a default (`= null`) where `SourceEdition.kind` could not in T031. The
default also keeps every existing `Reader(...)` construction site compiling
untouched, which is what keeps `infra.web` out of this task's diff.

**The transaction boundary is a second bean, and the duplicate-username catch
stays outside it.** The three writes of a first visit must be one unit, so the
method that performs them is `@Transactional`. Two traps forbid putting the
annotation on `ReaderVisit.visit` itself: Spring proxies calls between beans,
not a method calling another on `this`, so a boundary must be a bean's method
called from somewhere else; and PostgreSQL aborts the whole transaction on the
unique violation of a lost race, so the existing catch of
`DuplicateUsernameException` followed by a second `findByUsername` cannot run
inside the transaction that raised it (`current transaction is aborted,
commands ignored until end of transaction block`). Hence: `ReaderVisit` stays
plain and keeps the find, the delegation and the catch; the new bean owns
`@Transactional` and the three writes, and its failure rolls the bookshelf
back with the reader. If this trap costs a cycle anyway, it is an item for
`agent/GOTCHAS.md`.

**The join table is `bookshelf_member`, not `bookshelf_reader`.** D11 names a
join table after both sides, and the second side here is the reader; but PRD
§3 gives the join entity its own word, *Member*, and the domain type is
`Member`. The table takes the name the product uses, and its columns name both
sides.

**`MemberRole` declares `VIEWER` although this phase writes only `OWNER`.**
The closed set is the product's vocabulary in PRD §3, as `AuthorRole` was in
T013, and the `CHECK` must accept both for the same reason; the task creates
`OWNER` members only, and no test writes a `VIEWER`.

**The bookshelf's name is built in `application`.** `Bibliothèque de ` followed
by the display name is data Libris stores, not a word a screen shows, and the
backend has no message catalogue (U07 binds the frontend). The application
builds it when it welcomes the reader; the domain stores whatever name it is
given.

**A read answers whole aggregates in a stated order.** The reader's
bookshelves come back with their members; one query joining the two tables,
grouped in Kotlin, or two queries — either is fine, but the order the test
asserts must be the order the SQL states, never the order the database
happens to give.

**The readers already stored keep no default, and T037 will require one.**
`V002` adds a nullable column and backfills nothing; the staging readers
created before this task would answer `me` with no `defaultBookshelf` once
T037 makes the field required. Repairing them is neither in this task line nor
in S1, and a backfill written without a test to motivate it is exactly what
`CLAUDE.md` forbids. The implementer must: say it plainly in the PR body, and
add it to `agent/PROPOSED.md` as a question for Tophe — backfill the existing
rows in the migration of a later task, or recreate the staging database before
T037 deploys. It is a human's call, not a run's.

**Editing `V002` after a first run costs a database.** Flyway refuses a
changed checksum for an applied migration, and only `FreshSchema` cleans; the
boot test does not. If the migration must change after a gate has run, run a
JDBC slice test class alone first (it cleans and migrates) before running the
gate again. Writing the migration whole at step 4 of the test plan is what
avoids this.
