# T066 — The worker's run fetches the chosen inventaire.io cover

**Backlog line:**
> - [ ] T066 Backend: the worker's run fetches the chosen inventaire.io cover.
>       A use case of the bibliography takes each awaited cover whose chosen
>       source is inventaire.io, asks inventaire.io by ISBN for the picture and
>       stores it as T065 does; the edition of that ISBN records the cover's
>       name and the wait ends, in one transaction (D12). An awaited cover
>       whose chosen source is another, or none, is passed by; one whose fetch
>       brings no picture keeps waiting. Tests of the use case over fakes, of
>       the inventaire.io fetch over a stubbed source and of the JDBC slice;
>       nothing runs it yet; un-skips nothing.

**Serves:** spec `covers` S4 (first and second *Then*: "asks that source
alone for the picture of the edition's ISBN", "stores it … under a name
made from its bytes"), S6's "inventaire.io is asked for its picture at 600
tall", S7's "only a stored picture ends the wait"; PRD §3, §4.7; decisions
D02, D07, D10, D11, D12
**First of its kind:** the first `update` of a repository port
(`EditionRepository.update`) and the first `delete` (`AwaitedCoverRepository.delete`);
the first port answering a source's bytes (`CoverFetch`), and the first
adapter implementing two domain ports (`InventaireCoverLookup`); the first
shared fixture used by both contexts' use-case tests (`TransactionsObserving`
moved to `fr.amory.libris.fixture`).

## Goal
`FetchAwaitedCovers` fetches from inventaire.io the picture of each edition
whose awaited cover names it, stores it, names it on the edition and ends
the wait; T069 then only runs it away from the request.

## Rules in play
- D02 — `CoverFetch` is a port of `bibliography.domain.cover`, beside
  `Cover` and `CoverStore`; `FetchAwaitedCovers` lives in
  `bibliography.application.cover`, beside `FindCover`, and depends on
  domain ports only; the fetch's bound is the adapter's, the timeout of
  `LIBRIS_SOURCE_TIMEOUT`, and the use case never sees time
- D07 — the use case in plain JUnit over fakes; the adapter over WireMock;
  the two repositories in the JDBC slice; no scenario un-skipped or
  edited; every case of two or more statements carries Given / When / Then
- D10 — the use case is `FetchAwaitedCovers`, `operator fun invoke()` and
  nothing else public; the port's verb is `fetch`; no private member of
  `InventaireCoverLookup` made public; SQL keywords upper case; Kotlin
  layout kept by hand; a file reads from the top down
- D11 — `update` and `delete` are each a hard write over `JdbcClient`,
  nothing chooses between `insert` and `update`; no migration: `awaited_cover`
  and `edition.cover_name` exist since `V006` and `V007`
- D12 — the edition's new name and the end of its wait are written in one
  `TransactionOperations` block, proven with `TransactionsObserving`, the
  picture written to the store before it; the edition is changed by
  building it again (`copy(coverName = …)`) and calling `update`; each
  repository reads and writes its own aggregate

a step is committed before its guard's mutation is checked. A step marked
red that is green on arrival becomes a guard: its commit body names the
mutation that reds it, checked and reverted, and the PR body lists it.

## Risks and decisions
**`CoverFetch.fetch(isbn): Cover?`, in `domain.cover`.** Each source finds
its picture its own way (inventaire.io's entity, Open Library's covers by
ISBN, the BnF's ark), so the port takes the ISBN and answers the cover,
`null` for no picture, as `CoverLookup` answers `null` for no candidate.
It answers a `Cover`, so it sits beside `Cover` and `CoverStore`. The use
case passes by what is not `INVENTAIRE`, as the backlog line says.
*Rejected:* `fetch(url)`, which the BnF's ark cannot serve; a `source`
property on the port or a map of fetches by source, which no case of this
task reads (T054 brings the second fetch).

**`InventaireCoverLookup` implements `CoverFetch` too.** Fetching is its
lookup's answer followed by a `GET` of the address it names, on the same
client and bound, so the `100x600` rule stays in one place and no private
member is widened (D10). *Rejected:* a class `InventaireCoverFetch`
repeating the entity query; one over the lookup's public door, a second
client and bean for one `GET`. The PR body proposes D02's sentence on
`bibliography.infrastructure.lookup`: the inventaire.io client "answers a
picture's address, and fetches that picture for the worker".

**`EditionRepository.update(edition)` writes the whole aggregate.** D11
names `update`, D12 says an aggregate is changed by building it again and
calling it; an `update` that wrote `cover_name` alone would drop the next
caller's change silently. It writes the row, finds or creates the series
row as `insert` does, and writes the contributions again (delete then
insert). *Rejected:* `recordCover(isbn, name)`, a verb D11 does not name;
an `UPDATE` of `cover_name` alone under the name `update`.

**`AwaitedCoverRepository.delete(awaitedCover)` ends the wait.** S7 says
only a stored picture ends it, and the row holds nothing else; D11's
deletes are hard. Named after its statement as `insert` and `update` are,
taking the aggregate as `insert` does. *Rejected:* a state column on
`awaited_cover`, a migration no case needs; `delete(isbn)`, a second
spelling of the key the aggregate carries.

**The store is written before the transaction.** Files are not
transactional: written first, a crash leaves a picture no edition names,
never a name with no picture; step 11 observes it.

**`TransactionsObserving` moves to the root `fixture`.** The bibliography's
test needs it, and D02 forbids the bibliography to depend on the library;
the root `fixture` already holds what both contexts share (`MutableClock`,
`FreshSchema`). *Rejected:* a copy in `bibliography.fixture`.

**An awaited cover with no edition** cannot exist in the database (the
foreign key of `V006`); no step proves how the nullable `findByIsbn` is met.
