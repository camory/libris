# T002 — Frontend skeleton

**Backlog line:** Frontend skeleton. Vue 3 `<script setup>`, Vite, TypeScript
strict, Vue Router, Pinia, vue-i18n (`fr` only), Tailwind, Vitest + Vue Test
Utils, Prettier; `.node-version` 24, `save-exact` (D05, D10). Layers
`domain/ application/ infra/ ui/` with eslint-plugin-boundaries enforcing the
five D05 rules. `vite-plugin-pwa`: manifest (name Libris, theme colour,
placeholder icons) and precached app shell only; API caching comes with the
offline feature (PRD 4.8, P2). Dev server proxies `/api` to `localhost:8080`.
Home view: static French title from i18n. `npm test` = `vue-tsc` + ESLint +
Vitest with V8 coverage (D07); one component test; `npm run build` green.
`frontend/README.md`: commands.
**Serves:** PRD §4.8 (install half only), §5 (mobile first, French UI,
testability); decisions D01, D05, D07 (frontend gate), D10.

## Goal
When this task is done, `frontend/` is a Vue 3 + Vite application that builds,
serves a home page whose title comes from the French i18n messages, and whose
`cd frontend && npm test` is the D07 gate for the code that exists. It matters
now because T004 (image), T006 (member profile screen) and every later feature
build on that gate, and the CI `frontend` job starts running the moment
`frontend/package.json` exists.

Read `agent/PROGRESS.md`'s T001 entries first. They are about the backend, but
three lessons carry over: the proof hook wants the gate plain and last in its
command; `.gitignore` gains a line only when a real run proves a file is left
untracked; a tool version is pinned to what was measured, not to what looks
newest.

## Acceptance criteria
- [ ] `cd frontend && npm test` exits 0, run plainly (nothing piped or chained
      after it) so the sandbox records the gate.
- [ ] `npm test` runs, in this order and all three: `vue-tsc` type check,
      `eslint`, `vitest run --coverage`. Proven by the run's own output, pasted
      in the PR body, and by three throwaway-and-revert edits, each failing the
      gate on its own step and each failure line pasted in the PR body:
      a type error in `src/ui/views/HomeView.vue`; an ESLint violation; a
      changed assertion in the component test.
- [ ] After `npm test`, `frontend/coverage/lcov.info` exists (D07: V8 coverage,
      LCOV).
- [ ] One component test, `src/ui/views/HomeView.spec.ts`, mounts `HomeView`
      with the i18n plugin and asserts the rendered French title. It is the
      only test file; it passes.
- [ ] `npm run build` exits 0 and `dist/` contains `index.html`, `sw.js` and
      `manifest.webmanifest`; the manifest's `name` is `Libris` and lists the
      two placeholder icons; `sw.js`'s precache manifest contains
      `index.html`. Commands and output pasted in the PR body.
- [ ] The built CSS is Tailwind's: a utility class used by `HomeView.vue`
      appears as a rule in the emitted `dist/assets/*.css`
      (`grep -o '\.<class>{' dist/assets/*.css`), pasted in the PR body.
- [ ] The five D05 rules are enforced by `eslint-plugin-boundaries`. Each is
      proven by a throwaway file or import that makes `npx eslint .` fail, one
      at a time, deleted afterwards; the five failure lines are pasted in the
      PR body:
      1. `domain` importing from `application` (and `import { ref } from 'vue'`
         in a `domain` file) fails;
      2. `application` importing from `infra` fails;
      3. `infra` importing from `ui` fails;
      4. a file in `ui/components` importing from `application` fails;
      5. a file in `ui/views` imported by anything other than the router or
         `main.ts` fails.
- [ ] The dev server proxies `/api`: with no backend running,
      `npm run dev` then `curl -s -o /dev/null -w '%{http_code}'
      http://localhost:5173/api/v1/ping` answers a proxy failure status
      (5xx), not the SPA's `200`. Command and output pasted in the PR body.
- [ ] `frontend/package.json` pins every dependency exactly (no `^`, no `~`),
      `frontend/.npmrc` sets `save-exact=true`, `frontend/.node-version` exists,
      and `frontend/package-lock.json` is committed (the CI job runs `npm ci`).
- [ ] TypeScript is strict: `tsconfig.json` has `"strict": true`, and the
      type-check step of `npm test` covers `src/**` and the config files.
- [ ] `git status --porcelain` is empty after `npm test`, `npm run build` and
      `npm run dev`: no `node_modules`, `dist`, `coverage`, `dev-dist` or
      build-info file is untracked or committed.
- [ ] `frontend/README.md` states the commands: install, dev, build, test, and
      what `npm test` runs.
- [ ] The CI `frontend` job is green on the pull request (`npm ci && npm test
      && npm run build`).

## Test plan
This task ships exactly one test: `src/ui/views/HomeView.spec.ts`, written
before `HomeView.vue`. It mounts the view with the i18n plugin and asserts the
French title, so it proves at once that Vitest, Vue Test Utils, jsdom and
vue-i18n are wired and that the view renders text from the messages, not a
hard-coded string.

Everything else this task delivers is a gate or a build, so it is verified by
command, each run for real and its output pasted in the PR body under **How
verified**:

1. `npm test` — the gate, exit 0, plain and last in its command.
2. Three throwaway edits, one at a time, each reverted: a type error, an ESLint
   violation, a wrong assertion — one per step of the gate.
3. Five throwaway boundary violations, one at a time, each deleted: the five
   D05 rules.
4. `npm run build`, then the `dist/` inspections of the acceptance criteria.
5. `npm run dev` in the background, `curl` on `/api/v1/ping`, stop it.
6. `git status --porcelain` after 1, 4 and 5.

Green means `cd frontend && npm test`, nothing piped or chained after it, so
the sandbox records the gate on the current tree (see
`agent/prompts/implementer.md`). Partial runs (`npx vitest`, `npx eslint .`)
are fine while working and prove nothing.

## Risks and decisions
- **Versions.** Measured on the registry on 2026-09-08 and proven to resolve
  together (`npm install --package-lock-only`, no peer conflict, 677
  packages): `vue` 3.5.42, `vue-router` 5.3.1, `pinia` 4.0.3, `vue-i18n`
  11.4.10; dev: `vite` 8.2.2, `@vitejs/plugin-vue` 6.0.8, `@tailwindcss/vite`
  and `tailwindcss` 4.3.3, `vite-plugin-pwa` 1.3.0, `typescript` 6.0.3,
  `vue-tsc` 3.3.11, `vitest` 5.0.0, `@vitest/coverage-v8` 5.0.0, `jsdom`
  30.0.1, `@vue/test-utils` 2.5.0, `eslint` 10.10.0, `eslint-plugin-vue`
  10.11.0, `typescript-eslint` 8.70.0, `eslint-plugin-boundaries` 7.2.0,
  `prettier` 3.9.6. Decision: install exactly these. A newer patch that npm
  resolves on its own is fine; do not chase a newer major found on the way
  (D10 makes an upgrade its own task). Never `--force` or
  `--legacy-peer-deps`: a peer conflict is a signal, not noise.
- **TypeScript 6, not 7.** `typescript` 7.0.2 is the current `latest`, but
  `typescript-eslint` 8.70.0 declares `typescript >=4.8.4 <6.1.0`, so the
  linter of D07 cannot run with it. Decision: pin 6.0.3, the newest TypeScript
  the toolchain accepts. "Latest stable at scaffold time" (D10) means the
  latest set that holds together. Follow-up for the PR body: revisit when
  typescript-eslint supports 7.
- **Tailwind 4 has no config file.** It is installed as the Vite plugin
  `@tailwindcss/vite` and configured from CSS (`@import "tailwindcss";`).
  Decision: no `tailwind.config.js`, no `postcss.config.js` — neither is used
  by this version, and `CLAUDE.md` forbids configuration nothing exercises.
- **eslint-plugin-boundaries 7 elements and policies.** Its API is the single
  `boundaries/dependencies` rule with `default: "disallow"` and a list of
  policies (docs: <https://www.jsboundaries.dev/docs/policies/>). Decision,
  the element types and what each may import, which is D05's five rules
  written out:

  | type | pattern | may import |
  | --- | --- | --- |
  | `domain` | `src/domain/**` | `domain` only, and no external package |
  | `application` | `src/application/**` | `domain`, `application`, externals |
  | `infra` | `src/infra/**` | `domain`, `application`, externals |
  | `ui-components` | `src/ui/components/**` | `domain`, `ui-components`, externals |
  | `ui-views` | `src/ui/views/**` | `domain`, `application`, `ui-components`, externals |
  | `ui-app` | `src/ui/App.vue` | `ui-components`, externals |
  | `ui-router` | `src/ui/router.ts` | `ui-views`, externals |
  | `ui-i18n` | `src/ui/i18n.ts` | externals |
  | `main` | `src/main.ts` | anything |

  Two points this table decides, both to be listed under *Follow-ups* in the PR
  body as proposed clarifications of D05 for Tophe, since they are readings of
  the rule rather than changes to it:
  - D05 rule 5 says nothing imports `ui/views`, yet Vue Router must. The
    router (and `main.ts`, the wiring point D05 names) are the only exception;
    every other element is still refused.
  - D05 rule 1 says `domain` imports only `domain`; read literally that
    excludes external packages too, which matches "pure TypeScript: no Vue, no
    fetch, no DOM". So `domain` alone is denied external modules.
- **Test file convention.** No document states where frontend tests live.
  Decision, derived from D07 ("one test source set… test classes are named
  after the Libris code they exercise") and from D05's `src/` layout, which
  has no `tests/` tree: a test sits beside the file it exercises and is named
  after it, `HomeView.vue` → `HomeView.spec.ts` (`.spec` is what Vitest and
  the Vue tooling emit by default). Test files are their own element category
  for the boundaries rule, allowed to import the file they test. The PR body
  proposes the matching sentence for D07; this is one file today, so it stays
  cheap to change.
- **Pinia and the router have nothing to hold yet.** The backlog line asks for
  both in the skeleton, while `CLAUDE.md` forbids what no test or feature
  uses. Decision: install and wire them in `main.ts` — the wiring is what the
  task delivers and what `npm run build` exercises — but create no store and
  no second route. The first store is T006's session (D05).
- **ESLint and Prettier must not fight.** Decision: use `eslint-plugin-vue`'s
  `flat/essential` (error prevention only) rather than `flat/recommended`
  (layout rules Prettier owns), so no `eslint-config-prettier` is needed.
  Prettier stays out of the gate: D07 lists `vue-tsc`, ESLint and Vitest, and
  nothing else. It is a `format` script and takes its indentation from the
  root `.editorconfig`.
- **`.node-version` holds `24`,** the major line, matching the CI job's
  `node-version: '24'` and the sandbox's v24.20.0. A patch pin nothing
  enforces would only drift from CI.
- **Placeholder icons with no image tooling.** The sandbox has no image
  editor. Decision: generate two solid-colour PNGs (192 and 512) with a
  throwaway `python3` command, commit the two files, and paste the command in
  the PR body so the next run can redo it. Manifest: `name` and `short_name`
  `Libris`, `lang` `fr`, `display` `standalone`, `start_url` `/`,
  `theme_color` `#1e293b`, `background_color` `#ffffff` — a placeholder theme
  to be chosen with Tophe when the first screen is designed.
- **vite-plugin-pwa scope.** `generateSW`, the default, precaching the built
  app shell. No `runtimeCaching`, no `navigateFallbackDenylist`, no dev-mode
  service worker: those belong to the offline feature (PRD 4.8, P2). If the
  service worker registration needs a virtual module import in `main.ts`, the
  `vite-plugin-pwa/client` types go in `tsconfig.json`.
- **The proof hook** counts any command containing `npm test` as a gate run.
  Decision: keep the gate plain and last in its command, and use `npx vitest`,
  `npx eslint .` or `npx vue-tsc` for the throwaway checks while working; the
  last plain green `npm test` on the final tree is what matters.
- **CI installs the Contracteer CLI for the frontend job.** Harmless: nothing
  in this task uses it. It is there for T006's global setup (D04).
- **If a criterion cannot be met without a new dependency** (a Vitest
  environment, an ESLint config package, a PostCSS plugin), that is a
  structural conflict: try the smallest change that keeps this brief's set
  first, and report `blocked` with what was tried rather than adding it.
- **`gh pr edit`** can fail with a GraphQL error about classic Projects; the
  REST API (`gh api -X PATCH repos/…/pulls/N`) works.
