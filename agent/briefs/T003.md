# T003 — Backend image

**Backlog line:** Backend image. Precondition (human): the `images` job in
`.github/workflows/ci.yml` (D09). Multi-stage `backend/Dockerfile`: Gradle
build stage taking a `VERSION` build argument, JRE 25 runtime running the boot
jar as a non-root user, configuration by environment only, `HEALTHCHECK` on
`/actuator/health`, OCI labels (D09). `GET /actuator/info` reports the revision
passed as `VERSION` (Spring Boot build info), with a test. The sandbox has no
Docker (D08): the PR's `images` job is the oracle, and the PR body says so.
**Serves:** PRD §5 (operability: deployable behind Traefik, health endpoint);
decisions D01, D08, D09 (packaging and version exposure), D10.

Precondition checked: the `images` job exists in `.github/workflows/ci.yml`
since PR #7. It runs on every pull request after the `backend` and `frontend`
jobs, builds each side that has a `Dockerfile` with
`--build-arg VERSION=sha-<short sha>` and the four OCI labels, and pushes
nothing outside `main`.

## Goal
When this task is done, `backend/Dockerfile` builds a runnable image of the
backend from a clean checkout, and the application reports the revision it was
built with at `GET /actuator/info`. It matters now because T007's compose pulls
that image by tag and Phase 0 ends with Tophe checking, from a phone, that the
deployed revision matches `git rev-parse v0.1.0` — a claim only build info can
support.

Read `agent/PROGRESS.md`'s T001 and T002 entries first. Three things carry
over: the gate is recorded, so keep `./gradlew check` plain and last in its
command; a `.gitignore` line is added only when a real run proves a file is
left untracked; the `classpath.from(...)` on the plain `detekt` task is a gate
requirement, not decoration.

## Test plan
One test class ships: `src/test/kotlin/fr/amory/libris/LibrisApplicationTest.kt`,
the first test of the backend. Write it first; it fails before the
configuration exists, because `/actuator/info` is not exposed by default
(measured, see *Risks and decisions*). Then add the two lines of build
configuration and the one management setting that make it pass.

What it proves: the application exposes its build information over HTTP, which
is the link between the `VERSION` the image is built with and what a human can
read from the deployed app. What it does not prove: that `VERSION` reaches
Gradle, and that the image builds — criteria 3 to 6 and the `images` job cover
those.

Order of work:
1. `LibrisApplicationTest` → red (`/actuator/info` answers 404).
2. `springBoot { buildInfo() }`, the project version from the `version`
   property, `src/main/resources/application.yaml` → green.
3. `./gradlew check` plain → the gate, exit 0.
4. Throwaway edit: drop `info` from the exposure setting → the test fails;
   revert.
5. The command chain of criteria 3 to 6: `test -Pversion=…`, `bootJar
   -Pversion=…`, `unzip -p`, `java -jar` + `curl`, plain `bootJar`.
6. `Dockerfile` and `.dockerignore`, read once against criterion 7.
7. Open the PR, then watch the `images` job and paste its conclusion.

Green means `cd backend && ./gradlew check`, nothing piped or chained after it.
Partial runs (`./gradlew test`, `./gradlew bootJar`) are fine while working and
prove nothing to the sandbox.

Read first: `agent/PROGRESS.md` (the T001 entries), `docs/ARCHITECTURE.md` D08,

Changed under `backend/`:
- `build.gradle.kts` — three additions and nothing else: the project version
  read from the `version` Gradle property with a `dev` default,
  `springBoot { buildInfo() }`, the expected version handed to the test JVM
  (`tasks.test { systemProperty(…) }`), and
  `testImplementation("org.springframework.boot:spring-boot-starter-test")`
  (BOM-managed, no entry in the version catalog).
- `src/main/resources/application.yaml` — new, holding exactly one setting:
  `management.endpoints.web.exposure.include: health,info`.
- `src/test/kotlin/fr/amory/libris/LibrisApplicationTest.kt` — new.
- `Dockerfile` — new. Shape, to adapt but not to embellish:

  ```
  FROM eclipse-temurin:25.0.4_7-jdk-noble AS build
  WORKDIR /workspace
  COPY . .
  ARG VERSION=dev
  RUN ./gradlew --no-daemon bootJar -Pversion=$VERSION

  FROM eclipse-temurin:25.0.4_7-jre-noble
  ARG VERSION=dev
  LABEL org.opencontainers.image.version=$VERSION
  LABEL org.opencontainers.image.source=https://github.com/camory/libris
  RUN apt-get update && apt-get install -y --no-install-recommends curl \
      && rm -rf /var/lib/apt/lists/*
  RUN useradd --system --create-home libris
  COPY --from=build /workspace/build/libs/*.jar /app/app.jar
  USER libris
  EXPOSE 8080
  HEALTHCHECK --interval=30s --timeout=3s --start-period=30s --retries=3 \
      CMD curl -fsS http://localhost:8080/actuator/health || exit 1
  CMD ["java", "-jar", "/app/app.jar"]
  ```

- `.dockerignore` — new: `build/`, `.gradle/`, `.kotlin/`. It is what makes
  `COPY . .` safe when the context is a developer's `backend/` rather than a
  fresh checkout.
- `README.md` — the image section.

Not created: `deploy/` (T007), `frontend/Dockerfile` (T004), any
`application-<profile>.yaml`, any `compose.yaml` for the backend, any script
wrapping `docker build`.

## Risks and decisions
- **Measured on 2026-09-08 in a throwaway copy of `backend/`** (Gradle 9.7.1,
  Spring Boot 4.1.1, JDK 25), so the implementer does not have to rediscover
  it:
  - `-Pversion=sha-abc1234` sets the project version; the boot jar is named
    `libris-backend-sha-abc1234.jar` and it is the *only* jar in
    `build/libs` (the Boot plugin disables the plain jar).
  - `springBoot { buildInfo() }` writes
    `build/resources/main/META-INF/build-info.properties`, so a `@SpringBootTest`
    sees it on the test classpath, and the same file ships in the jar.
  - With the default exposure, `GET /actuator/info` answers **404**; the
    actuator index lists `health` only. With
    `management.endpoints.web.exposure.include: health,info` the endpoint
    answers
    `{"build":{"artifact":"libris-backend","name":"libris-backend","time":…,"version":"sha-abc1234"}}`.
    The build info contributor needs no other property: it is on by default
    once the file exists.
  - `/actuator/health` answers `{"groups":["liveness","readiness"],"status":"UP"}`,
    as T001 recorded.
- **Base images.** `eclipse-temurin:25.0.4_7-jdk-noble` and
  `eclipse-temurin:25.0.4_7-jre-noble`, both published for linux/amd64
  (checked on Docker Hub, 2026-09-08). Decision: pin the full Temurin build
  tag rather than `25-jdk` / `25-jre`, because D10 wants versions pinned and
  upgrades to be their own task; not a digest, because a digest needs an update
  workflow no document describes. The two stages stay on the same Temurin
  build. The build stage must be a JDK 25 image: `jvmToolchain(25)` with no
  toolchain resolver (D08) only works if the JDK is already there.
- **The runtime image has no HTTP client.** Read from the upstream Temurin
  Dockerfile (`adoptium/containers`, 25/jre/ubuntu/noble): `wget` is installed
  to fetch the JDK and then purged with `apt-get purge -y --auto-remove`;
  `curl` is never installed. So the `HEALTHCHECK` cannot assume one. Decision:
  install `curl` in the runtime stage (`--no-install-recommends`, apt lists
  removed) and keep the check to one line. Rejected: the alpine variant, whose
  busybox `wget` would do but changes libc for no other gain; a bash
  `/dev/tcp` port check, which does not call `/actuator/health` as D09
  requires. This cannot be exercised in the sandbox — keep the command trivial
  and expect T007 to be where it first runs.
- **`CMD`, not `ENTRYPOINT`.** The Temurin image sets
  `ENTRYPOINT ["/__cacert_entrypoint.sh"]`, which syncs the system CA
  certificates into the JVM truststore and then `exec`s its arguments.
  Overriding the entrypoint silently drops that; an exec-form `CMD` keeps it
  and still lets signals reach the JVM through the entrypoint's `exec`.
- **OCI labels.** CI already passes all four D09 labels with `--label` on every
  build, and a CLI label wins over a `LABEL` line with the same key, so the
  published images carry CI's values whatever the Dockerfile says. Decision:
  the Dockerfile declares the two a hand-built image can know and CI would set
  identically — `org.opencontainers.image.version` from `VERSION` and
  `org.opencontainers.image.source`, the repository URL — and leaves
  `revision` and `created` to CI, which alone knows them. Note it as a
  follow-up for Tophe if he wants all four declared, since that needs build
  arguments the workflow does not pass.
- **Test naming.** D07 names test classes after the Libris code they exercise
  and forbids a suffix that sorts tests by what they need; no document fixes
  the `Test` suffix itself. Decision: `LibrisApplicationTest`, since what is
  under test is `LibrisApplication` together with its `application.yaml`, and
  `Test` is what JUnit and Gradle default to. Propose the matching sentence for
  D07 in the PR body, as T002 did for `*.spec.ts` — this is the first backend
  test class, so it is the cheapest moment to fix the convention.
- **How the test calls the endpoint.** Measured from the 4.1.1 POM:
  `spring-boot-starter-test` does not bring `spring-boot-resttestclient`, so a
  `RANDOM_PORT` test would need that extra artifact. Decision: `@SpringBootTest`
  with `@AutoConfigureMockMvc` (the default MOCK web environment), which needs
  the starter and nothing else, with Kotest assertions on the parsed body
  (D07). Allowed fallback if the actuator endpoints are not mapped in the mock
  context: add `org.springframework.boot:spring-boot-resttestclient`
  (BOM-managed) and use `RestTestClient` with `webEnvironment = RANDOM_PORT`.
  Record it as a deviation; it is not a blocker.
- **The expected version in the test** comes from the build:
  `tasks.test { systemProperty("libris.version", version.toString()) }`, and
  the test compares `build.version` from the response to that property.
  Hardcoding `dev` would make `./gradlew check -Pversion=sha-…` fail; reading
  the same `build-info.properties` the endpoint reads would assert nothing.
- **`build.time` changes on every build**, so `bootBuildInfo` and everything
  after it are never up to date and `check` always recompiles. Accepted: the
  build takes seconds and the deployed build time is worth having. Do not
  exclude `time` to win that back.
- **detekt now sees `src/test/kotlin`.** The plain `detekt` task's `classpath`
  is the main source set only (T001), and `agent/PROGRESS.md` is explicit that
  removing it makes a `!!` pass the gate. If detekt fails or warns on
  unresolved types in the new test sources, add the test compile classpath and
  output to the same `classpath.from(...)`; never drop the main one.
- **`allWarningsAsErrors` covers test compilation too**: a deprecated Spring
  test API fails the build, not just warns. Use the current API rather than
  suppressing.
- **`application.yaml` is new.** T001 deliberately shipped none. It holds the
  one setting this task's test exercises. Nothing else goes in it — no
  application name, no logging configuration, no profile — until a task needs
  it (`CLAUDE.md`: no configuration nothing exercises).
- **Layer caching is not worth building for.** The `images` job configures no
  buildx cache, so every CI build downloads the Gradle distribution and the
  dependencies once. Decision: a single `COPY . .` guarded by `.dockerignore`
  rather than a split copy plus a dependency warm-up `RUN`, which would only
  pay off with a cache that does not exist.
- **The `images` job needs both test jobs green** (`needs: [backend, frontend]`),
  so a red gate means no image proof at all. Get `check` green before opening
  the PR, and expect the frontend job to run untouched. The job skips the
  frontend image with `frontend/Dockerfile not present yet`; that is normal
  until T004.
- **`gh pr edit`** can fail with a GraphQL error about classic Projects; the
  REST API (`gh api -X PATCH repos/…/pulls/N`) works.
