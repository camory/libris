# T020 — The ISBN endpoint and its four answers

**Backlog line:** Backend: the ISBN endpoint and its four answers.
`application`: the lookup use case over the source port of T013, asking Open
Library and answering what it knows, that no source knows the ISBN, or that no
source replied. `infra.web`: `GET /api/v1/isbn/{isbn}`, its response and its
problems (D02, D11) — not-found when no source knows the ISBN,
sources-unavailable when every source fails or answers past
`LIBRIS_SOURCE_TIMEOUT`, validation `{field: isbn, code: not-an-isbn}` on a
wrong check digit. Bumps the backend pin to `v0.3.0` in `ApiContractTest`, the
only contract edit; Contracteer green on the four responses, the 200 over the
stubbed use case (D04, D07). Realises S4, S7 and the API's own check in S3;
un-skips `S4 Unknown ISBN` and `S7 Every source down`.

**Serves:** spec `fast-entry` S4, S7 and the API's own check in S3 (the reader
half of S3 is the frontend's, T016 and T017); the *Contract* section of that
spec. PRD §4.7 (a source that fails or knows nothing degrades gracefully) and
§3 (Edition, Series, Volume number, Collection, Author, Role). Decisions D02
(the layers), D04 (the pinned contract and Contracteer), D06 (authentication
is upstream), D07 (the gate, the slices, the scenario tests), D10 (Kotlin and
commit conventions), D11 (problem details, JSON shapes, ISBN-13 normalised).

**First of its kind:** the first problem detail of the code base — the first
`/problems/` type slug served, and the choice of where an error answer is
built (in the controller, from the use case's result, with no exception and no
`@RestControllerAdvice`); with it, the first use case answering a sealed
result and the first backend bump of the contract pin.

## Goal
When this task is done Libris answers `GET /api/v1/isbn/{isbn}` with the four
answers the contract declares — what the sources know, not an ISBN, no source
knows it, no source replied — over the Open Library source T013 built, and the
backend is verified against release `v0.3.0` of `camory/libris-api`. It
matters now because it is the first end of the feature a caller can reach: it
turns the source port into an HTTP operation, it settles how a problem detail
is produced, and it is what T016 and T017 develop the screen against through
`contracteer mock`.

## Rules in play
- **D02** — the use case lives in `application` and depends on `domain` only
  (`@Service` is the one framework type it may carry); the controller, its
  response types and its problem details live in `infra.web`; neither touches
  `infra.lookup`. The five ArchUnit rules stay as they are and stay green.
- **D04** — the only contract edit is the `openApiDoc` pin of `ApiContractTest`,
  moved from `v0.1.0` to `v0.3.0`; the document itself is never edited, never
  consumed from a branch, and a gap in Contracteer blocks the task with a
  question rather than being worked around. Read
  <https://contracteer.dev/latest> before touching the verifier.
- **D06** — the endpoint is authenticated like every other: the header filter
  already sets the reader, the contract declares no security scheme, nothing
  here reads a `Remote-*` header, and the 401 is not this task's business.
- **D07** — `cd backend && ./gradlew check` is the gate and must be run plainly
  (not piped, not chained, one gate per command, or the sandbox records
  nothing and refuses the push); `application` is tested with plain JUnit over
  a fake of its port, `infra.web` in the web slice over a stubbed use case, and
  the Contracteer test runs over that same slice; the two scenario methods the
  backlog line names are un-skipped and nothing else in
  `src/test/kotlin/fr/amory/libris/scenario/` changes; shared test doubles go
  to the `fixture` package; test bodies are laid out Given / When / Then unless
  a single statement; a test written to learn the framework is deleted before
  the pull request.
- **D08** — nothing is added to the environment: no Docker, no Testcontainers,
  no new service, no new variable. The two source variables already exist and
  keep their defaults.
- **D10** — Kotlin official style, immutable by default, a sealed type for the
  use case's result, constructor injection, no `!!` and no `lateinit`; a member
  is imported, not qualified, when its bare name is unambiguous; commit
  `feat(backend): …` on branch `task/T020-isbn-endpoint`; no `D##` and no
  rationale in code, tests or configuration.
- **D11** — paths under `/api/v1/`, camelCase JSON, the ISBN-13 as its thirteen
  digits; every absent optional value is serialised as `null`, never omitted;
  every error carries an RFC 9457 body of `application/problem+json` with
  `type`, `title` and `status`, no `detail` and no nullable field, the
  validation problem adding `errors: [{field, code}]`; the wording is the
  frontend's, so no message text crosses the API.
- **docs/DESIGN.md** — none: U01…U08 are screen rules and this task has no
  frontend side.

## Acceptance criteria
- [ ] `GET /api/v1/isbn/{isbn}` answers `200 application/json` for an ISBN the
      source knows, with exactly the thirteen fields of the contract's `Isbn`
      schema — `isbn13`, `title`, `subtitle`, `authors` (`name`, `role`),
      `series` (`name`, `volumeNumber`), `collection`, `publisher`,
      `publicationYear`, `language`, `pageCount`, `summary`, `coverUrl`,
      `sources` — every field the sources leave empty present and `null`, and
      no field the schema does not declare. Proof: `IsbnControllerTest`,
      asserting the whole body of an edition that fills every field and of one
      that fills none but the title.
- [ ] A path that is not an ISBN-13 — a wrong check digit (`9782723488526`),
      the wrong length, letters — answers `400 application/problem+json` with
      `{"type": "/problems/validation", "title": "Bad Request", "status": 400,
      "errors": [{"field": "isbn", "code": "not-an-isbn"}]}`, and the use case
      is never called. Proof: `IsbnControllerTest`, two cases, the last
      asserting no interaction with the stubbed use case.
- [ ] When no source knows the ISBN the answer is `404
      application/problem+json` with `type` `/problems/not-found` and `title`
      `Not Found`. Proof: `IsbnControllerTest` and the scenario
      `S4 Unknown ISBN`.
- [ ] When no source replies — a failure or an answer past
      `LIBRIS_SOURCE_TIMEOUT` — the answer is `503 application/problem+json`
      with `type` `/problems/sources-unavailable` and `title`
      `Service Unavailable`. Proof: `IsbnControllerTest` and the scenario
      `S7 Every source down`.
- [ ] `fr.amory.libris.application.IsbnLookup` answers, for one `Isbn13`, one
      of three results: what the source knows with the list of the sources that
      answered, that no source knows the ISBN, that no source replied — one per
      answer of the port, with no HTTP type and no framework type but
      `@Service`. Proof: `IsbnLookupTest`, three cases over the fixture fake,
      no Spring context; `ArchitectureTest` stays green unchanged.
- [ ] `S4 Unknown ISBN` and `S7 Every source down` run and pass;
      `S1 Typed ISBN, found`, `S5 Merged answer` and the two `S6` methods are
      still skipped. Proof: the output of `./gradlew check`, and
      `git diff main -- backend/src/test/kotlin/fr/amory/libris/scenario`
      showing two removed `@Disabled` lines and nothing else.
- [ ] `ApiContractTest` pins
      `https://raw.githubusercontent.com/camory/libris-api/v0.3.0/openapi.yaml`
      and is green on the four verification cases of the ISBN operation
      (`ONE_PIECE_1`, `400_NOT_AN_ISBN`, `404_UNKNOWN_ISBN`,
      `503_SOURCES_DOWN`) and on the existing `/api/v1/me` case. Proof: the
      test report names the cases; `git diff main -- backend/src/test/kotlin/fr/amory/libris/ApiContractTest.kt`
      shows the pin line and the added stubbing of the use case, nothing else.

- [ ] No new dependency and no build change: `git diff main --stat` touches

## Test plan
Green suite: `cd backend && ./gradlew check`, run plainly — nothing piped or
chained after it. While iterating, `./gradlew test --tests
'fr.amory.libris.application.IsbnLookupTest'` costs seconds (no Spring
context); `--tests 'fr.amory.libris.infra.web.IsbnControllerTest'` and
`--tests 'fr.amory.libris.ApiContractTest'` boot the web slice; `--tests
'fr.amory.libris.scenario.FastEntryScenarios'` boots the whole application
over WireMock.

Order, one test at a time, red before green:

1. `src/test/kotlin/fr/amory/libris/application/IsbnLookupTest.kt` — plain
   JUnit with Kotest assertions, as `ReaderVisitTest` is written, over the new
   fixture fake of `IsbnSource`. Three cases, each proving one mapping:
   a source that knows answers what it knows and names itself in the list of
   sources; a source that knows nothing answers that no source knows the ISBN;
   a source that failed answers that no source replied. The edition used is a
   local `SourceEdition` of the test, not a fixture.
2. `src/test/kotlin/fr/amory/libris/infra/web/IsbnControllerTest.kt` — the web
   slice (`@WebSliceTest`), `@MockitoBean(types = [ReaderVisit::class,
   IsbnLookup::class])` as `MeControllerTest` does for `ReaderVisit`, the
   reader headers on every request, both media types in `Accept`. Cases, in
   this order:
   - an edition that fills every field is the 200 body, asserted whole
     (`expectBody().json(…, JsonCompareMode.STRICT)`), which proves the field
     names, the enum spellings `WRITER` and `OPEN_LIBRARY`, and the ISBN-13 as
     thirteen digits;
   - an edition that fills nothing but the title is a 200 body where every
     other field is present and `null`, which proves D11's rule on absent
     values and the strictness of the contract's `additionalProperties: false`;
   - `9782723488526` answers 400 with the validation problem, content type
     `application/problem+json`, and `errors` exactly
     `[{field: isbn, code: not-an-isbn}]`;
   - `pas-un-isbn` answers the same 400 and the stubbed use case records no
     interaction at all (`verifyNoInteractions`);
   - no source knows answers 404 with `/problems/not-found` and the title
     `Not Found`;
   - no source replied answers 503 with `/problems/sources-unavailable` and the
     title `Service Unavailable`.
   Assert `title` explicitly in the two last cases: it is what proves the
   contract's `required: [type, title, status]` is met whether Spring derives
   the title from the status or not.
3. `src/test/kotlin/fr/amory/libris/ApiContractTest.kt` — move the pin to
   `v0.3.0` and add to the existing setup method the stubbing of `IsbnLookup`
   for the three ISBNs the contract's examples name: `9782723488525` knows the
   `ONE_PIECE_1` edition, `9782000000006` is known by no source,
   `9791000000008` is replied to by none. `9782723488526` needs no stub: the
   controller refuses it before the use case. The setup runs before every case,
   so all three stubs are declared unconditionally, as the `ReaderVisit`
   stubbing already is. This step adds no production code; it proves the shape
   of what step 2 built against the document.
4. `src/test/kotlin/fr/amory/libris/scenario/FastEntryScenarios.kt` — remove
   the `@Disabled("S4")` and `@Disabled("S7")` lines, and nothing else: not the
   bodies, not `ScenarioTest.kt`, not the recorded answers, not the two
   remaining `@Disabled` groups. Both must pass over the real Open Library
   client against the WireMock stubs; run the class twice on its own before
   trusting it (see the timeout risk below).

`ArchitectureTest` needs no new rule and no edit: its existing rules already
cover `application` and `infra.web`. Delete any scratch test written to learn
how Spring renders a `ProblemDetail` once the controller test asserts it.

## Out of scope
- **Several sources and the merge rule** — T014. One source is injected, one is
  asked; nothing ranks, nothing merges, no field of one source fills a gap of
  another, and the answer's `sources` is the list of the one source that
  answered.
- **The BnF** — T015. No SRU client and no use of the recorded BnF answers,
  even though `S4` and `S7` stub the BnF server: those stubs stay unused, which
  is expected and must not be "fixed".
- **Un-skipping S1, S5 or S6.** They need the merge and the BnF; leaving them
  skipped is a criterion.
- **The frontend** — T016 and T017 own the ISBN rule of S3, the client, the
  screen, the wording of every message, and the frontend pin bump.
- **Storing anything.** Nothing is persisted: no table, no migration, no
  repository, no transaction. This feature shows what the sources know.
- **A global error handler.** No `@RestControllerAdvice` mapping Spring's own
  exceptions, no `spring.mvc.problemdetails.enabled`, no problem body for
  anything but the three answers of this operation; a 5xx without a body is
  exactly what D11 wants for Libris being unavailable.
- **Bean validation.** No `spring-boot-starter-validation`, no `@Valid`, no
  `@Pattern`: `Isbn13.of` is the check, and the 400 is its refusal.
- **The `978`/`979` prefix.** The contract's path pattern states it and the
  mock enforces it on the client; the backend accepts any thirteen digits whose
  check digit is right, as `Isbn13` already decided in T013.
- **Caching, retries, rate limiting, an `Accept-Language`** — no document asks
  for any of them.

## Risks and decisions
- **One source or a list.** Decided: `IsbnLookup` takes one `IsbnSource` in its
  constructor. The backlog line of T020 says "asking Open Library" and the line
  of T014 says "the use case asks every source", so the plural, the bound per
  source and the merge are T014's, which is the next task. Spring has exactly
  one `IsbnSource` bean until T015 adds the BnF, and `LibrisApplicationTest`
  already asserts that.
- **The result of the use case and its names.** Decided: a sealed
  `LookupResult` in `IsbnLookup.kt` with `Found(edition, sources)`,
  `UnknownIsbn` and `SourcesUnavailable`. The names deliberately differ from
  the port's `Known`, `NothingKnown` and `Failed`: both types are imported in
  the same file and D10 forbids qualifying what can be imported, so a clash
  would be paid in every line. `sources` is a `List<Source>` — the contract's
  field is an array and T014 must not have to reshape the result. `Found`
  carries the port's `SourceEdition` as it stands; nothing new describes an
  edition in this task.
- **How a problem detail is produced.** Decided, and flagged as first of its
  kind: the controller answers a `ResponseEntity` whose body is either the
  response type or a `ProblemDetail` built by a private function of the same
  file from `ProblemDetail.forStatus(…)` plus `type` (and `errors` for the
  validation one). No exception is thrown, no advice is declared and no
  property is enabled: the three failing answers are ordinary results of the
  use case, not exceptional events, and Spring writes `application/problem+json`
  for a `ProblemDetail` body on its own. Verify that: assert the content type
  and the `title` in `IsbnControllerTest`, and if Spring does not derive the
  title from the status, set it explicitly — the contract requires it.
- **The `instance` field.** Spring fills a `ProblemDetail`'s `instance` with
  the request path when it writes it. The contract's `Problem` and
  `ValidationProblem` do not declare `additionalProperties: false`, and
  Contracteer tolerates what the document does not declare, so leave it alone:
  removing it would be work against the framework for nothing. `detail` stays
  absent, as D11 demands, and Spring omits it.
- **The enums of the response.** Decided: the response types carry the domain
  enums `Source` and `AuthorRole` directly; their constants are spelled exactly
  as the contract's `sources` and `role` enumerations, so Jackson writes the
  right words and a divergence would break the contract test.
  `MeController` declares its own `Role` because the domain has none — roles
  are Spring authorities there (D06) — which is not the case here.
- **What Contracteer will actually run.** Measured against the document and
  <https://contracteer.dev/4.0.0/concepts/testing-your-server/>: the four
  example keys of the operation give four verification cases, and no automatic
  type-mismatch case is generated because the `isbn` path parameter is a
  `string` without a `format` (a string cannot be "not a string"). The verifier
  checks status, headers and the shape of the body, never its values — so the
  stubs of `ApiContractTest` are free, but stub the example's own values
  anyway: a reader of the test then sees the document's case. `/api/v1/me` is
  unchanged in `v0.3.0` and carries no example, so it is still verified from
  its schema alone.
- **Stubbing a method that takes a value class.** `Isbn13` is a
  `@JvmInline value class`, so `lookUp` compiles to a mangled JVM method taking
  a `String`; stub it from Kotlin call syntax, `given(lookup.lookUp(isbn13Of(
  "9782723488525"))).willReturn(…)`, with a private helper wrapping
  `checkNotNull(Isbn13.of(text))` — never `!!` (D10). If Mockito cannot stub it
  at all, say so in the pull request and use a hand-written fake of the use
  case in the slice instead; do not change the port's signature.
- **The scenarios run with a one-second timeout on a cold JVM.** T013 measured
  that the first HTTP request of a JVM costs more than a second, and
  `ScenarioTest` registers `LIBRIS_SOURCE_TIMEOUT=1s`. `S4` must answer 404
  rather than 503, so a first call slow enough to time out would make it fail
  or, worse, flake. Run `./gradlew test --tests
  'fr.amory.libris.scenario.FastEntryScenarios'` on its own at least twice, and
  the full gate after it. If it times out: the harness is Tophe's and this task
  may not edit it, so the client must build whatever it can build once at
  construction time rather than per call — and if that is not enough, stop and
  report `blocked` with the measurement, naming `ScenarioTest.kt` as the file
  that would have to change. Do not widen the timeout, do not retry, do not
  touch the scenario file beyond the two `@Disabled` lines.
- **The unknown-ISBN example is a real record.** `9782000000006`, the contract's
  `404_UNKNOWN_ISBN`, is known to the real Open Library (noted in
  `agent/PROPOSED.md` on 2026-09-12). It changes nothing here: the contract test
  stubs the use case and the scenario uses `9782000000013`. Do not "fix" the
  example — the contract is released and is Tophe's.
- **The pin bump is the whole contract edit.** If `v0.3.0` turns out to
  describe something this task cannot satisfy — a field the sources cannot
  give, a status Spring will not produce — that is a contract conversation:
  report `blocked` with the question rather than bending the code or the
  document (D04).
