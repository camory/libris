## Goal
Each list of names keeps the answer to the latest ask alone, so a slow
answer to an earlier lookup no longer replaces the names the form suggests
and reads its *Existante*/*Nouvelle* word from. On a dropping network the
reader is then offered the house's names as they stood at the lookup on
screen.

## Risks and decisions
**The rule lives in each composable.** They hold `names` and are called on
each ask, so each knows which call is the latest, as `useSearchCatalogue`
does. Rejected: a lookup counter in `IsbnView` (the bug is also
`EditionPageView`'s on two quick pencils, and the view would own a rule of
`application/`); building a fresh composable per lookup in a `shallowRef`
(`names` would read `null` until the new answer, dropping the word and the
suggestions the reader had).

**An answer to an earlier ask is dropped whenever it lands.** The line says
only the answer to the latest ask counts, so an earlier answer landing
before the latest one is dropped too, and `names` keeps what it held until
the latest lands, as `useSearchCatalogue` keeps its books. Rejected:
writing an earlier answer while the latest is pending (an order the line
does not ask, and two counters where one serves).

**The fakes in turn are spec-local.** No other spec needs names answered
late; `FakeSeriesApi` and `FakeAuthorsApi` stay as every scenario file
builds them. Rejected: widening the fixtures' constructors to lists or
promises (a fixture change no other caller uses).
