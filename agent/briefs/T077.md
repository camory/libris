**Serves:** spec `bookshelves` S6 and its *Contract* section (`POST
/api/v1/bookshelves/{id}/members`, keys `400_UNKNOWN_READER`,
`404_NOT_MY_BOOKSHELF`, `409_ALREADY_A_MEMBER`); PRD §3 (*Bookshelf*,
*Membership*, owner, viewer); decisions D02, D04, D07, D10, D11, D12
**First of its kind:** the first change of an aggregate that the aggregate
itself refuses: `Bookshelf.withMember` answers `null` for a reader already
a member, the form D12 gives a value's `of`, applied to an aggregate's
change.

## Goal
`AddMemberToBookshelf` refuses what S6 refuses: only an owner adds, a reader
Libris does not know is never added, and a member is never added twice, the
bookshelf unchanged each time. This closes the gap T073 left open, where any
reader who knew a bookshelf's id could add to it.

## Risks and decisions
**Fit.** One run: one aggregate method changes its answer, one use case
gains two outcomes, four un-skips, three test files; no web, SQL or
contract change. Rejected: a split (the four cases share one use case and
one test class).

**A viewer and a stranger, one outcome through `isOwnedBy`.** The contract
answers both `404`, and `AddBookToBookshelf` already refuses a non-owner
through the aggregate's `isOwnedBy`. `AddMemberResult` has no variant for
a viewer, and needs none. Rejected: a `NotAnOwner` variant (a second branch
at the edge with the same answer); `withMember(asker, membership)` (two
refusals folded into one `null`, and the asker is no part of the new
membership).

**A member already there, refused by `withMember`.** D12 puts a rule in the
aggregate that holds the data, and T073's brief named `withMember` as the
place. It answers `null`, as D12's `of` does for what the domain refuses,
and as `Cover.normalised()` already does for a change; the caller decides
what the `null` means. This is the *First of its kind*: Tophe settles the
form at review. Rejected: the use case asking `hasMember` before the add
(the aggregate's rule decided outside it); an `init` that `require`s one
membership per reader (a constructor exception no use case may catch, D12,
so the use case would still ask first; the primary key `(bookshelf_id,
reader_id)` already keeps the rows read back distinct); catching the
primary key's `DuplicateKeyException` (an exception as an outcome, D11).

**Refusals write nothing.** Every refusal is decided from the reads, before
the transaction, so `TransactionsObserving` records none, as T073's two
refusals already prove. No optimistic locking (D11): two owners adding the
same reader at once may still meet the primary key, a `500`, accepted for a
household.

**S6's ordered comparisons.** The viewer's and the duplicate's cases
compare the members with `shouldBe listOf(marc.member(OWNER),
lea.member(VIEWER))`, an order the backend has not promised since T085,
while S1 and S4 compare in any order since #234. They pass all the same:
`FindBookshelf` answers in the order of `JdbcReaderRepository.findByIds`,
which has no `ORDER BY`, so the reader rows' order, and in both cases
Marc's row is written before Léa's and no reader row is updated
afterwards. D07 forbids editing them; should one go red on the order alone,
the implementer stops and reports `blocked`. The PR body and an item of
`agent/PROPOSED.md` propose to Tophe `shouldContainExactlyInAnyOrder`, as
T087 did for the authors. Rejected: an `ORDER BY` in `findByIds` (an order
D11 says the backend does not promise, added to satisfy a test).

**detekt.** `ReturnCount` allows two returns: the outcomes stay in one
`when`, as in `AddBookToBookshelf`.
