# T016 — The ISBN rule and the lookup client

**Backlog line:** Frontend: the ISBN rule and the lookup client.
`domain`: the rule of S3 — separators dropped, the old ten converted, the
check digit verified — answering the ISBN-13 or a refusal, with its unit
tests (D05). `application`: the `IsbnApi` port and its injection key;
`infra/api`: the hand-written response and problem types and the fetch
client, sending `Accept: application/json, application/problem+json`, which
is what makes the mock serve a problem (D05, D06). One spec per response the
contract declares — 200, 400, 404, 503 — and none it does not, against
`contracteer mock` (D07). Bumps the frontend pin to `v0.3.0` in
`vitest.global-setup.ts`, the only contract edit (D04). `FetchMeApi` sends the
same `Accept` header from then on (D06). Realises the rule of S3 and the
client half of S1, S4, S7; un-skips nothing.

**Serves:** spec `fast-entry` — the rule of S3, and the client half of S1, S4
and S7, all of which go green on the screen of T017 and T018; PRD §4.7 (the
reader types an ISBN and reads what the sources know), §3 (Edition, Series,
Volume number, Collection, Author, Role and their *Avoid* lists); decisions
D04 (the pin bump is the only contract edit a run makes; no code generation),
D05 (the frontend layers, the client's base URL as a constructor argument,
hand-written types), D06 (the `Accept` header of every request), D07
(`npm test` is the gate, one spec beside the module, one case per declared
response and none it does not, Given / When / Then), D10 (strict TypeScript,
Conventional Commits, identifiers in English), D11 (`type` is the key of a
problem, a validation `code` is documentation until the contract enumerates
it, absent optional values arrive as `null`).

**First of its kind:** the first frontend *domain rule* — a pure function with
a spec of its own, where `domain/` held nothing but types until now — and the
first *port that answers an outcome rather than a value*, `IsbnAnswer`, a
discriminated union the view will switch on; also the first hand-written
problem type in `infra/api`, and the second fetch client, which is what turns
`FetchMeApi`'s shape into a convention.

## Goal
When this task is done the frontend owns both halves of the lookup that no
screen needs yet: the pure rule that turns what a reader types — thirteen
digits, the old ten, hyphens, spaces — into an ISBN-13 or a refusal, and the
client that asks `GET /api/v1/isbn/{isbn}` and answers what the sources know
or which problem came back, proven against `contracteer mock` on all four
responses the contract declares. It matters now because the screen of T017 is
then a view over two pieces that are already green, and because the pin bump
it carries is what makes the `v0.3.0` operation exist for every frontend task
of the phase.

- **D10** — TypeScript strict, ESLint and Prettier, identifiers and code in

- **D11** — the API sends keys and the frontend owns the wording: the client

## Test plan
Green suite: `cd frontend && npm test`, run plainly — nothing piped or
chained after it, or the proof hook refuses the call. While iterating,
`npx vitest run src/domain` needs no mock and is instant; `npx vitest run
src/infra` starts the mock through the global setup (about four seconds) and
needs `contracteer` on the PATH. The mock is a strict reference
implementation: it validates the request, then matches it against the
scenarios the document's examples define, and a request that matches none
gets a generated body. That is why the four cases use the four ISBNs of the
contract's path examples.

1. **The pin, first and alone.** Move the URL in `vitest.global-setup.ts` to
   `v0.3.0` and run the gate: it must stay green, which proves the new
   document loads and that `/api/v1/me` still answers as `FetchMeApi.spec.ts`
   and the scenario case expect. Commit it on its own
   (`build(frontend): pin the API contract v0.3.0`). If the mock refuses the
   document or answers `418` on `/api/v1/me`, stop and report `blocked`
   (D04: a gap in Contracteer is never worked around).
2. **Red → green, the rule, one case per cycle** in
   `src/domain/Isbn13.spec.ts`, plain Vitest, no double, each body Given /
   When / Then or a single statement:
   - thirteen digits are kept: `9782723488525` answers itself;
   - hyphens and spaces are dropped: `978-2-7234-8852-5` and
     `978 2 7234 8852 5` answer `9782723488525`;
   - a wrong check digit is refused: `9782723488526` answers `null`;
   - a wrong length is refused: `978272348852` answers `null`;
   - the old ten is converted: `2723488527` and `2-7234-8852-7` answer
     `9782723488525`;
   - a ten whose check digit is `X` is converted: `080442957X` answers
     `9780804429573` (and `080442957x` the same);
   - a ten with a wrong check digit is refused: `2723488521` answers `null`;
   - a thirteen-digit EAN with another prefix is refused: `4006381333931`,
     whose check digit is right, answers `null`;
   - a text that is not digits is refused: `978-2-7234-8852-X` and the empty
     string answer `null`.
   Every value above was computed and checked while writing this brief; a red
   on one of them is a bug in the rule, not in the expectation.
3. **The port compiles, and nothing tests it.** `src/application/IsbnApi.ts`
   is an interface, a union and a key: no spec of its own, exactly as
   `MeApi.ts` has none. It arrives in the same cycle as the client's first
   case, which is what motivates it.
4. **Red → green, the client, one response per cycle** in
   `src/infra/api/FetchIsbnApi.spec.ts`, `new FetchIsbnApi(inject("mockBaseUrl"))`:
   - *the found answer*: ask `9782723488525`, then assert
     `answer.outcome === "found"` and, on the edition, that `isbn13`,
     `title` are strings, that `subtitle`, `collection`, `publisher`,
     `language`, `summary`, `coverUrl` are a string or `null`, that
     `publicationYear` and `pageCount` are a number or `null`, that every
     author carries a string `name` and a `role` among the four, that
     `series` is `null` or carries a string `name` and a number-or-`null`
     `volumeNumber`, and that `sources` is a non-empty array whose every item
     is `BNF` or `OPEN_LIBRARY`. Shape and types, never a value: the mock
     generates the values it is not given;
   - *no source knows it*: ask `9782000000006`, assert the answer is a
     problem whose `type` is `/problems/not-found`;
   - *no source answered*: ask `9791000000008`, assert the answer is a
     problem whose `type` is `/problems/sources-unavailable`;
   - *the API refuses the ISBN*: ask `9782723488526`, assert the answer is a
     problem whose `type` is `/problems/validation`, and assert nothing about
     `errors` (D11).
   These three `type` values are the contract's own keys, returned by the
   scenario the example defines, not data: they are the one thing that tells
   the three cases apart, and the wording they map to is T017's. If the mock
   answers a generated `type` instead of the example's, keep the case,
   assert `expect.any(String)`, and add the finding to `agent/GOTCHAS.md`.
5. **The `Accept` header of `FetchMeApi`.** One line, no new case: the `/me`
   operation declares one content type and no problem, so the mock cannot
   prove the header there, and a spec that stubbed `fetch` to read it would
   be a test of wiring (D07). It is proven by reading, and by the three
   problem cases above, which the mock serves only because the header lists
   `application/problem+json`.
6. **Tidy on green**, then the full gate, then the pull request.

**Not to be written:** a spec for `IsbnApi.ts` or for the injection key; a
fake of the port (T017's line puts it in `src/fixture`); a case for a 401, a
500, a network failure or any status the contract does not declare; a test
that stubs `fetch` (nothing in this task needs one — `vi.unstubAllGlobals()`
exists in `FetchMeApi.spec.ts` for the 401 case and stays there); a component
or a view; a Playwright test.

## Risks and decisions
- **A refusal is `null`, decided here.** S3 has one refusal and one message,
  *ISBN invalide*, whatever went wrong, so a union of reasons would be a
  shape no caller reads. `string | null` is what TypeScript strict already
  makes safe to unwrap, and it mirrors the backend's `Isbn13.of`, which
  answers the value or `null` for the same reason (T013). If a screen ever
  needs to tell a wrong length from a wrong check digit, the rule gains a
  result type then.
- **The answer of the port is a discriminated union on `outcome`, decided
  here.** The view of T017 switches on the problem's `type` (D11), so the
  client must carry both the edition and the key through one return value; an
  exception for an expected outcome would contradict D11's "an outcome is a
  result, not an exception". The discriminant is named `outcome` and not
  `kind` because PRD §3 reserves *kind* for what an edition is (`BOOK`, `BD`,
  `MANGA`) and lists *type* under its *Avoid* words; `type` inside the
  problem arm is the contract's own field name. This is the first result
  union of the frontend: the reviewer repeats the *First of its kind* line
  and Tophe settles the convention on the pull request.
- **`SourceEdition` carries `sources`, where the backend's does not.** The
  backend's use case tracks which sources answered and its response DTO adds
  them; the frontend receives the merged answer, `Isbn`, in one piece, and
  the card of T018 shows its chips from the same object. One type with
  thirteen fields beats a wrapper the card has to unpack. The `Source` prefix
  on `SourceEdition`, `SourceAuthor` and `SourceSeries` is kept from the
  backend (T013): `Edition`, `Author` and `Series` are the aggregates of
  PRD §3, which this feature does not store and must not squat.
- **The types live in `domain/`, not in `infra/api`, and flat.** `ui/components`
  may import `domain` and nothing else (D05), so the card of T018 can only
  take `SourceEdition` as props if it sits there; the hand-written *wire*
  types stay private to the client, as `CurrentReaderResponse` already does.
  No `src/domain/lookup/` sub-folder: the tree has none, D05 describes
  `domain/` flat, and the `boundaries/elements` patterns in
  `eslint.config.ts` are written for flat folders — a sub-folder would be a
  layout convention this task has no right to invent.
- **An ISBN-13 must start with `978` or `979`.** The contract's path
  parameter is `^97[89][0-9]{10}$`, so any other prefix is a request the API
  refuses by shape; S2 says the same of the barcode. `4006381333931` is a
  valid EAN-13 and is not an ISBN: the rule answers `null` and no request
  leaves.
- **The ten's own check digit is verified before conversion.** Converting
  first and checking after would accept every wrong ten, since the conversion
  recomputes the check digit. The ISBN-10 rule is the mod-11 weighted sum
  with `X` for ten, accepted in either case.
- **The client branches on `200`, not on a list of statuses.** The contract
  declares four responses; the three problems share one branch, which reads
  `type` from the body. A 5xx without a problem body — which D11 says means
  Libris itself is unavailable, not the sources — makes `response.json()`
  reject, and the promise with it. That is undeclared, untested and
  unbranched on purpose: D07 allows a case for every response the contract
  declares and none it does not. Say it in the PR body.
- **The `Accept` header cannot be proven on `/me`.** The operation declares
  one content type and no problem response, so the mock answers the same
  either way. The header is verified by reading it, and its effect is
  verified by the three problem cases of `FetchIsbnApi.spec.ts`. Do not add a
  spec that stubs `fetch` to read a header.
- **The pin bump changes what every frontend spec runs against.** `v0.3.0`
  still declares `/api/v1/me` exactly as `v0.1.0` did, so
  `FetchMeApi.spec.ts` and the scenario case must stay green untouched; if
  either goes red, the cause is the document, not this task's code, and the
  report is `blocked` with the question (D04).
- **The sandbox runs the gate, this box does not.** `npm test` needs
  `contracteer` on the PATH and Node 24, which the sandbox has (D08); on
  Tophe's machine the frontend gate runs inside the image
  (`agent/GOTCHAS.md`). No measurement of the suite's duration or coverage is
  quoted here: the run reports what it measured.
