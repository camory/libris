# T029 — The check while the app stays open

**Backlog line:** Frontend: the check while the app stays open. The adapter
asks the server for a newer worker an hour after its last check and whenever
the app comes back to the foreground, a foreground check starting the hour
again; it asks nothing while the app is hidden and stops asking when it goes
away. A unit test with fake timers and a stubbed registration: the hour, the
return to the foreground, the hour restarted by it, and no check in between
(D07). Neither the banner, the port, the words nor the contract change.
Realises S3; un-skips nothing, S3's proof being that unit test.

**Serves:** spec `update` — S3 *The app checks while it stays open*, whose
proof is "unit test of the check schedule with fake timers and a stubbed
registration"; PRD §4.8; decisions D05, D07, D08, D10, and D04 by its silence
(the phase header: "Contract: none … no pin moves"). No rule of
`docs/DESIGN.md` fires: nothing the reader sees changes shape, and the banner
of U09 appears through the announcement path T028 already built.

**First of its kind:** the first **clock of the app's own** — nothing in the
tree yet counts a duration and acts when it runs out (`CameraBarcodeScanner`
pauses 100 ms inside a loop the reader started; this one keeps its own hour
with nobody watching). With it come two conventions no document states: the
first test that controls time (`vi.useFakeTimers`, used nowhere on either
side of the tree today) and the first adapter that listens to the page's
lifecycle rather than to its own device (`visibilitychange` on `document`).
The reviewer repeats this line in its verdict and Tophe reviews the pull
request interactively before merging.

## Goal
When this task is done, an app left open on the Pixel learns about a version
deployed since it was launched: it asks the server for a newer worker an hour
after its last question, and again the moment the reader brings the app back
to the front, so the banner of T028 appears without the app being relaunched.
It matters now because the banner only ever shows what the browser volunteers,
and a browser volunteers a new worker on navigation alone: an installed PWA
that is never closed would never see one.

- [ ] It asks when the app comes back to the foreground, with no time passing.

## Test plan
Green suite: `cd frontend && npm test`, run plainly — nothing piped or chained
after it, or the proof hook counts the call as a gate run. While iterating,
`npx vitest run src/infra/pwa/ServiceWorkerAppUpdate.spec.ts` from
`frontend/`, never from the repository root (`agent/GOTCHAS.md`).

Read first: `src/infra/pwa/ServiceWorkerAppUpdate.ts` and its spec whole — the
stub helpers `aBrowser`, `aWorker` and `settled` are what the new cases build
on; `src/scenario/UpdateScenarios.spec.ts` (the harness that must keep
passing, and whose fake registration has **no** `update` method);
`src/infra/camera/CameraBarcodeScanner.ts` for `betweenLooks`, the shape of a
duration in this tree.

Two facts probed on this tree on 2026-09-18, so no cycle is spent on them:
`Object.defineProperty(document, "visibilityState", { configurable: true, get:
() => "hidden" })` shadows jsdom's accessor and a handler reading it during a
dispatched `visibilitychange` sees the stubbed value;
`await vi.advanceTimersByTimeAsync(0)` flushes the microtask queue as well as
the zero-delay timers, and `await vi.advanceTimersByTimeAsync(betweenChecks)`
runs a timer whose callback chains a promise.

1. **The harness first.** Give the spec's `aBrowser` fake registration an
   `update` spy (`update: ReturnType<typeof vi.fn>` on `FakeRegistration`,
   `registration.update = vi.fn()` resolving), and add `vi.useRealTimers()` to
   the file's existing `afterEach`, so a case that fakes time cannot poison
   the next one. The eight existing cases stay green and unchanged.
2. **Red — the hour.** *asks for a newer version an hour after it registered*:
   `vi.useFakeTimers()` in the Given, construct the adapter, settle the
   registration with `await vi.advanceTimersByTimeAsync(0)`, then advance
   `betweenChecks`; assert `registration.update` was called once. **Green:**
   the constant and one `setTimeout` armed when the registration resolves.
3. **Red — not before.** *asks nothing before the hour is up*: a minute less,
   no call. Green already, so mutate the constant once to prove the case
   disagrees with the code, then put it back (`git checkout` reverts to the
   last commit, not to the working tree: commit before mutating).
4. **Red — it keeps asking.** *asks again an hour after the last check*: two
   hours, two calls. **Green:** the check arms the next one.
5. **Red — the foreground.** *asks the server when the app comes back to the
   foreground*: stub `document.visibilityState` to `"hidden"` and dispatch
   `visibilitychange`, then to `"visible"` and dispatch again, with no time
   advanced; one call. **Green:** the listener. Remove the stub in the
   `afterEach` with `Reflect.deleteProperty(document, "visibilityState")`.
6. **Red — the hour restarted by it.** *starts the hour again when it checks
   on coming back*: after that foreground check, an hour minus a minute keeps
   the count at one, the last minute makes it two. **Green:** the foreground
   check cancels the pending timer and arms a new one.
7. **Red — hidden.** *asks nothing while the app is hidden*: hidden, then two
   hours, no call. **Green:** going hidden cancels the pending check and arms
   nothing.
8. **Red — a refused check.** *keeps asking when a check fails*: `update`
   rejects; the hour, then the next hour, two calls, and Vitest reports no
   unhandled rejection. **Green:** a `catch` on the call.
9. **Red — no worker at all.** *asks nothing where the browser has no service
   worker*: no stub, construct, advance two hours, dispatch
   `visibilitychange`; nothing thrown, nothing called. **Green:** the guards
   the adapter already has, extended to the schedule.
10. **Run the scenarios** (`npx vitest run src/scenario`) before the gate: they
    are the proof that the schedule did not break the announcement, and their
    fake registration has no `update` — a check fired at registration time
    would throw there.
11. **Tidy on green**, then the full gate, then the pull request.

## Risks and decisions
- **"Stops asking when it goes away" is the hidden signal, not a second
  listener — decided here.** A page that goes away is hidden first: the
  browser fires `visibilitychange` with `"hidden"` before it freezes,
  discards or unloads the app, and the pending check is cancelled there, so
  nothing survives to ask. No `pagehide` or `unload` listener is added: it
  would cancel what is already cancelled, and D07 asks each case to prove a
  behaviour that can differ. The backlog line's own test list — "the hour, the
  return to the foreground, the hour restarted by it, and no check in
  between" — names no case for it.
- **Nothing is checked at registration time — decided here.** Registering is
  itself the question the browser asks the server, so the hour starts when
  the registration resolves. It is also what keeps
  `src/scenario/UpdateScenarios.spec.ts` green: its fake registration has no
  `update` method, and a check fired while that harness runs would throw
  inside a promise nobody awaits.
- **A foreground return before the registration resolves does nothing —
  decided here.** There is nothing to ask yet; the hour armed when the
  registration resolves covers what follows. One `null` guard, no case of its
  own: the existing *does nothing where the browser has no service worker*
  case already dispatches into that state.
- **The new cases stay flat, each fixing time in its own Given — decided
  here.** No spec in this tree nests a `describe`, and a test-layout
  convention is not a run's to invent (`CLAUDE.md`): `vi.useFakeTimers()`
  goes in the Given of each scheduling case and `vi.useRealTimers()` in the
  file's one `afterEach`.
- **The hour is `betweenChecks`, a module constant — decided here**, named
  after `betweenLooks` in `CameraBarcodeScanner.ts`, the only duration the
  tree already names. The spec advances by that constant, so the number lives
  in one place; no comment explains it (D10).
- **The adapter reads `document` — decided here.** It already reads
  `navigator.serviceWorker`; `document.visibilityState` is the same kind of
  thing, the browser the adapter exists to adapt, not configuration handed in
  by `bootstrap`. Only what jsdom refuses to let a test observe — the reload
  — is passed as a function, and that stays as it is.
- **The check is `registration.update()`.** It is the one call that asks the
  server for a newer worker; the browser answers it with `updatefound` when
  there is one, which is exactly the event the adapter already watches. Its
  promise rejects offline, so it is caught and the schedule survives.
- **To watch on the Pixel, for the pull request body:** an app woken from a
  long background on Android may fire `visibilitychange` before the network
  is back, so the first foreground check can fail and the next answer is an
  hour away. Nothing in this task shortens that; if Tophe sees it, it is a
  spec conversation about a retry, not a fix inside the run.
