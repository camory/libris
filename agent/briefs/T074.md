## Goal
`ListReaderBookshelves` answers the reader's bookshelves in the order of S1:
their default first, then the others by name, ignoring case and accents.
The home page of T079 lists the rows in the order of the answer, so the
order is the backend's to decide, and T078's new default rises to the top
through it.

## Risks and decisions
**Fit.** One run: one use case gains an order, three unit cases, one
un-skip; no port, adapter, web or migration change.

**The order lives in `ListReaderBookshelves`.** The default is the
reader's and the names are the bookshelves', so the order spans two
aggregates, which D12 gives the use case; the use case already holds both,
the `Reader` it is called with and the bookshelves it reads. Rejected: an
`ORDER BY … COLLATE ignoring_case_and_accents` in `findByMember` (a
repository of one aggregate holds no read's order, the default would still
need the use case, and the spec asks for a unit test); a comparator on
`Bookshelf` (a bookshelf's place depends on who asks); a collection type of
the domain (`ReaderBookshelf` is the application's answer, with no rule).

**"Ignoring case and accents" ignores nothing else.** The spec ignores case
and accents only, and the house's collation of the catalogue counts spaces
and hyphens (`One piece` before `Onepiece`, `backend.md`); step 3 pins it,
since the JDK's `Collator` at `PRIMARY` ignores the space and would answer
*Albums* before *À lire*. Which JDK means the implementer uses (a
`Normalizer` decomposition with the combining marks dropped and the case
folded, or a `Collator` configured otherwise) is theirs, recorded in the PR
body; the gotcha item names what `Collator` at `PRIMARY` does with a space,
for T075 and T076. Rejected: `Collator` at `PRIMARY` as it comes (it orders
by more than the spec says); a new dependency such as ICU4J (the JDK
suffices).

**Names equal ignoring case and accents keep the repository's order.** A
reader may belong to two bookshelves named *Salon* and *salon* (T075
refuses the second only among bookshelves they already belong to, not one
another reader adds them to later). The spec names no order between them;
a stable sort keeps the order `findByMember` answers, today by id. No case
asserts it. Rejected: a tie on the id in the use case (an order nobody
asked for, and no test could tell it from the repository's).

**S1 is a guard.** Measured while planning: un-skipped on today's `main`,
S1 passes, because `findByMember` orders by id and the ids are minted in
the order the Givens create the bookshelves. The unit cases carry the red;
step 4 names the mutations that make S1 red.
