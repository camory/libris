## Goal
`FetchCatalogueApi` reads a page of books in one private place, which
`browse` and `search` both go through; each keeps building its own
address and the search still reads `near`. The catalogue's client then
says once how a page is asked and read.

## Risks and decisions
**One rejection message, *The catalogue answered {status}*.** The reading
is one, so its message is; nothing reads the message (both composables
read a rejection as no answer, `git grep -n "\.message" -- frontend/src/application
frontend/src/ui` answers nothing), and `useBrowseCatalogue.spec.ts`'
`Error("The catalogue answered 503")` is a fake's own. Rejected: a word
per caller handed to the reading (a parameter for a text no one reads).

**Each read keeps building its own address; the reading starts from it.**
The addresses are what differs between the two reads, and the bare
`browse(null)` address, `/api/v1/books` with no `?`, is pinned by no
case (the trailing-`?` mutation stays green, measured above): leaving
the address lines untouched keeps it by construction, and the `git diff`
criterion shows it. Rejected: one reading taking the query parameters
and writing the `?` (it moves the one unpinned line); a guard case for
the bare address (a case the line does not ask, as T186 settled).

**The status check moves with the reading, unproven by a case.** Removing
it leaves the refusal cases green, since the problem body's missing
`books` makes the `map` throw; the move keeps the check before the body
is read, and the reviewer reads it in the diff. Rejected: a stubbed case
of a `400` with a page-shaped body (a new case, outside the line);
proposing it in `agent/PROPOSED.md` from here (the planner's run writes
the brief alone).

**Two moves, two commits.** The browse moves first, introducing the
reading; the search follows, adding `near`. Rejected: one commit (one
file, but two moves whose proof differs, the second adding `near`).
