## Goal
When Libris does not answer the ouvrage, its page says to try again later,
alone, instead of leaving the card's skeleton up for good. It closes the
last state of the edition page's spec.

## Test plan
Gate: `cd frontend && npm test`; fast loop `npx vitest run <path>` from
`frontend/`. A Libris that does not answer is `FakeCatalogueApi` built with
`new TypeError("Failed to fetch")` as its second argument: it rejects when
`find` is called, never in the Given (`frontend.md`, the unhandled
rejection).

**`src/application/useFindCatalogueEdition.spec.ts`**
1. **Red.** *is unavailable when Libris does not answer*: the find
   rejecting; after `await find(asterixLeGaulois.id)`, `state` is
   `{ status: "unavailable" }`. Red: `find` rejects and the state stays
   `loading`.
2. **Red.** *reads another problem as no answer*: the find answering
   `{ outcome: "problem", type: "/problems/conflict" }`; after the find,
   `state` is `{ status: "unavailable" }`. Red under step 1's green: every
   problem reads `notFound`. The two not-found cases already in the file
   keep S2's types on `notFound` through the change.

**`src/ui/views/editionPage/EditionPageView.spec.ts`**
3. **Red.** *says to try again later when Libris does not answer, alone*:
   mounted over a `FakeCatalogueApi` whose find rejects, once flushed,
   `normalised(wrapper.element)` is the sentence and
   `findAllComponents(CircleAlert)` has length 1, as *says there is no
   such ouvrage, alone* reads its own. Red under step 2's green: the view
   draws *Ouvrage introuvable.* for every state but loading and found.

**`src/scenario/EditionPageScenarios.spec.ts`**
4. **Guard.** S3 un-skipped. Mutation: the composable's catch of a
   rejected find removed, which leaves the page on its skeleton and reds
   S3 on `findByText` (with an unhandled rejection reported); reverted.
   The scenario may be un-skipped and its red read before step 1, then
   put back skipped, uncommitted, as T108 did.

## Out of scope
- A retry button or an automatic retry: the spec's Unavailable has none;
  the page asks anew on its next arrival, as today.
- `FetchCatalogueApi`, `problemOf` and `FakeCatalogueApi`: a proxy's
  plain-text answer already rejects there, and the fake already rejects
  with the error it is given.
- The catalogue's own failure (`catalogue.error`), the series page and
  every other screen; a shared failure message component for the pages.
- The offline cache of the PWA: what Workbox answers from its cache is
  not this task's.
- The sentences of `specs/catalogue.md` and `specs/series-page.md` saying
  a row leads nowhere: Tophe's, under *Questions for the human*.

## Risks and decisions
**Another problem type reads as unavailable.** T113 kept every problem as
no such ouvrage until this task; D11 asks a fallback for a key the
frontend does not know, and `useFindCatalogueSeries` (T108) and
`useFindBookshelf` read another problem as no answer, the same sentence.
A problem the contract does not declare for this operation, a 5xx with a
problem body, is not an ouvrage that cannot be found. Rejected: keep it
`notFound` (says an ouvrage the reader owns does not exist); a third
message (no spec words).

**The sentence's key is `editionPage.error`.** Each screen holds its
messages under its own key, `seriesPage.error` beside
`seriesPage.notFound`, `editionPage.notFound` already. Rejected: reusing
`seriesPage.error` (a change to the series page's words would change the
ouvrage's).

**The message takes the not-found one's place and layout.** The mockup
draws the alert and the sentence at the top of the content, as *Ouvrage
introuvable.*; how the view picks the sentence per state (two branches,
or a computed message as `SeriesPageView`'s `failure`) is the
implementer's.

**S3 un-skipped last, a guard**, as in T108: by step 3 it passes.
