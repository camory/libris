`/problems/conflict`; the first `PUT` and the first `204`.

## Goal
The backend serves the whole of `v0.11.0`: a reader lists the bookshelves
they belong to with their role and creates one they alone own, and the four
other bookshelf operations answer through use cases that T073 to T078 fill.
The frontend of the phase reads these operations.

## Rules in play
- D04 — the pin moves from `v0.10.0` to `v0.11.0`, nothing else of the
  contract; the cases of the earlier operations stay green unchanged.
- D07 — the pin bump is the first red, each operation's controller method its
  green; `S2 A reader creates a bookshelf` is un-skipped and nothing else of
  `BookshelvesScenarios` changes; no hand-written web test.
- D02 — a controller calls use cases, never a repository; the new paths sit
  in `web` sub-packages named after their first segment, as the tree does.
- D12 — `Bookshelf` answers a reader's role (`roleOf`), the use case never
  reads `memberships`; `CreateBookshelf` mints the id and builds the
  aggregate, which keeps its owner rule in `init`.
- D10 — use cases named by their sentence, `operator fun invoke` alone
  public; DTOs map themselves (`from`, request to application type); a bare
  name imported, qualified where two results share it in one file; no
  visibility widens.
- D11 — `400`, `404`, `409` are use-case results the controller maps; the
  validation problem carries `errors: [{field, code}]`; `/problems/conflict`
  joins the slugs; ids are strings in JSON.

## Risks and decisions
**Fit.** One run: the pin bump reds all six operations at once, and S2's
behaviour is two small use cases. Rejected: a split (the bump cannot be
split; T043 served a whole pin the same way).

**Web placement.** D02 asks one sub-package per path, named after it; the
tree names each after the path's first segment (`web.isbn`, `web.cover`,
`web.bookshelf` for `/bookshelves/{id}/books`, `web.me`). So the three
`/bookshelves…` paths join `web.bookshelf`, `/me/default-bookshelf` joins
`web.me`, `/readers` opens `web.reader`, one controller per sub-package as
now. The PR body proposes D02 say "named after the path's first segment,
one controller per sub-package". Rejected: one sub-package per literal path
(`/bookshelves` and `/bookshelves/{id}` would both claim `bookshelf`, taken);
one controller per operation (a naming scheme no document states). Watch
detekt's `TooManyFunctions` (11) on `BookshelfController`: a private helper
shared by the four methods (`invalid`, a `notFound()`) keeps it under; if
not, ask in the PR, do not raise the threshold.

**Use cases at the root of `library.application`,** the bookshelf use
cases' home now. Rejected: an `application.bookshelf` sub-package (moves
existing use cases, not this task's).

**Every refusal a result now.** The backlog line asks each declared `400`,
`404`, `409` from a use case's outcome, so `BlankName`, `NameTaken`,
`UnknownReader`, `AlreadyAMember` exist now, answered only by the contract's
stubs until T075 and T077 make them real; T075 may move the blank refusal to
where the name is built and keep `BlankName` as the outcome of that refusal.
Rejected: a refusal at the edge in `NewBookshelfRequest.validate` (a rule at
the edge, and T075's choice).

**`roleOf` on `Bookshelf`.** The aggregate answers a reader's role, `null`
when no member, so `ListReaderBookshelves` holds no rule. Rejected: reading
`memberships` in the use case (a rule outside its aggregate, D12).

**`CreateBookshelf` writes in one transaction.** The repository writes the
bookshelf row and each membership row in separate statements; a bookshelf
without its owner row must never be stored. Rejected: no transaction (a
failed membership insert leaves a bookshelf no one sees).

**`ListReaderBookshelves` takes a `Reader`, `CreateBookshelf` a `ReaderId`.**
The list's order (T074) reads the reader's default first; creating needs the
id only. `ChooseDefaultBookshelf` takes the `Reader` it will change (T078).
Rejected: a `ReaderId` everywhere (T074 would change the signature).

**Shared names.** `NoSuchBookshelf` and `Added` exist in several results:
in `BookshelfController` they are written qualified
(`OpenBookshelfResult.NoSuchBookshelf`) wherever two would collide, as D10
allows. Rejected: renaming a result's members per use case (a naming scheme
of its own).
