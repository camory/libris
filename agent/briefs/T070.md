**First of its kind:** the first ImageIO plugin: a library no line of code
names, found by the JDK's service loader on the class path at run time, and
with it the first `runtimeOnly` entry of the version catalog.

## Goal
A fetched body is a cover only when Libris reads it as a picture whose
header claims no side over 5 000 pixels, checked before any pixel is
decoded; anything else is not a picture: the cascade asks the next source,
a chosen source leaves the wait dated. A header claiming 20 000 × 20 000 no
longer brings the worker down with an `OutOfMemoryError`, and inventaire.io's
WebP is read as the picture it is.

## Risks and decisions
**The rule is `Cover.normalised(): Cover?`.** Normalising already reads the
picture; the picture rule reads it once with it: the header's sides first,
then the pixels, then the scaling of S6, one pass. `null` means "no
picture". *Rejected:* `Cover.of` refusing what is no picture: `FileCoverStore.read`
builds through it, so every served cover would be decoded, and a picture
would be read twice on its way in; a second method `isPicture()` before
`normalised()`, two reads of one body.

**The cascade applies the rule, not the use case.** S7 and the task line
want the next source asked when one answers no picture; `CoverFetches`
already stops at the first answer, so the rule sits where it stops. One
call site serves the chosen source too: its one fetch answering no picture
is `null`, and the use case keeps the wait dated as it does for any miss;
S8's fourth case is that proof. *Rejected:* each adapter checking its
picture, three copies, and the domain rule in infrastructure; the use case
iterating the sources, the cascade's order rule leaving `CoverFetches`.

**`runtimeOnly`.** No code names the plugin: ImageIO finds its reader
through the service loader, so the library stays off the compile class path,
where nothing can import it by mistake and ArchUnit has nothing to see.
*Rejected:* `implementation`, a compile-time dependency no code uses.

**Production: the plugin is found in the boot jar.** ImageIO registers the
plugins its first caller's context class loader sees; in a Spring Boot jar
that is Boot's loader on the main, request and worker threads, but no test
runs the jar: the gate's class path is flat. A missed plugin would not
fail: every inventaire.io WebP would be no picture and the cascade would
fall to Open Library. The PR asks Tophe to check on staging that an ouvrage
added with *Couverture inventaire.io* shows a WebP cover.

**"Never decoded" is proven by the heap.** Gradle's test JVM defaults to
512 MB and `build.gradle.kts` sets no `maxHeapSize`: a 20 000 × 20 000
header decoded needs 1.2 GB, so step 4 is red for a rule that decodes before
it checks. Do not raise the heap.

**`jpegClaiming` patches a generated JPEG.** The spec asks for generated
bytes; writing a 20 000 × 20 000 picture is the very allocation the rule
forbids. The patch rewrites the SOF0 marker (`FF C0`) of a 1×1 JPEG from
`ImageIO`, height then width, two bytes each; measured on JDK 25: the
header reads as claimed and the reader decodes at those sides.

**Two covers compare as instances.** `Cover` has no `equals`, and
`CoverFetchesTest` and `FetchAwaitedCoversTest` compare covers with
`shouldBe`: a picture kept as fetched must remain the instance given, as
today.
