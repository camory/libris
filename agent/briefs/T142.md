**First of its kind:** the bibliography's first query port, and the first
port that reads a name row (`author`) on its own, beside the repository
that writes it: `AuthorNames`, read by `JdbcAuthorNames` while
`JdbcEditionRepository` keeps every write of the table.

## Goal
The backend pins `v0.17.0` and serves `GET /api/v1/author-names`, the name
of every author the house holds, read through a bibliography use case over
a query port on the `author` table, so that S6's backend scenario holds and
Contracteer verifies the operation's shape. T143 then changes how a name is
matched, behind `JdbcEditionRepository`, and T144 moves the frontend onto
this release.

## Rules in play
- D04 — the pin moves from `v0.16.0` to `v0.17.0` and nothing else of the
  contract changes; every case of the earlier operations stays green.
- D07 — the pin bump is the first red, the controller its green; the S6
  method of `AuthorsEditScenarios` is un-skipped and nothing else in that
  file changes; no hand-written web test; the contract stub fills every
  constraint of the answer (`minLength`, `pattern`, `uniqueItems`).
- D02 — the bibliography answers the names: the use case in
  `bibliography.application`, the port in `bibliography.domain`, the SQL in
  `bibliography.infrastructure.persistence`; the controller in `web.author`
  calls the use case, never the port.
- D12 — an author is a value of the edition, not an aggregate: no
  `AuthorRepository`, no `Author` type; the name row is what the read
  reads. *None blank* is `Contribution`'s `init`, the only writer of a
  name; *each once* the unique index on the name: neither is written again
  in the use case or the SQL (no `DISTINCT`, no blank filter).
- D10 — `ListAuthorNames`, imperative sentence, `operator fun invoke` its
  one public member, held in `listAuthorNames`; a query port named by what
  it answers, no `Repository` suffix, its method keeping a repository's
  verb, `authorNames.findAll()`; SQL keywords upper case; no rationale and
  no `D##` in code.
- D11 — the names come in no promised order: no `ORDER BY`, no sort in
  Kotlin, every assertion in any order.

## Risks and decisions
**Fit.** One run: one pin, a new one-route controller, a query port of one
method with its adapter and fake, a one-line use case, eight test files
touched, the same shape as T119. Rejected: a split, since the bump reds
the new operation and only the controller greens it.

**A query port `AuthorNames` over the `author` table.** An author is a
value of the edition (D12), so no repository of its own exists to read
it; D12 makes the name row "what a filter or a sort by the name reads",
and a query port, named by what it answers (D10, as `CatalogueEditions`),
is how the tree reads what no repository answers alone. The answer is
one column of one table in one statement. Rejected:
`EditionRepository.findAuthorNames()` (a repository answering a field,
which T119 rejected for the series; and `JdbcEditionRepository` sits at
one function short of detekt's `TooManyFunctions`); `EditionRepository.findAll()` with
the names taken in the use case (rebuilds every edition of the house,
summaries included, for one column, and moves *each once* into a
`distinct()` the schema already keeps); an `Author` aggregate (D12: it
becomes one the day it gains a fact or an id, and the contract gives it
neither).

**Every row of `author`, not only those a contribution names.** No
statement deletes a contribution without writing the same ones again
(`update` is called for the cover alone), so today every row is named by
an edition; the series' names read every row of `series` the same way.
What an edition's corrected authors leave behind is the open item of
`agent/PROPOSED.md` on the rows old values named, for the spec that edits
a stored edition. Rejected: a semi-join on `contribution` (a rule for a
case no code produces yet).

**`AuthorNames` in `bibliography.domain.edition`, `ListAuthorNames` in
`bibliography.application.edition`.** The author is the edition's value
and its table is written by the edition's repository; D12 places a query
port in the sub-package of its concern, as `CatalogueEditions` sits in
`library.domain.copy`; the use case follows its port's sub-package, as
`ListSeriesNames` follows `domain.series`. Named as `ListSeriesNames`.
Rejected: a new `author` sub-package in `domain` and `application` (a
concern with no aggregate, one interface and one class).

**The route in a new `web.author`, `AuthorController`.** D02 names a web
sub-package after the product word of the resource, and *author* (PRD §3)
has none yet; the controller returns the use case's `List<String>` as it
is, as `SeriesController.names` does. Rejected: the route in
`web.isbn` or `web.series` (neither is the product word of the resource).

**`AuthorNamesAnswering`, a fake answering what it is built with.** The
port only answers, as `CatalogueEditionsAnswering`'s does, so its fake
takes the names in its constructor; the use case's test then proves the
use case answers what the port read. Rejected: an `…InMemory` fed through
editions (a second implementation of the read in a test double).

**Step 6 is a guard.** Mockito answers an empty list to an unstubbed
`List` method, so the generated case is green at step 5 with `[]`, which
checks no item. The stub of two names makes the verifier read the items'
constraints; its mutation proves `uniqueItems` is read on this release.
