## Risks and decisions
**Fit.** One run: one pin, one controller, one use case answering a
constant, two small types, three test files touched. Rejected: a split (the
bump and the operation it reds cannot be parted).

**`ListCatalogueSeries` in `library.application.catalogue`.** The spec and
the contract call the answer "the series of the reader's catalogue", and T093
applies the catalogue's rule (an edition with a copy on a bookshelf the
reader belongs to), so the use case sits beside `BrowseCatalogue`, its answer
type beside `CataloguePage`, and its call reads
`listCatalogueSeries(reader.id)`. Rejected: the root of
`library.application` (where the bookshelf use cases live, not the
catalogue's reads); a new `application.series` sub-package (a layout the
tree does not have, for one class); `ListReaderSeries` (the reader's
bookshelves are `ListReaderBookshelves`; the series are the catalogue's).

**`CatalogueSeries`, four fields, `coverName` and `kind` nullable.** It
carries what the answer needs as the application knows it: the cover as a
`CoverName`, turned into an address at the edge as for a `Book`; the kind
null when the editions differ, the cover null when the first has none, both
null until T094 and T095. Rejected: naming it `Series` (the scenario DSL and
the contract use it, and the domain's `SeriesEntry` sits beside it: three
meanings of one word in one stack trace); `coverUrl` in the application type
(the path is the web's, `coverPathOf`).

**`invoke(readerId: ReaderId)`.** The catalogue's read takes the id
(`BrowseCatalogue`), and T093 needs only the bookshelves the reader belongs
to, `findByMember(readerId)`. Rejected: the `Reader` (nothing of it but the
id is read).

**The stub as a guard.** With no stub the mock answers an empty list, which
the verifier accepts, so step 3 is green without it; D07 still asks a stub
filling every constrained field, so that the response's form meets the
schema. It is a guard of its own, step 4, named by the mutation it catches.
