## Risks and decisions
**The client implements one operation.** `BookshelvesApi` names five, and
the type check needs all five on `FetchBookshelvesApi`; the four this task
does not use reject with an `Error` naming the operation, untested, each
replaced by the task bringing its screen. Rejected: a narrower port for the
home page (the precondition's port is given, and splitting it is a
structural choice no document makes). Rejected: implementing all five now
(four operations no screen of this task exercises).

**No status check in `memberships()`.** The contract declares `200` alone,
and D07 allows no case for another; a non-JSON answer rejects through
`response.json()`, which the composable turns into `unavailable`.
Rejected: a `response.ok` check (code no test can motivate).

**The view keeps reading the reader.** The greeting already asks
`meApi.currentReader()`; the view passes its `defaultBookshelf.id` to
`membershipsInOrder`, and the composable takes `bookshelvesApi` alone.
The rows wait for both answers; until then the skeleton shows. Rejected:
the composable reading both ports (a second `GET /api/v1/me`).

**The order lives on `Membership`.** `membershipsInOrder` sits beside the
type it sorts, as `authorsInOrder` sits in `SourceEdition.ts`. Rejected:
the order in the composable (D05 and D11 want it pure, in the domain).

**The port joins `LibrisPorts` before the view uses it.** Step 3 comes
before the view injects the port, so no app-level test on `/` meets a
missing key; the precondition left both ports out, each task bringing its
own (#244). Rejected: providing it beside `createLibrisApp` in `open()`
(the scenario then tests a wiring `bootstrap` does not have).

**Guards for the scenarios.** By step 15 both pass, so each is un-skipped
as a guard, as T060 did. Rejected: un-skipping them first, red for twelve
commits.

**Three skeleton rows.** The mockup *1-home-loading* draws three; the spec
names no count. Rejected: five, as the catalogue (another screen's mockup).
