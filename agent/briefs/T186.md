## Goal
`useRemoveCopy` hands the id of the copy it removed to `afterRemoval`, and
the two views read it there: both `let removedId` and both `removeCopy`
wrappers go. What follows a removal then learns which copy went from the
removal itself, not from a variable each view keeps beside it.

## Risks and decisions
**The id travels as the argument of `afterRemoval`.** The composable
already holds it when it calls the callback, and the callback is what
each view wrote the wrapper for; `afterRemoval: (copyId: string) =>
Promise<void>` reads as the composable's verb does. Rejected: the
`removed` state carrying the id (the views act inside `afterRemoval`,
while the state is still `removing`, and the spinner depends on it);
`remove` answering the id (its caller knows it already, and the views
act before it returns).

**No case added to `useRemoveCopy.spec.ts`.** The line is a refactor
whose proof is the existing tests unchanged, as T185 settled; losing the
id reds sixteen view and scenario cases (measured above) and a call
without it fails `vue-tsc`. The existing cases' callbacks take no
parameter and stay assignable to the new type. Rejected: a case
asserting the id handed (a case the line does not ask).

**Three moves, three commits.** The composable's change compiles with
both views untouched, so each view moves on its own with its own specs.
Rejected: one commit for all three files (a diff whose proof is three
rows at once); a split (three small files, read in minutes).
