## Goal
The add of an ISBN the house holds writes the fields sent over the
edition, through `EditEdition`, the save's own use case. Its own series and
authors are respelled and its stored cover kept, and the copy lands as
before. With this, the add and the save write an edition the same way,
which T159's pencil on the lookup's card needs before the frontend moves.

## Rules in play
- D02 — `HoldEdition` (`bibliography.application.edition`) calls
  `EditEdition` from the same package. `AddBookToBookshelf`, `library`,
  `web`, the domain, the ports and the adapters do not change.
- D04 — no contract edit: the backend has pinned `v0.18.0` since T153.
  That release already words the add of a held ISBN as writing the fields
  sent.
- D07 — the two `@Disabled` lines of *S2* and *S5 …, the add of a held
  ISBN* and the now-unused `Disabled` import are removed, nothing else in
  `HeldEditionEditScenarios`. `HoldEditionTest` is plain JUnit over the
  fakes, with its `EditEdition` built over the same fakes and
  `withoutTransaction()`. No test of a controller. `ApiContractTest`'s
  `tests=` stays as on `main` (50).
- D10 — `HoldEdition` keeps `operator fun invoke` as its one public member
  and takes `EditEdition` through its constructor, held as `editEdition`.
  The conversion is a public method of `NewEdition`, named `to…` as
  `NewMemberRequest.toMembership()` is. Given / When / Then; a new fixture
  goes below the class, where its first user reaches it. No rationale and
  no `D##` in code.
- D11 — no optimistic locking: the add's write wins over a save made
  before it, and the other way round. The add of a held ISBN inserts no
  awaited cover, and its `coverSource` is read by nothing.
- D12 — the add of a held ISBN respells its own series and authors because
  it writes through `EditEdition`, which calls
  `respellOrFindOrInsert(…, own series id)` and `EditionRepository.update`.
  The add of an ISBN the house lacks keeps `findOrInsert` and `insert`,
  which never respell.
- PRD §4.1 — the edition is created when its ISBN is unknown, else written
  with the fields sent. The copy goes on the bookshelf asked, as before.

## Risks and decisions
**Fit.** One run: no migration, SQL, port, dependency or contract change.
The work is one branch of `HoldEdition`, one conversion, one use-case case
and two un-skips. Rejected: a split (each half would be one cycle).

**The write through `EditEdition`.** The line says *as the save does*.
T154 put the save's write in the bibliography so that `HoldEdition` could
reach it (T154's brief, *The write in a bibliography use case*). Calling
it keeps the series' and the authors' respelling and the kept cover in one
place, so a later rule of the save is a rule of the add too. `EditEdition`
reads the edition back after the write, so the add answers what the house
holds, as the save does. Rejected: a second copy of `editedOf` and
`seriesVolumeOf` in `HoldEdition` (two writes of one rule). Rejected: a
function shared by the two use cases (`EditEdition` already is that
function, with its transaction).

**`NoSuchEdition` cannot answer a held edition.** `HoldEdition` hands
`EditEdition` the id of an edition it has just found, and an edition is
never deleted (PRD §3, D11). That branch fails as `EditEdition`'s own
`checkNotNull` on its read-back does, with no outcome of its own and no
test. Rejected: a result type for `HoldEdition` (no caller can meet it).

**Transactions.** The held branch opens no block of `HoldEdition`'s own.
`EditEdition` writes in its block, which joins `AddBookToBookshelf`'s, so
the edition's write and the copy's insert commit together, as the insert
branch's do. `HoldEditionTest` builds `EditEdition` over
`withoutTransaction()`, so the transaction case still records
`HoldEdition`'s one block (the gotcha on a use case called inside
another's block).

**`NewEdition.toEditionDetails()`, not composition.** The PROPOSED item
from T154 left open whether `NewEdition` composes `EditionDetails`.
Composition would reshape `NewEdition.of`, `NewBookRequest.validate`,
`NewEditionTest`, `NewBookRequestTest`, the add's contract stubs and every
`copy(…)` of the add's tests, a refactor larger than this task. One method
on `NewEdition`, the type holding the data, does the conversion, and the
item stays open for its own task. Rejected: a private helper in
`HoldEdition` (the use case converting a value's own data).

**A worker run racing the add.** `FetchAwaitedCovers` writes a fetched
cover through `update` with the names it read, and could cross the add's
write as it already crosses a save (D11, no optimistic locking). A held
edition's cover was awaited when it was first added, so the race is no
wider than the save's. Nothing to do here.
