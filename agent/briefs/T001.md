DSL with `gradle/libs.versions.toml`; starters webmvc and actuator only: no
Spring Security and no datasource yet, both arrive with T005. `./gradlew check`

test.
**Serves:** PRD §5 (operability: health endpoint; testability); decisions D01,
D02 (package root only), D07, D09 (health endpoint only), D10.

## Goal
When this task is done, `backend/` is a Spring Boot / Kotlin application that
starts, answers `GET /actuator/health` with `UP`, and whose `cd backend &&
./gradlew check` is the D07 gate for the code that exists. It matters now
because every later backend task (T003, T005) builds on that gate, and the CI
`backend` job starts running the moment `backend/gradlew` exists.

      Kover XML report task; after a real `check`,

- [ ] `backend/README.md` states how to run (`./gradlew bootRun`, the health

- [ ] The CI `backend` job is green on the pull request (JDK 25,

## Test plan
This task ships no test class. D07 allows a test of framework or library
wiring to be written while learning and deleted before the pull request, and
the backlog line asks for the gate itself to be verified by commands. The
first permanent tests arrive with T005, which brings the first domain code and
the six ArchUnit rules of D02.

So the plan is a verification script, each step run for real and its output
pasted in the PR body under **How verified**:

1. `./gradlew check` — the gate, exit 0, run plainly and last in its command.
2. `./gradlew check --dry-run` — `:detekt`, `:test`, Kover XML in the task
   list.
3. Throwaway `src/main/kotlin` edit: useless cast → `compileKotlin` fails;
   revert.
4. Throwaway `src/main/kotlin` edits, one at a time: `!!`, `lateinit var`,
   wrong indentation → `detekt` fails, three distinct rule names; revert.
5. Throwaway test class using JUnit 5 `@Test` and Kotest `shouldBe` →
   `./gradlew test` reports 1 test passed; delete the class.
6. `./gradlew bootRun` in the background, `curl` the health endpoint, stop it.
7. `env -u LIBRIS_DB_* ./gradlew check` — still green.

Green means `cd backend && ./gradlew check`, nothing piped or chained after it,
so the sandbox records the gate on the current tree (see
`agent/prompts/implementer.md`).

## Risks and decisions
- **Versions.** Pin exactly what `agent/PROGRESS.md` recorded as measured to
  work yesterday: Gradle 9.7.1, Spring Boot 4.1.1, Kotlin 2.3.21 (the version
  Boot 4.1.1 manages), detekt 1.23.8, Kover 0.9.9, Kotest 6.2.4. Decision: do
  not chase a newer release found on the way; D10 makes an upgrade its own
  task, and every gotcha below was measured against these.
- **Boot 4 artefact names** (`agent/PROGRESS.md`): the web starter is
  `spring-boot-starter-webmvc`; `kotlin-reflect` is needed at runtime by
  Spring's Kotlin support. Versions the BOM manages are not repeated in the
  catalog.
- **detekt 1.23.8 on JDK 25.** Its embedded Kotlin 2.0.21 compiler fails with
  `IllegalArgumentException: 25.0.x` only when handed a JDK 25 as `jdkHome`,
  which the plugin's type-resolution tasks set by convention. Decision: use
  the detekt **Gradle plugin** and clear that convention, as measured:
  ```
  tasks.withType<io.gitlab.arturbosch.detekt.Detekt>().configureEach {
      jdkHome.convention(null as Directory?)
      jvmTarget = "21"
  }
  ```
  This replaces the JavaExec + JDK 21 toolchain + foojay construction of PR
  #11, which the same entry says is not needed. Consequence to accept: with no
  JDK on detekt's classpath, `!!` is reported on Kotlin-typed receivers only —
  enough for the `!!` criterion, which is verified on a Kotlin-typed one.
  Falling back to the CLI, or to a detekt pre-release, is a structural change:
  report `blocked` instead.
- **detekt covers part of D10 only.** It has no rule for "sealed types for
  states" or "constructor injection". Decision: enforce what it can (`!!`,
  `lateinit`, formatting) and state the gap under *Follow-ups* in the PR body,
  for Tophe to amend D10 or ask for an ArchUnit rule later.
- **A gate with no tests.** The backlog line asks for JUnit 5 + Kotest
  assertions in the gate while verifying this task by commands, so the test
  dependencies ship with no test class to exercise them. Decision: keep the
  smallest set that makes `./gradlew test` able to run a JUnit 5 test with a
  Kotest assertion — `org.junit.jupiter:junit-jupiter` and
  `org.junit.platform:junit-platform-launcher` (both BOM-managed) and
  `io.kotest:kotest-assertions-core` — and prove it with the throwaway test of
  the test plan. `spring-boot-starter-test` is not added here: it arrives with
  T005's first Spring test.
- **Kover with no test.** `koverXmlReport` still runs and reports zero
  coverage of `LibrisApplication`. The criterion is that the XML exists, not
  what it contains.
- **The proof hook** counts any command containing `gradlew … check` as a gate
  run, `--dry-run` and heredoc text included. Decision: write files with the
  Write tool, keep the gate plain, and run `--dry-run` knowing it also counts —
  the last plain green `check` on the final tree is what matters.
- **CI runs the `backend` job with a PostgreSQL service and `LIBRIS_DB_*` set.**
  Harmless: this task's application reads neither. The criterion that the gate
  passes with those variables unset is what keeps T001 free of a datasource.
- **`gh pr edit`** can fail with a GraphQL error about classic Projects; the
  REST API (`gh api -X PATCH repos/…/pulls/N`) works.
