## Goal
`ListCatalogueSeries` stops answering a constant: it reads the reader's
bookshelves, the copies on them and their editions, and answers one
`CatalogueSeries` per series name with the number of its editions, so S1
holds over HTTP. T094 and T095 fill `kind` and `coverName` behind the same
read.

## Risks and decisions
**Fit.** One run: one finder with two slice cases, one use case with one
unit case, one scenario un-skipped, six files. Rejected: a split (the finder
has no user but this read).

**Three repositories, not a query port.** D12 gives a read across
aggregates to the use case through each aggregate's repository, and a query
port only to a read the repositories cannot serve within a few queries:
here three statements, the reader's bookshelves, the copies on them, their
editions. A household holds a few hundred editions, read whole each time
the series screen opens, which is what an unpaged answer of a few dozen
series costs. Rejected: `CatalogueEditions` answering every edition id of
the reader (a query port where repositories suffice); one SQL query
grouping by series (the count, then T094's kind and T095's cover, would be
rules in SQL, unseen by a unit test).

**`CopyRepository.findByBookshelfIds`.** The copies of the reader's
bookshelves are the catalogue's rule read through the library's own
aggregates, the way `BrowseCatalogue` filters copies on `findByMember`'s
bookshelves. Rejected: `findByEditionIds` (it needs the edition ids first,
which only the copies give); a finder taking the `ReaderId` (a join of
`copy` and `membership`, two aggregates in one repository statement).

**A series matched by its name as read back.** A series is the
`SeriesEntry` of its editions, matched by name (PRD §3); persistence keeps
one `series` row per name whatever its capitalisation, and every edition
reads back that row's spelling, so the editions of one series carry one
`name` and grouping on it is exact. Rejected: folding case in Kotlin (a
second matching rule beside the database's, for spellings no read
answers).

**The count is the use case's for now.** No aggregate holds a series'
editions, so counting them is the read's own work, like `BrowseCatalogue`
grouping copies by edition; the count is the size of the series' editions,
which are distinct by construction, never the number of copies. Whether
T094's shared kind and T095's cover pick move this grouping into a domain
type is their briefs' call. Rejected: a domain type now (it would hold no
rule but `size`).
