# T006 — Backend persistence: the member table and its repository

**Backlog line:** Backend persistence: the member table and its repository.
Starters data-jdbc and flyway plus the PostgreSQL driver; datasource from
`LIBRIS_DB_URL` / `LIBRIS_DB_USER` / `LIBRIS_DB_PASSWORD`, migrated by Flyway,
never by `ddl-auto` (D02, D08). `V001__member.sql`: `id` uuid primary key,
`username` unique and not null, `display_name` not null, `created_at` and
`updated_at` in `timestamptz` (D11). `domain`: the member profile aggregate and
its port, exposing `insert` and a lookup by username; `infra.persistence`: the
adapter over `JdbcAggregateTemplate` with uuid v7 ids
(`com.fasterxml.uuid:java-uuid-generator`) and Spring Data JDBC auditing, never
`CrudRepository.save` (D11). Nothing web changes: `/api/v1/me` still answers the
headers alone, and `api/openapi.yaml` is untouched. Tests: the adapter against
the PostgreSQL of D08 — insert then find by username, the id a version 7 uuid,
both timestamps filled, a second row with the same username refused — in a
transaction rolled back at the end (D07). The ArchUnit rules these classes give
something to check: `infra` packages never depend on each other, a port declared
in `domain` is implemented only in `infra`, `CrudRepository.save` is never
called (D02, D11); the `application` rule arrives with T009.
**Serves:** PRD §2 (Admin and Member), §4.10 (Libris creates a member profile on
first visit); decisions D02, D03, D07, D08, D10, D11.

## Goal
When this task is done the backend has a database: the given PostgreSQL of D08
is migrated by Flyway at start-up, a `member` table exists, and a member profile
can be written and read back through a port declared in `domain` and implemented
in `infra.persistence` — with an application-generated version 7 uuid and the
two audit timestamps D11 asks for. It matters now because T009 hangs
first-visit profile creation on exactly this port, and because this is the run
that turns "the environment is given" (D08) and the persistence half of D11 from
documents into code the gate exercises.

Read `agent/PROGRESS.md`'s T005 entry first. Four things carry over: the gate is
recorded, so keep `cd backend && ./gradlew check` plain and last in its command;
`detekt` runs on the test sources inside `check`; an ArchUnit rule is written
``@ArchTest fun `name`(classes: JavaClasses)`` with `.check(classes)`, never as a
`val`; and a Spring test class takes its beans through an `@Autowired`
constructor (D10).

```kotlin
@Table("member")
data class MemberProfile(
    @Id val id: UUID,
    val username: String,
    val displayName: String,
    @CreatedDate val createdAt: Instant? = null,
    @LastModifiedDate val updatedAt: Instant? = null,
)

interface MemberProfileRepository {
    fun insert(profile: MemberProfile): MemberProfile

    fun findByUsername(username: String): MemberProfile?
}

interface IdGenerator {
    fun next(): UUID
}

@Component
class UuidV7IdGenerator : IdGenerator {
    private val generator = Generators.timeBasedEpochGenerator()

    override fun next(): UUID = generator.generate()
}

@Repository
class JdbcMemberProfileRepository(
    private val aggregates: JdbcAggregateTemplate,
    private val auditing: IsNewAwareAuditingHandler,
) : MemberProfileRepository {
    override fun insert(profile: MemberProfile): MemberProfile = aggregates.insert(auditing.markCreated(profile))

    override fun findByUsername(username: String): MemberProfile? =
        aggregates
            .findOne(Query.query(Criteria.where("username").`is`(username)), MemberProfile::class.java)
            .orElse(null)
}
```

## Risks and decisions
Everything marked *measured* was run on 2026-09-09 in a throwaway copy of
`backend/`; nothing was left in the repository and the given database was
restored to no user tables.

- **The Flyway checksum trap.** *Measured*: once `V001__member.sql` has run
  against the sandbox database, editing a single character of it fails every
  later run at context start-up with `Validate failed: Migrations have failed
  validation / Migration checksum mismatch for migration version 001`. The
  database is shared and outlives the run, and the sandbox has no `psql` (D08).
  Decision: write `V001` complete in one cycle, and never edit it afterwards —
  which is also D11's rule for a merged migration. If it happens anyway, the
  *measured* repair is a throwaway test class, run once and deleted:
  `@SpringBootTest(properties = ["spring.flyway.enabled=false"])` with an
  `@Autowired` `JdbcClient` running `drop table if exists member cascade` and
  `drop table if exists flyway_schema_history`; the next run applies the edited
  migration from scratch.
- **`flyway-core` alone does nothing on Spring Boot 4.** *Measured*: with
  `implementation("org.flywaydb:flyway-core")` no migration runs at all and the
  first query fails with `relation "member" does not exist`. Boot 4 moved the
  auto-configuration into its own module: the dependency is
  `implementation("org.springframework.boot:spring-boot-flyway")`, BOM-managed.
- **`flyway-database-postgresql` is required.** *Measured*: without it,
  start-up fails with `Unsupported Database: PostgreSQL 18.6`. It is BOM-managed
  (12.4.0) and belongs on `runtimeOnly`, like the driver.
- **Dependencies, and no others.** `implementation("org.springframework.boot:spring-boot-starter-data-jdbc")`,
  `implementation("org.springframework.boot:spring-boot-flyway")`,
  `runtimeOnly("org.flywaydb:flyway-database-postgresql")`,
  `runtimeOnly("org.postgresql:postgresql")` — all BOM-managed, so no catalogue
  entry (T003 precedent) — plus `implementation(libs.uuid.generator)` with
  `com.fasterxml.uuid:java-uuid-generator` pinned to **5.2.0** in
  `gradle/libs.versions.toml` (D10; latest on Maven Central, checked
  2026-09-09).
- **Auditing skips `created_at` when the application generates the id.**
  *Measured*: with `@EnableJdbcAuditing` alone, `updated_at` is filled but the
  insert fails with `null value in column "created_at" … violates not-null
  constraint`, because an entity whose `@Id` is already set is not "new" and
  `@CreatedDate` is only applied to new entities. Decision: the adapter calls
  `IsNewAwareAuditingHandler.markCreated(profile)` before
  `JdbcAggregateTemplate.insert`, *measured* green. The timestamps still come
  from Spring Data's auditing handler and never from an `Instant.now()` of ours,
  which is what D11 asks. Rejected: implementing `org.springframework.data.domain.Persistable`
  in the aggregate (a Spring Data type in `domain` beyond the mapping
  annotations D02 allows), a `@Version` column (D11: no optimistic locking in
  v1), and SQL `default now()` (that is the database filling them, not
  auditing).
- **Where uuid v7 generation lives.** `domain` may depend only on the standard
  libraries (D02 rule 1), so it cannot call `com.fasterxml.uuid`; `application`
  may depend only on `domain` (rule 2), so T009's use case cannot either; and
  D11 wants the id non-null in the domain, so the adapter cannot invent it after
  the fact. Decision: a port `IdGenerator` in `domain` with the single method
  `next(): UUID`, implemented once by `UuidV7IdGenerator` in
  `infra.persistence`. It is used by this task's tests and by T009's use case;
  no other implementation is written.
- **Names, and the convention they set.** The aggregate is `MemberProfile`, not
  `Member`: `domain/Member.kt` already holds the header-derived identity of D06
  (username, display name, email, role), which is not stored, and the PRD and
  D06 both call the stored thing a member profile. The table stays `member`, as
  the backlog line spells it, through `@Table("member")`. The port is
  `MemberProfileRepository` in `domain` and its adapter
  `JdbcMemberProfileRepository` in `infra.persistence` — `<Aggregate>Repository`
  for the port, `Jdbc<Aggregate>Repository` for the adapter, mirroring
  `SecurityConfig` / `PersistenceConfig` for configuration classes. This is the
  first persistence port in the repository and no document states a scheme:
  propose the sentence for D02 in the PR body so the next aggregate is not a
  fresh decision.
- **`domain` gains four Spring Data annotations, so ArchUnit rule 1 must allow
  two more packages.** *Measured*: `@Table`, `@Id`, `@CreatedDate` and
  `@LastModifiedDate` fail the existing rule with four violations on
  `MemberProfile`. Decision: add `org.springframework.data.annotation..` and
  `org.springframework.data.relational.core.mapping..` to the allowed packages.
  D02 names `@Id`, `@Table` and `@MappedCollection` explicitly and D11 requires
  auditing, so the two auditing annotations are the mechanical consequence:
  propose the wording for D02 in the PR body.
- **The aggregate's timestamps are `Instant?` with a `null` default**, since a
  profile that has not been inserted yet has none and the adapter must be able
  to build one from three values. The columns are `not null` in SQL: the
  database is where the invariant lives. `MemberProfile.id` is non-null (D11).
- **`V001` creates no extension.** D03 says the first migration creates
  `unaccent` and `pg_trgm`; nothing in this task uses either, and `CLAUDE.md`
  refuses infrastructure before the task that needs it. Decision: `V001` creates
  the `member` table only, and the extensions arrive with the migration that
  introduces `search_text` and `search_vector`. The privilege point D03 makes
  (both extensions are trusted, so the owner user suffices) is unaffected.
  Propose the rewording of that sentence in the PR body.
- **The port exposes `insert` and `findByUsername`, not `update`.** D11 lists
  `insert` and `update` as the shape persistence ports take; nothing in this
  task or in T009 modifies a profile, and a method no test exercises is what
  `CLAUDE.md` forbids. `update` arrives with the first task that edits a profile
  (PRD §4.10, admin edits).
- **The lookup is `JdbcAggregateTemplate.findOne` with a `Query`**, *measured*,
  not hand-written SQL and not a `CrudRepository`: the same mapping as the
  insert, nothing to keep in step, and the D02/D11 ban on `save` stays trivially
  true. Hand-written SQL in `infra.persistence` is for the search and listing
  queries D02 mentions, which do not exist yet.
- **Every `@SpringBootTest` in the suite now needs the database.** *Measured*:
  Flyway runs once per Spring context, and the suite boots three
  (`MeControllerTest` and `SecurityConfigTest` share one, `ApiContractTest` has
  the `contract-test` profile, the repository test is the third). T005's
  criterion that the gate passes with `LIBRIS_DB_URL`, `LIBRIS_DB_USER` and
  `LIBRIS_DB_PASSWORD` unset stops being true with this task, and the defaults
  in `application.yaml` are what a laptop uses. Keep the repository test's
  annotations to `@SpringBootTest` and `@Transactional`: any extra annotation
  (`@ActiveProfiles`, `@AutoConfigureRestTestClient`, a `properties = [...]`)
  makes a fourth context and costs another boot. *Measured*: the whole `test`
  task takes about 50 s warm with the three contexts.
- **The duplicate username surfaces as `org.springframework.dao.DuplicateKeyException`**,
  *measured* — Spring translates it, and it is not wrapped in a
  `DbActionExecutionException`. Assert that type with `shouldThrow`, not a
  message.
- **detekt formatting on the new test classes**, *measured*: write
  ``class JdbcMemberProfileRepositoryTest @Autowired constructor(`` on a single
  line, as `MeControllerTest` does — putting `@Autowired` on its own line
  produces about thirty `Indentation` findings — and keep every line under 120
  characters, extracting an ArchUnit predicate into a local `val` where the
  fluent call would overflow.
- **Kover.** Coverage has no threshold (D07); `check` still runs
  `koverXmlReport` and must stay green.
- **The `images` job runs on this PR** and needs both test jobs green. The
  Dockerfile does not change, but the image now starts an application that
  wants a database: nothing to do here, since `deploy/` and the compose file are
  T008, and the container healthcheck is `/actuator/health`, which stays open.
