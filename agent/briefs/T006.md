# T006 — Backend persistence: the member table and its repository

**Backlog line:** Backend persistence: the member table and its repository.
Starter jdbc, `spring-boot-flyway` with `flyway-database-postgresql`, and the
PostgreSQL driver; datasource from `LIBRIS_DB_URL` / `LIBRIS_DB_USER` /
`LIBRIS_DB_PASSWORD`, migrated by Flyway, never by `ddl-auto` (D02, D08).
`V001__member.sql`: `id` uuid primary key, `username` unique and not null,
`display_name` not null; no other column (D11). `domain`: the member profile
aggregate, its `id` defaulted to a version 7 uuid from
`com.fasterxml.uuid:java-uuid-generator`, and its port exposing `insert` and a
lookup by username; no annotation (D02, D11). `infra.persistence`: the port
implementation over `JdbcClient`, one insert and one select, the row mapped by
the aggregate's constructor (D02). Nothing web changes: `/api/v1/me` still
answers the headers alone, and `api/openapi.yaml` is untouched. Tests: the
implementation against the PostgreSQL of D08 — insert then find by username,
the id a version 7 uuid, a second row with the same username refused — in a
transaction rolled back at the end (D07). ArchUnit: the domain rule gains the
uuid generator; new rules: `infra` packages never depend on each other, a port
declared in `domain` is implemented only in `infra` (D02); the `application`
rule arrives with T009.
**Serves:** PRD §2 (Libris creates a member profile on a user's first visit),
§4.10 (member profiles); decisions D02, D07, D08, D10, D11.

This is the repository's first database code: the first datasource, the first
migration, the first `infra.persistence` class and the first test that needs
the PostgreSQL of D08. Everything below marked *measured* was run on
2026-09-09 in a throwaway copy of `backend/` under `/tmp`, against the
sandbox's PostgreSQL 18, with JDK 25, Gradle 9.7.1 and Spring Boot 4.1.1;
twenty tests green in 1 min 3 s from `clean`. Nothing was left in the
repository, and the tables the spike created were dropped again, so the
implementer's first run starts on an empty database.

## Goal
When this task is done the backend owns a `member` table created by Flyway on
the database D08 gives it, and a port in `domain` that inserts a member profile
and finds it by username, implemented over `JdbcClient` in `infra.persistence`
and proved against the real PostgreSQL inside `./gradlew check`. It matters now
because T009 hangs first-visit creation on exactly this port, and because every
later aggregate copies the shape decided here: the id from the constructor, the
hand-written SQL, the row mapped by the constructor, the rolled-back
integration test.

Read `agent/PROGRESS.md`'s "T005 Backend authentication" entry first. Three
things carry over: the gate is recorded, so keep `cd backend && ./gradlew check`
plain and last in its command; `detekt` runs on the test sources too, but only
inside `check`; and a Spring test class takes its beans through an `@Autowired`
constructor (D10).

## Test plan
Two new test classes, both part of `./gradlew check`. Follow the `tdd` skill:
one test at a time, red first, commit the cycle before mutating anything.

1. `src/test/kotlin/fr/amory/libris/domain/MemberProfileTest.kt` — plain JUnit,
   no Spring. One test: a new profile gets a version 7 uuid. Red because the
   class does not exist. Green with the aggregate and the generator; the domain
   ArchUnit rule goes red in the same cycle (*measured*, four violations), which
   is what motivates amending it.
2. `src/test/kotlin/fr/amory/libris/infra/persistence/JdbcMemberProfileRepositoryTest.kt`
   — `@SpringBootTest` and `@Transactional`, an `@Autowired` constructor taking
   the **port** (`MemberProfileRepository`), not the implementation, so the test
   reads as the use case will. First test: insert then find by username. Red
   first because there is no bean, then because there is no table. That single
   cycle brings the four dependencies, the datasource properties, the migration,
   the port and the adapter — it is the biggest step of the task; take the
   two smaller ones (unknown username, duplicate username) one at a time after
   it.
3. `ArchitectureTest` — one cycle per rule, each written from its red step:
   amend the domain rule, then add the `infra` slices rule and the port rule.
   For the two new rules the red step is a deliberate violation that is reverted
   once seen (see *Risks and decisions* for the exact violations and messages).

Green means `cd backend && ./gradlew check`, nothing piped or chained after it.
While working, `./gradlew test --tests '*JdbcMemberProfileRepositoryTest'` is
about 30 s against about 60 s for the whole gate; the partial run proves nothing
to the sandbox.

```kotlin
// domain/MemberProfile.kt
private val uuids = Generators.timeBasedEpochGenerator()

data class MemberProfile(
    val username: String,
    val displayName: String,
    val id: UUID = uuids.generate(),
)

interface MemberProfileRepository {
    fun insert(profile: MemberProfile)

    fun findByUsername(username: String): MemberProfile?
}
```

```kotlin
// infra/persistence/JdbcMemberProfileRepository.kt
@Repository
class JdbcMemberProfileRepository(private val jdbc: JdbcClient) : MemberProfileRepository {
    override fun insert(profile: MemberProfile) {
        jdbc.sql("insert into member (id, username, display_name) values (:id, :username, :displayName)")
            .param("id", profile.id)
            .param("username", profile.username)
            .param("displayName", profile.displayName)
            .update()
    }

    override fun findByUsername(username: String): MemberProfile? =
        jdbc.sql("select id, username, display_name from member where username = :username")
            .param("username", username)
            .query { rs, _ ->
                MemberProfile(
                    rs.getString("username"),
                    rs.getString("display_name"),
                    rs.getObject("id", UUID::class.java),
                )
            }
            .optional()
            .orElse(null)
}
```

## Risks and decisions
- **Dependencies.** *Measured*: these five, and no more, make the gate pass —
  `implementation("org.springframework.boot:spring-boot-starter-jdbc")`,
  `implementation("org.springframework.boot:spring-boot-flyway")`,
  `implementation(libs.java.uuid.generator)`,
  `runtimeOnly("org.flywaydb:flyway-database-postgresql")`,
  `runtimeOnly("org.postgresql:postgresql")`. The four Spring and Flyway ones
  are BOM-managed and take no catalog entry (T003 and T005 precedent);
  *measured* resolutions: `spring-boot-starter-jdbc` 4.1.1,
  `spring-boot-flyway` 4.1.1, `flyway-core` and `flyway-database-postgresql`
  12.4.0, `postgresql` 42.7.13. `com.fasterxml.uuid:java-uuid-generator` is
  third-party, so it is pinned in `gradle/libs.versions.toml` (D10) at **5.1.0**,
  the latest on Maven Central on 2026-09-09. In Spring Boot 4 the Flyway
  auto-configuration lives in the module `spring-boot-flyway`, not in a
  starter; the driver and the Flyway PostgreSQL support are needed at runtime
  only, and `runtimeOnly` keeps them off the compile classpath so no production
  class can import them by accident.
- **The aggregate is `MemberProfile`, not `Member`.** `domain/Member.kt`
  already holds the identity T005 reads from the request headers — username,
  display name, email and role, none of it stored. This task adds the stored
  profile — id, username, display name. They are two different things and both
  survive T009, so they keep two names, and the PRD's own words ("member
  profile", §2 and §4.10) name the new one. The table stays `member` as the
  backlog line and D11 (singular, snake_case) ask.
- **Port `MemberProfileRepository`, implementation `JdbcMemberProfileRepository`.**
  D02 names the package `infra.persistence` and D11 speaks of "persistence
  ports"; `Repository` is the word both use, and the `Jdbc` prefix says which
  adapter it is. No document states the scheme, so this run picks it and the
  PR body **must propose the sentence for D02** — "a persistence port is named
  `<Aggregate>Repository`, its adapter `Jdbc<Aggregate>Repository`" — the way
  T005 proposed D07's sentence about test class names. A future run must not
  have to guess again.
- **The port lives in `domain/MemberProfile.kt`, beside its aggregate.** Not a
  new convention: `domain/Member.kt` already holds `Role` and `Member`, and
  `infra/web/SecurityConfig.kt` holds the filter, the principal and the chain,
  so this repository already puts closely related types in the file named after
  the main one. Say it in the PR body; if the reviewer prefers one file per
  port, the move is a rename.
- **The id is the last constructor parameter, defaulted.** D11 asks for the
  uuid to come from the aggregate's constructor as the default of its `id`
  parameter; putting it last lets a new profile be built positionally
  (`MemberProfile("tophe", "Tophe")`) while a row read back passes all three,
  which is exactly the two call sites this task has.
- **One generator, once, at file level.** `private val uuids =
  Generators.timeBasedEpochGenerator()` in `MemberProfile.kt`. *Measured*:
  `generate().version()` is 7, and detekt is clean on it. A generator built per
  call would throw away the sequence the generator keeps.
- **The domain ArchUnit rule gains `com.fasterxml.uuid..`.** *Measured*, the red
  step of cycle 1, four violations, the first being
  `Constructor <fr.amory.libris.domain.MemberProfile.<init>(…)> calls method
  <com.fasterxml.uuid.impl.TimeBasedEpochGenerator.generate()> in
  (MemberProfile.kt:11)`. D02 already allows "the uuid generator of D11", so the
  rule is being made true, not loosened.
- **The two new ArchUnit rules bite.** *Measured* violations and messages, to
  reproduce and revert:
  - a class in `domain` implementing the port gives
    `Rule 'no classes that reside outside of package 'fr.amory.libris.infra..'
    should implement a port declared in the domain' was violated (1 times):
    Class <fr.amory.libris.domain.InMemoryMemberProfiles> does implement a port
    declared in the domain`. Without the ``.`as`("a port declared in the
    domain")`` description the message reads "does implement reside in a package
    '..domain..' and interfaces", which is why the predicate is described.
  - injecting `JdbcMemberProfileRepository` into `MeController` gives
    `Rule 'slices matching 'fr.amory.libris.infra.(*)..' should not depend on
    each other' was violated (1 times): Slice web depends on Slice persistence`.
  `@AnalyzeClasses` already carries `ImportOption.DoNotIncludeTests`, so a fake
  port in a test class is not a violation — which is what lets T009 write one.
- **The failed insert poisons the transaction; assert nothing after it.**
  *Measured*: a `findByUsername` after the duplicate insert fails with
  `SQL state [25P02] … current transaction is aborted, commands ignored until
  end of transaction block`. The unique constraint refusing the second row is
  the whole assertion; the rollback at the end of the test still works
  (*measured*: the table is empty afterwards).
- **How a test gets the database, and how it cleans up.** `@SpringBootTest` with
  `@Transactional` on the class: Spring rolls the transaction back after each
  test, so nothing is left behind and no truncation is needed (D07). Flyway runs
  once per Spring context against the given database and creates
  `flyway_schema_history` and `member` there; D08 forbids dropping or recreating
  the database, and nothing here does. HTTP-level seeding — Contracteer's
  truncate-and-seed — is T009's, when a row must survive the request.
- **A migration edited after it has run fails the next run.** Flyway records a
  checksum; changing `V001__member.sql` after the gate has applied it gives a
  validation failure on the sandbox's long-lived database. Recover by dropping
  `member` and `flyway_schema_history` (the two tables this task owns, not the
  database — D08), then rerunning. Once the PR is merged the file is frozen
  (D11).
- **The gate now needs the database.** T005's criterion that `check` passes with
  the three variables unset is dead as of this task: *measured*, without them
  the context fails to start with `Unable to obtain connection from database:
  Connection to localhost:5432 refused` and every `@SpringBootTest` class fails.
  The sandbox, CI (`services: postgres` in the `backend` job) and the human's
  compose all provide one; `backend/README.md` must now say so.
- **Three Spring contexts instead of two.** `MeControllerTest` and
  `SecurityConfigTest` share one, `ApiContractTest` has its own
  (`contract-test` profile), and the repository test adds a third because it
  boots no web environment. *Measured*: the whole build (compile, 20 tests,
  detekt on both source sets, Kover) is 1 min 3 s from `clean`, against about
  42 s before — the extra context and the Flyway run are the difference. Do not
  chase it: sharing a context by copying `@AutoConfigureRestTestClient` onto a
  test that never makes an HTTP call would be wiring for its own sake.
- **detekt on the test sources, *measured* on the spike.** Adding the fifth
  package to the domain rule pushes that line past 120 characters: wrap the
  arguments one per line, or `MaximumLineLength`, `MaxLineLength` and
  `ArgumentListWrapping` all fire. New imports must stay in lexicographic order
  (`ImportOrdering`). And `!!` fails the same run, so a nullable assertion in a
  test is `shouldBeNull()` or `shouldNotBeNull()`, never `!!`.
- **`@Repository` on the adapter.** It is the stereotype that makes the bean and
  the word D02 uses for the package. *Measured*: the `DuplicateKeyException` the
  duplicate test expects arrives through `JdbcClient`'s own exception
  translation, so the annotation is a marker, not a mechanism.
- **`text` columns, not `varchar(n)`.** PostgreSQL treats them identically and a
  length nobody has specified would be a product rule invented here. Validation
  lives in the domain when the PRD gives it a rule.
- **Secrets.** The datasource block carries the D08 defaults
  (`libris`/`libris`), which are the throwaway sandbox and CI credentials, not a
  production secret; production passes real values by environment (D09).
  *Measured*: `gitleaks dir` finds no leak in the changed sources, so the
  `guardrails` job stays green.
- **Kover.** Coverage has no threshold (D07); `check` still runs
  `koverXmlReport` and must stay green.
