# T006 — Backend persistence: the reader entity and its repository

**Backlog line:** Backend persistence: the reader entity and its repository.
Starter jdbc, `spring-boot-flyway` with `flyway-database-postgresql`, and the
PostgreSQL driver; datasource from `LIBRIS_DB_URL` / `LIBRIS_DB_USER` /
`LIBRIS_DB_PASSWORD`, migrated by Flyway, never by `ddl-auto` (D02, D08).
`V001__reader.sql`: `id` uuid primary key, `username` unique and not null,
`email` not null, `display_name` not null; no other column (D11). `domain`: the
one entity for a person, `Reader(id, username, email, displayName)`, its `id`
defaulted to a version 7 uuid from `com.fasterxml.uuid:java-uuid-generator`, no
annotation (D02, D11, D06); it replaces T005's `Member` class: the filter
builds a `Reader` from the headers (its id not stored until T009) and maps the
groups to the Spring authorities `ROLE_READER` and `ROLE_ADMIN`; the T005
principal class carries the reader and the authorities; T005's `Role` enum
survives only as the JSON type of the `/me` response in `infra.web`, derived
from the authorities. Contract edit, decided with Tophe on 2026-09-09 (D04):
the schema `CurrentMember` is renamed `CurrentReader`, its `role` enum becomes
`[READER, ADMIN]`, the operation summary becomes "The reader making the
request, as Authelia describes them" and the response description "The reader's
identity and role"; nothing else in `api/openapi.yaml` changes, and
`ApiContractTest` going red on the role value is the task's first red step. The
port `ReaderRepository` exposes `insert` and `findByUsername`;
`infra.persistence`: `JdbcReaderRepository` over `JdbcClient`, one insert and
one select, the row mapped by the entity's constructor (D02). Tests: the
repository against the PostgreSQL of D08 — insert then find by username returns
an equal reader, an unknown username finds none, a second row with the same
username refused — in a transaction rolled back at the end (D07); the T005
tests keep passing. ArchUnit: the domain rule gains the uuid generator; new
rules: `infra` packages never depend on each other, a port declared in `domain`
is implemented only in `infra` (D02); the `application` rule arrives with T009.

**Serves:** PRD §2 (Admin and Reader), §4.10 (accounts live in Authelia, Libris
keeps a reader profile); decisions D02, D03, D04, D06, D07, D08, D10, D11.

## Goal
When this task is done the backend has a database: the given PostgreSQL of D08
is migrated by Flyway at startup, `reader` is its first table, and
`JdbcReaderRepository` writes and reads a row over `JdbcClient`. In the same
run the person the backend already knows from the Authelia headers becomes the
`Reader` of D06 — one entity, no role field, the role an authority — and the
contract says `CurrentReader` with `[READER, ADMIN]`. It matters now because
T009 hangs the find-or-create use case on this repository and T007's home view
greets the reader by name; and because this is the run that turns D08's
"the environment is given" from a sentence into part of the gate.

Read `agent/PROGRESS.md`'s "T005 preparation" and "T005 Backend
authentication" entries first. Four things carry over: the gate is recorded, so
keep `cd backend && ./gradlew check` plain and last in its command; detekt runs
on the test sources inside `check` and `VariableNaming` rejects a backticked
`val`, so ArchUnit rules stay ``@ArchTest fun `name`(classes)``; `ReturnCount`
allows two returns; and `git checkout <file>` after a mutation reverts to the
last commit, so commit the cycle before mutating.

## Test plan
One new test class and three existing ones changed, all part of
`./gradlew check`. Follow the `tdd` skill: one test at a time, red first.

1. **The contract first (D04's order of work).** Apply the four-line edit to
   `api/openapi.yaml`, then run `ApiContractTest`: the application still
   answers `"role":"MEMBER"` and the response no longer satisfies
   `enum: [READER, ADMIN]`. That failure is the task's first red step. Green it
   by renaming the enum and the response DTO in `infra.web` — `Role { READER,
   ADMIN }`, `CurrentReaderResponse` — and by changing the four `MeControllerTest`
   expectations from `MEMBER` to `READER` in the same cycle, since they assert
   the same value.
2. **`MeControllerTest`** keeps its four cases and its `Test` names change
   member to reader. Nothing about its HTTP shape changes; it is the test that
   proves the role still comes out right once it is derived from the
   authorities instead of read off a field.
3. **`JdbcReaderRepositoryTest`**, new, in
   `src/test/kotlin/fr/amory/libris/infra/persistence/`. `@SpringBootTest`
   (no web environment: nothing here goes over HTTP) and `@Transactional`, an
   `@Autowired` constructor taking `JdbcReaderRepository`. Three cycles, in
   this order: insert-then-find (red on the missing class, then on the missing
   table, then green), unknown username, duplicate username. This is the class
   that drives the dependencies, the datasource properties and
   `V001__reader.sql` into existence.
4. **`ArchitectureTest`** gains its two new rules last, once `infra.persistence`
   and `ReaderRepository` exist to check. The domain rule's allowed-package
   list gains `com.fasterxml.uuid..` in the cycle that introduces the generator
   — it goes red on its own, no throwaway edit needed (measured below).
5. **`SecurityConfigTest`** is not touched: the refusals are about headers, not
   about who the principal is. If a change there seems necessary, something
   about the filter changed that this task did not ask for.

Green means `cd backend && ./gradlew check`, nothing piped or chained after it.
Partial runs (`./gradlew test --tests '*JdbcReaderRepositoryTest*'`) are fine
while working and prove nothing to the sandbox.

```kotlin
// domain/Reader.kt — the id first and defaulted, so every call site names its
// arguments; that is what D11's "the default of its id parameter" costs.
data class Reader(
    val id: UUID = Generators.timeBasedEpochGenerator().generate(),
    val username: String,
    val email: String,
    val displayName: String,
)

// domain/ReaderRepository.kt
interface ReaderRepository {
    fun insert(reader: Reader)
    fun findByUsername(username: String): Reader?
}

// infra/persistence/JdbcReaderRepository.kt
@Repository
class JdbcReaderRepository(private val jdbcClient: JdbcClient) : ReaderRepository {
    override fun insert(reader: Reader) {
        jdbcClient
            .sql("insert into reader (id, username, email, display_name) values (:id, :username, :email, :displayName)")
            .param("id", reader.id)
            …
            .update()
    }

    override fun findByUsername(username: String): Reader? =
        jdbcClient
            .sql("select id, username, email, display_name from reader where username = :username")
            .param("username", username)
            .query { rs, _ -> Reader(id = rs.getObject("id", UUID::class.java), username = rs.getString("username"), …) }
            .optional()
            .orElse(null)
}
```

const val ADMIN_AUTHORITY = "ROLE_ADMIN"
const val READER_AUTHORITY = "ROLE_READER"

    val reader: Reader,
    private val authorities: Collection<GrantedAuthority>,

    override fun getPassword(): String? = null
    override fun getUsername(): String = reader.username

// infra/web/MeController.kt
enum class Role { READER, ADMIN }

@GetMapping("/api/v1/me")
fun me(@AuthenticationPrincipal principal: ReaderPrincipal): CurrentReaderResponse =
    CurrentReaderResponse(…, role = roleOf(principal.authorities))

private fun roleOf(authorities: Collection<GrantedAuthority>): Role =
    if (authorities.any { it.authority == ADMIN_AUTHORITY }) Role.ADMIN else Role.READER

## Risks and decisions
Everything marked *measured* was run on 2026-09-09 in a throwaway copy of
`backend/` and `api/` against the sandbox PostgreSQL; nothing was left in the
repository.

- **Dependencies.** *Measured*: these four, and no more, make the nineteen
  tests pass —
  `implementation("org.springframework.boot:spring-boot-starter-jdbc")`,
  `implementation("org.springframework.boot:spring-boot-flyway")`,
  `implementation(libs.java.uuid.generator)`,
  `runtimeOnly("org.flywaydb:flyway-database-postgresql")` and
  `runtimeOnly("org.postgresql:postgresql")`. The three Spring/Flyway/pgjdbc
  ones are managed by the Spring Boot 4.1.1 BOM (Flyway 12.4.0, pgjdbc
  42.7.13) and take no catalog entry, as T005 did for the security starter;
  `com.fasterxml.uuid:java-uuid-generator` is not in the BOM and is pinned in
  `gradle/libs.versions.toml` at **5.1.0**, the latest on Maven Central on
  2026-09-09 (D10).
- **`flyway-database-postgresql` is not optional.** *Measured*: without it
  every test that needs the context fails at startup with
  `FlywayException: Unsupported Database: PostgreSQL 18.6`. Flyway 10+ ships
  each database in its own module. `runtimeOnly` is enough: no Kotlin source
  names a Flyway type.
- **The datasource lives in `application.yaml` with D08's defaults.** Decision:
  `${LIBRIS_DB_URL:jdbc:postgresql://localhost:5432/libris}` and the two
  others, exactly the defaults D08 states, so a human with the compose
  PostgreSQL needs no environment at all and the sandbox and CI override them.
  Rejected: a `application-test.yaml`, which would give the tests a second
  source of truth for the same three values.
- **The gate now requires a database.** This is a real change: T005's brief
  made "the gate passes with `LIBRIS_DB_*` unset" a criterion, and that stops
  being true here. All four `@SpringBootTest` classes boot a context with a
  Hikari pool and Flyway, including the three that never touch a table. Say it
  in the PR body; it is what D08 asks for and what CI already provides (the
  `backend` job has declared a `postgres:18-alpine` service and the three
  `LIBRIS_DB_*` variables since the loop was bootstrapped).
- **Flyway never drops anything.** *Measured*: `flyway_schema_history` and
  `reader` survive between runs and the second run is a no-op, which is what
  D08 requires ("tests migrate the given database and never drop or recreate
  it"). The sandbox PostgreSQL is on tmpfs and starts empty each iteration; CI
  starts a fresh service container. No `clean`, no `cleanDisabled: false`.
- **The rolled-back transaction is what keeps the table empty**, per D07.
  *Measured*: `@SpringBootTest` + `@Transactional` on the class rolls back
  after each test, including the one whose insert raised
  `DuplicateKeyException` — the exception marks the transaction rollback-only,
  which is exactly what the test framework was going to do anyway. Test classes
  do not run in parallel (D07), so the three cases cannot collide.
- **`JdbcReaderRepositoryTest` gets no web environment.** *Measured*: it is a
  fourth Spring context, so `check` grows from about 42 s to about 60 s. It
  could be folded into `MeControllerTest`'s context by copying that class's
  `webEnvironment` and `@AutoConfigureRestTestClient`, but a persistence test
  that starts Tomcat to reach a table is a lie about what it needs. Decision:
  plain `@SpringBootTest`, and the gate-speed follow-up in `agent/TASKS.md`
  stands.
- **The test injects the adapter, not the port.** `JdbcReaderRepository` is
  what this test exercises and what D07 names it after; there is one
  implementation and injecting the interface would only hide which one ran.
- **`Reader` has no `role`.** D06 is explicit: roles are Spring authorities,
  never stored, and the table has four columns. So the role cannot come off the
  entity any more; it is derived from the authorities at the one place that
  serialises it, `MeController`. That is why T005's `Role` enum moves to
  `infra.web`: it is a JSON type now, not a domain concept.
- **The principal carries the authorities, so the filter builds the
  `UserDetails` itself.** *Measured*: `PreAuthenticatedAuthenticationProvider`
  replaces the token's principal with whatever its user-details service
  returns, and the service sees only the token — not the request, not the
  groups. Returning `ReaderPrincipal` straight from
  `getPreAuthenticatedPrincipal` and casting it through in the service is the
  shortest thing that keeps the authorities. T009 deletes `ReaderPrincipal` and
  makes the `Reader` entity the principal, as D06 describes; do not try to get
  there early — without a stored id there is nothing to be the principal *of*.
- **`ADMIN_AUTHORITY` and `READER_AUTHORITY` are file-level `const val` in
  `SecurityConfig.kt`**, read by `MeController` in the same package. The string
  `ROLE_ADMIN` written twice in two files is the kind of drift the role test
  would not catch, since both sides would be wrong together.
- **The id ordering costs named arguments.** *Measured*: `Reader(id = …,
  username, email, displayName)` with only `id` defaulted compiles, and every
  call site must name its arguments. That is the backlog line's order and D11's
  rule; it also matches the column order of `V001__reader.sql`. Accept the
  named arguments rather than moving `id` last.
- **`findByUsername` returns `Reader?`.** *Measured*:
  `JdbcClient…query { … }.optional().orElse(null)` is the shape that gives a
  nullable without throwing on the empty result. `.single()` throws
  `EmptyResultDataAccessException`, which would make "no such reader" an
  exception — wrong for a lookup T009 calls on every request.
- **Uniqueness is the database's job.** The port has no `existsByUsername` and
  the adapter does no pre-check: `username text not null unique` is what
  refuses the second row, and `DuplicateKeyException` is what Spring's
  exception translation makes of it. T009's two-simultaneous-first-visits case
  depends on exactly that; a check-then-insert in Kotlin would pass its own
  test and lose the race.
- **The two new ArchUnit rules are checkable.** *Measured*, each by a
  deliberate violation reverted afterwards:
  - a field of type `fr.amory.libris.infra.web.Role` on `JdbcReaderRepository`
    gives `Rule 'slices matching 'fr.amory.libris.infra.(*)..' should not
    depend on each other' was violated (1 times): Slice persistence depends on
    Slice web`;
  - a `class InMemoryReaderRepository : ReaderRepository` in `domain` gives
    `Rule 'classes that implement reside in a package '..domain..' should
    reside in a package '..infra..'' was violated (1 times)`.
  Both are the mutation check of the acceptance criteria. Paste the two lines
  in the PR body.
- **The domain rule goes red by itself.** *Measured*: the moment `Reader` calls
  `Generators.timeBasedEpochGenerator()`, T005's rule fails with two violations
  naming `com.fasterxml.uuid.Generators` and
  `com.fasterxml.uuid.impl.TimeBasedEpochGenerator`. Adding
  `com.fasterxml.uuid..` to the allowed packages is the green step of that
  cycle — no throwaway edit is needed, and the rule's `Test` name changes with
  it.
- **The `application` rule and the `infra` -> `application` direction are not
  written here.** There is no `application` package yet; an ArchUnit rule no
  class can violate passes forever and hides its own removal (T005's brief,
  same reasoning). It arrives with T009, as the backlog line says.
- **`@Repository` on the adapter.** A Spring stereotype in `infra` is what D02
  allows and what turns the PostgreSQL error into `DuplicateKeyException`
  through Spring's exception translation. The domain stays annotation-free.
- **The contract edit is Tophe's, already decided.** Apply exactly the four
  lines the backlog line spells out. *Measured*: with those four lines the
  Contracteer verifier still generates and passes one case, and the mock still
  answers — the document stays OpenAPI 3.0.3 and gains no `$ref` Contracteer
  4.0.0 cannot resolve (the 3.1 gap in `agent/PROGRESS.md`).
- **`ApiContractTest`'s fixed reader.** Its constants and nested class mention
  a member; rename them with the rest. The fixed identity itself
  (`contracteer` / `family`) does not change: it is in no group, so it is a
  plain `READER`, which is what the enum's first value now is.
- **detekt.** *Measured*: no new finding on either source set with the shapes
  above, and no `@Suppress` anywhere. Watch `ReturnCount` if the row mapper is
  written with early returns, and keep ArchUnit rules as backticked *functions*
  (`VariableNaming` rejects a backticked `val`, `agent/PROGRESS.md`).
- **Kover.** Coverage has no threshold (D07); `check` still runs
  `koverXmlReport` and must stay green.
- **The `images` job runs on this PR** and needs both test jobs green. Nothing
  here changes a Dockerfile, but the backend image now contains a Flyway
  migration: its first startup in production will create the table, which is
  what T008's deploy expects.
