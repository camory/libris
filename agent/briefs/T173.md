## Goal
At the end of a search's rows the screen asks Libris for the next page of
the same query, its rows following the first, two skeleton rows standing
under the last while it comes, and nothing more once a page names no next.
A search that finds more than fifty editions then lists them all, as the
catalogue does.

- D05 — `useSearchCatalogue` holds the query and the cursor and decides

- D10 — the composable's functions read as the sentence, `search(text)`

- D11 — keyset paging: the next page is asked with `after` the `next` of

- U05 — *Loading more*: the catalogue's two skeleton rows under the last

## Risks and decisions
**A second verb, `searchMore()`, beside `search(text)`.** The catalogue
pages by calling `browse()` again, but `search(text)` called again with
the same text must start that search afresh (the search key, the pause),
so it cannot also mean "the next page". The composable keeps the query and
the cursor; the view says only "more". Rejected: `search(text)` continuing
when the text is unchanged (the search key would page); the view passing
the query and the cursor (the cursor is the composable's, D05).

**`loadingMore` is a field of `found` and `near`, not a status.** A near
search loading its next page must still say the sentence and the label,
so the paging is orthogonal to which answer is shown. Rejected: a status
`loadingMore` (it would have to carry `near` and `query` again); an
optional field (the existing whole-state assertions would not say it).

**The view chooses the list the observer grows.** Which list is drawn is
the view's; so is which composable it asks: `searchMore()` while the
search's rows are drawn, `browse()` otherwise. Each composable keeps its
own guard. Rejected: calling both and letting each guard (the catalogue
would load pages nobody sees, and draw its skeleton under the search).

**The skeleton follows the list shown**, which answers half of the
`agent/PROPOSED.md` item found on T169's review: the catalogue's
`loadingMore` rows no longer stand under a search's rows. Its other half,
the catalogue's error sentence there, is a failure's and stays for T175.

**The fetch client's duplication stays.** T169's entry hoped T173 would
merge `browse` and `search` in `FetchCatalogueApi`; no test of this task
touches the client, so the implementer moves that suggestion to
`agent/PROPOSED.md` instead.
