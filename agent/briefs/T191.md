## Risks and decisions
**A `const val` moves with the `val`s.** The entry says "the top-level
fixtures" of the four files, and the backend gotcha says a file that moves
its fixtures moves all of them; `HoldEditionTest` and
`JdbcCatalogueEditionsTest` keep their consts below the class.
`ONE_PIECE` therefore moves in `LookupIsbnForReaderTest` and
`AwaitedCoverTest`. Rejected: consts kept on top as in
`JdbcEditionRepositoryTest` (an older file, not a model by that gotcha).

**The order is the order reached, not the order written.** D10's stepdown
rule places each fixture below its first user, in the order reached, and
the reviewer sent T130 back for a fixture placed by kind. That reorders
`LookupEditionByIsbnTest`: `ROMANCE_DAWN_COVER` (second case) comes
before `NO_COVER` (fourth). The gotcha's "in the order written" guards
initialisation: no fixture of these files reads another `val` (only
`ROMANCE_DAWN` reads `ONE_PIECE`, a `const` inlined at compile time and
still above it), so the reached order is safe. Rejected: the order written
(contradicts the stepdown rule where it differs).

**The deletion is proven by a mutation, not by trust.** While planning,
dropping `TypeMismatchException::class` from the advice's handler made 8
of `ApiContractTest`'s 50 cases fail, the seven `auto: path 'id' type
mismatch` cases and `GET /api/v1/books -> 400 (auto: query 'after' type
mismatch)`, the add's among them; `ProblemAdviceTest`'s remaining case
cannot see it. The implementer runs the same mutation so the PR shows the
proof. Rejected: deleting on the entry's word alone.

**Five steps, one per move.** Each move touches one file and is one
commit a reviewer reads at a glance; the deletion precedes `TOPHE`'s move
so that each commit of `ProblemAdviceTest` does one thing. Rejected: one
commit for the four files (mixes a deletion with four moves).
