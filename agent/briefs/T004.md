# T004 — Frontend image

**Backlog line:** Frontend image. Multi-stage `frontend/Dockerfile`: Node build
taking `VERSION`, nginx serving `dist/` with SPA fallback; `index.html` and the
service worker `no-cache`, hashed assets `immutable`; OCI labels (D09). The
revision shows in a footer, with a component test. Verified as T003.
**Serves:** PRD §4.8 (installable PWA, so the service worker must never be
served stale), §5 (operability: deployable behind Traefik); decisions D01, D05,
D08, D09 (packaging and version exposure), D10.

The `images` job of `.github/workflows/ci.yml` already builds every side that
has a `Dockerfile`, with `--build-arg VERSION=sha-<short sha>` and the four OCI
labels. It printed `frontend/Dockerfile not present yet` on T003's pull
request; this task is what makes it build the second image. No human
precondition is missing.

## Goal
When this task is done, `frontend/Dockerfile` builds a runnable nginx image of
the Vue application from a clean checkout, and the built application shows in a
footer the revision it was built with. It matters now because T007's compose
pulls that image by tag, and Phase 0 ends with Tophe checking from a phone that
the footer revision matches `git rev-parse v0.1.0` — the frontend half of the
claim `/actuator/info` makes on the backend.

Read `agent/PROGRESS.md`'s T002 and T003 entries first. Four things carry over:
the gate is recorded, so keep `npm test` plain and last in its command; only
the frontend changes here, so the frontend gate is the only one that must be
green on this tree; a `.gitignore` line is added only when a real run proves a
file is left untracked; the tree is committed in Prettier's default style, so
run `npm run format` before committing (nothing in the gate checks formatting).

## Test plan
One spec ships: `src/ui/components/AppFooter.spec.ts`, next to the component it
exercises, as `HomeView.spec.ts` sits next to `HomeView.vue`. Write it first;
it fails on the missing `AppFooter.vue`. It mounts the component with
`revision: "sha-abc1234"` and asserts the text of the rendered `footer`.

What it proves: the footer is a presentational component that displays the
revision it is given (D05 rule 4: components take props in, no API calls, no
environment reads). What it does not prove: that the build-time version reaches
it — criteria 3 and 4 cover that by grepping the built bundle, and the deployed
image is where the whole chain is first true at once.

No spec is written for `App.vue`. Mounting it needs the router and the i18n
plugins to render one line of wiring, and D07 would call the result a wiring
test; the two `npm run build` greps are the honest check of that line.

Order of work:
1. `AppFooter.spec.ts` → red (`Failed to resolve import … AppFooter.vue`).
2. `AppFooter.vue` → green.
3. `App.vue` renders the footer with the version from the environment.
4. `npm test` plain → the gate, exit 0.
5. The two build greps of criteria 3 and 4.
6. `npm run format`, then `Dockerfile`, `nginx.conf`, `.dockerignore`,
   `README.md`, read once against criteria 5 to 7.
7. Open the PR, then watch the `images` job and paste its conclusion.

Green means `cd frontend && npm test`, nothing piped or chained after it. The
backend is untouched, so `./gradlew check` is not required on this tree.

## Risks and decisions
- **Measured on 2026-09-08 in a throwaway copy of `frontend/`** (Node 24.20.0,
  npm 11.19.0, Vite 8.2.2, vite-plugin-pwa 1.3.0), so the implementer does not
  have to rediscover it:
  - `npm run build` writes exactly: `dist/index.html`,
    `dist/assets/index-<hash>.js`, `dist/assets/index-<hash>.css`,
    `dist/manifest.webmanifest`, `dist/registerSW.js`, `dist/sw.js`,
    `dist/workbox-<hash>.js`, `dist/pwa-192x192.png`, `dist/pwa-512x512.png`.
    Those names are what `nginx.conf` keys on: everything hashed is under
    `/assets/` except `workbox-<hash>.js`, and `sw.js` and `registerSW.js` are
    not hashed, which is exactly why D09 wants them uncached.
  - `const revision = import.meta.env.VITE_APP_VERSION ?? "dev"` passes both
    `vue-tsc --noEmit` and `eslint .`: Vite's own `ImportMetaEnv` carries a
    string index signature, so no `env.d.ts` and no `any` annotation is needed,
    and the `no-explicit-any` rule that T002 recorded as a gate failure is not
    triggered.
  - `VITE_APP_VERSION=sha-abc1234 npm run build` inlines the literal into
    `dist/assets/index-<hash>.js`; a plain build inlines the `dev` fallback
    (`grep -o 'revision:[^,}]*'` shows ``revision:Yt(`dev`)``). The `??` is
    load-bearing: Vite replaces an unset `import.meta.env.VITE_*` with
    `undefined`, and a footer reading `undefined` would be a worse bug than one
    reading `dev`.
- **How the version reaches the bundle.** Decision: the `VITE_APP_VERSION`
  environment variable, Vite's own mechanism — only `VITE_`-prefixed variables
  are exposed to client code, and the `VERSION` build argument the CI job
  already passes is assigned to it in the Dockerfile. Rejected: a `define:`
  entry in `vite.config.ts` reading `process.env.VERSION`, which would need a
  `declare const` in a new `.d.ts` file to typecheck and invents a convention
  where Vite has one. The `dev` default matches the backend's `-Pversion`
  default, so the two sides say the same word when built by hand.
- **Where the footer lives.** `src/ui/components/AppFooter.vue`, flat under
  `components/`: D05 gives each *view* its own folder and says nothing of the
  kind for components, so flat is the layout the document already implies.
  The name is `AppFooter`, not `Footer`, because `vue/multi-word-component-names`
  is part of `eslint-plugin-vue`'s essential ruleset that `npm test` runs.
  `App.vue` (the `ui-shell` element) may import a `ui-components` element:
  that policy already exists in `eslint.config.ts` and needs no edit.
- **The footer reads no environment itself.** `App.vue` reads
  `import.meta.env` and passes a prop, so the component stays presentational
  (D05) and its spec is deterministic — under Vitest no `VITE_APP_VERSION` is
  set, and a component reading it directly would assert `"dev"` forever.
- **The footer shows the revision and no French label**, so `src/ui/i18n.ts` is
  untouched. D10 wants UI *text* in French; a build revision is an identifier,
  not prose, and what Tophe compares to `git rev-parse` on a phone is the bare
  string. If a label is wanted later it is one i18n message and a one-line
  change; do not add it here on a guess.
- **Base images.** `node:24.20.0-trixie-slim` for the build stage —
  the Node major of `.node-version` (24) pinned to the patch the sandbox itself
  runs, glibc like the machine where `package-lock.json` was resolved — and
  `nginx:1.30.4-alpine3.24` for the runtime. Both are published for linux/amd64
  (checked on Docker Hub, 2026-09-08). `1.30.4-alpine3.24` is nginx's *stable*
  branch: its digest is the one `stable-alpine` points at, while
  `1.31.5-alpine3.24` is mainline, and D10 asks for the latest stable, pinned,
  with upgrades as their own task. Full patch tags rather than digests, as
  T003 decided for Temurin.
- **`npm ci` needs the dev dependencies.** Vite, `vue-tsc` and the plugins are
  all in `devDependencies`; `--omit=dev` (or a `NODE_ENV=production` inherited
  from somewhere) would break `npm run build` with a missing-module error. The
  official Node images set no `NODE_ENV`, so a plain `npm ci` is correct — but
  do not "optimise" it later.
- **One `COPY . .` guarded by `.dockerignore`**, not the usual copy-manifests-
  then-copy-sources split. T003 recorded why: the `images` job configures no
  buildx cache, so nothing is reused between builds and the split would only
  duplicate a line. `npm ci` and `npm run build` stay separate `RUN` lines
  because their failures read differently.
- **`ARG VERSION` sits after `COPY . .` and `RUN npm ci`** in the build stage:
  an `ARG` invalidates every layer below it, and the version changes on every
  commit while the dependency install does not. Harmless today (no cache), free
  to get right now.
- **Nothing in this repository can run nginx.** The sandbox has no Docker and
  no nginx binary (checked), and CI only builds the image, so `nginx.conf` is
  reviewed by reading and first exercised by T007's compose and the Phase 0
  phone check. Two consequences: keep the file to the shape above rather than
  embellishing it, and state the gap in the PR body. Rejected: a Vitest spec
  asserting the text of `nginx.conf`, which would only prove the file says what
  the file says — the kind of test Tophe removed from T003.
- **`try_files $uri /index.html` and the cache rules do compose**: the fallback
  is an internal redirect, so the request re-enters location matching and hits
  `location = /index.html`, which is what keeps the SPA fallback `no-cache`
  (nginx documented behaviour; unverifiable here, see above). Keep the exact
  `location =` blocks: an `add_header` in a *prefix* location would not win
  over the exact one, and dropping them would let the app shell go stale on a
  phone that already has the site installed — the one failure D09's rule
  exists to prevent.
- **The two images share one tag** (D09), so the `images` job builds the pair
  from the same commit; nothing in this task changes the backend, and the
  backend job must still be green for `images` to run at all
  (`needs: [backend, frontend]`).
- **OCI labels.** As in T003: the Dockerfile declares
  `org.opencontainers.image.version` from `VERSION` and
  `org.opencontainers.image.source`; `revision` and `created` come from the CI
  job's `--label` flags, which win over a `LABEL` line with the same key. The
  *Proposed* item T003 left about declaring all four stays open — do not act on
  it here.
- **Prettier.** Nothing in `npm test` checks formatting, and the tree is
  committed in Prettier's default style (T002). Run `npm run format` before
  committing the new `.vue` and `.spec.ts` files; it ignores `dist/` and
  `coverage/` through `--ignore-path ../.gitignore`.
- **`gh pr edit`** can fail with a GraphQL error about classic Projects; the
  REST API (`gh api -X PATCH repos/…/pulls/N`) works.
