# T168 — Near matches when the words find nothing

**Backlog line:**
> - [ ] T168 Backend: near matches when the words find nothing.
>       When the words find no edition of the reader's catalogue, Libris
>       answers the nearest by their trigrams, said near: *asterik* answers
>       the *Astérix* albums; it looks for them only then, so an edition the
>       words find never stands among near ones (D03). Near matches come in
>       the catalogue's order and pages, each page said near; a page with no
>       edition is never near, and a whole ISBN finds its edition or none,
>       never a near match (S2). The trigram index and its extension arrive
>       here (D02, D03). Realises S3; un-skips its backend test, both cases.

**Serves:** spec `search` S3, the near pages of S4, the *never a near match*
of S2; PRD §3 (*near*), §4.2; decisions D02, D03, D07, D10, D11, D12
**First of its kind:** the first SQL function of the schema (an `IMMUTABLE`
wrapper of `unaccent`, needed because an index expression takes only
`IMMUTABLE` functions) and the first trigram index (`pg_trgm`, an index over
an expression rather than a column).

## Goal
When the words of a query find no edition of the reader's catalogue, the
catalogue's search answers the reader's editions nearest to the query by
their trigrams, in the catalogue's order and pages, each page said `near`;
otherwise it answers as before, never near. With it the backend's search is
whole and T169 can move the frontend's pin once it is deployed.

## Rules in play
- D03 — the near matches use a `pg_trgm` index on `edition.search_text`
  (over its unaccented text) and are asked only when the words find nothing,
  in the same one statement as the words, in the catalogue's order, not
  ranked; a whole ISBN is still answered from `isbn13` alone; `search_text`
  and `search_vector` stay as they are.
- D02 — one Flyway SQL migration brings the extension, the wrapper and the
  index; the rest is hand-written SQL in `JdbcCatalogueEditions` over
  `JdbcClient`; no new port, use case, controller or DSL type.
- D12 — `CatalogueEditions` is the query port answering a read model the
  adapter builds from one query: `EditionIdPage` carries `near`;
  `BrowseCatalogue` copies it, decides nothing.
- D07 — S3's `@Disabled` removed, nothing else in `SearchScenarios`; near
  is computed and tested in the JDBC slice (`JdbcCatalogueEditionsTest`); no
  use-case test of a copied value, no web or controller test; Given / When /
  Then on every case of two statements or more.
- D11 — the migration is `V018__…sql`, three digits, never `V013`'s Kotlin
  form; no column, no default, no `CHECK`.
- D10 — SQL keywords and functions in upper case, at every call of a
  function (`UNACCENT`, the wrapper) too; the names Libris declares (the
  function, the index) in lower snake case; no `!!`; no rationale and no
  `D##` in code, SQL or tests; no member widened.
- D04 — no pin moves: `v0.19.0` already declares `near`.

## Risks and decisions
**Fit.** One run: a migration of three statements, one clause, one field,
one copied value, seven slice cases, two scenario lines. Rejected: a split
(the field, the migration and the clause land together in step 2).

**Near is decided in the words' statement, and the port says it.** D03
makes the search one query whose trigram index serves only when the words
find nothing, and D12 has a query port answer a read model built from one
query; so `EditionIdPage` carries `near` and `BrowseCatalogue` copies it.
Rejected: a second port method the use case calls after an empty words'
page (two statements, and an empty page after `after` would wrongly fall to
near ones, step 6).

**"The words find nothing" is over the reader's whole catalogue**, never the
page after `after` and never the house: the task line says *no edition of
the reader's catalogue*. Steps 6 and 7 pin both.

**How near is near: pg_trgm's word similarity (`<%`) at its default
threshold, 0.6, both sides without accents.** Measured on the sandbox's
PostgreSQL 18.6: *asterik* to the *Astérix* texts 0.75 (0.375 with the
accents kept); *goths* to *Goth* 0.67; *gaston* to every fixture 0.14 or
less; S1's *lotus bleu* 0.09 and S5's *romance dawn* 0.08 to their
catalogues; the earlier slice cases that answer none all below 0.6, the
nearest *one piece tome 2* (0.588) and *serpe loup* (0.545). The spec makes
the setting Libris's, no promise of the contract. Rejected: `similarity`
(`%`) over the whole text (a word against a long text scores far below 0.3);
`strict_word_similarity` (no proof it reads better here); a threshold
property or `SET` (no test asks another value).

**The wrapper is an `IMMUTABLE` SQL function with a SQL-standard body.**
`UNACCENT` is `STABLE`, which no index expression takes. Probed on 18.6: a
quoted body fails the `CREATE INDEX` (since PostgreSQL 17 an index is built under
a restricted `search_path`), and would fail a `pg_dump` restore the same
way; a SQL-standard body passes, and `DROP EXTENSION unaccent CASCADE`
drops it, so Flyway's clean leaves nothing behind. Rejected: a quoted body
with `SET search_path` (not inlined, so the index's expression would not
match the clause's); an unaccented copy of `search_text` (a column and a
re-fill for what an expression gives).

**`near` defaults to `false` on `EditionIdPage`.** Every page but a near one
is not near, the catalogue's included, and the forty-odd existing
`EditionIdPage(ids, next)` of the tests then still assert a page that is not
near, a guard for free. `AwaitedCover.attemptedAt` is the tree's precedent.
Rejected: a required parameter (every existing construction edited for no
claim); a page type of the search's own (a second read model for one flag).

**The index is proven by `EXPLAIN`, not by a test**: no test reads a plan
(T167), yet an index the clause cannot use would be dead schema;
`enable_seqscan = off` makes the plan name it whenever its expression
matches. Probed with a table of 2 000 rows: `Bitmap Index Scan`, `Index
Cond: (probe_wa(t) %> 'asterik'::text)`, `probe_wa` the probe's wrapper.
