## Goal
`EditionDetailsRequest.validate` refuses what the pinned contract (`v0.19.0`)
bounds and does not check today: a `language` not matching `^[a-z]{2}$`, and
a `publicationYear`, a `pageCount` or a `series.volumeNumber` below 1, each
with its error in the validation problem. After that, no add stores a value
that every later answer carrying it (the book, the lookup, the catalogue)
would send against its own contract.

## Risks and decisions
**What goes red today.** The line says the add answers `500` once the
database refuses the value, but `V003` declares no constraint on
`language`, `publication_year`, `page_count` or `volume_number`, and no
code between the edge and `JdbcEditionRepository` checks them: an add of
page count `0` answers `201` and stores it, and every later answer carrying
it breaks the contract's `minimum`. Only a language holding a NUL character
reaches PostgreSQL's refusal, a `500`, and the pattern refuses that too. The
fix the line asks is the same either way, so the red is the unit case of the
class that decides, `Accepted` where `Refused` is due; the PR body says so.
Rejected: a scenario or web-slice case of the add answering `500` (it
answers `201`, and D07 tests the deciding class, never a controller).

**The rule lives in `EditionDetailsRequest`.** The fields the add checks
today are checked there, and the add's `NewBookRequest.validate` delegates
to it; the edit's `PUT /api/v1/books/{id}` validates through the same class
against the same `EditionDetails` schema, so it refuses the same values from
this task on, declared in the PR. Rejected: the checks in `NewBookRequest`
alone (the edit keeps storing what its contract bounds, and the add's rule
would sit beside, not with, its other field checks).

**Field and codes.** The volume number's error names `series`, the request
field as the JSON does and as the blank series name is named (T037 named
the top-level field and rejected paths). Codes: `not-a-language`, after
`not-an-isbn`, for a language that is not the contract's pattern, and
`not-positive` for a number below the contract's `minimum: 1`; both
documentation only, no operation of the contract enumerating codes.
Rejected: `series.volumeNumber` (a path form no error of the API uses);
one code `out-of-bounds` for all four (it says less than the two the tree's
slugs would say).

**No domain rule.** `SeriesEntry.of` is also the door of the BnF mapping
(`BnfRecord`), and a source's mapping never throws on what a source sends: a
`require` on the volume number there would fail a whole lookup on a BnF
*tome 0*. The line asks the web adapter, so the domain types stay as they
are. Rejected: `of` answering `null` for a volume below 1 (it would also
drop the series of such a lookup, a lookup change no one asked).

**No screen sends what is now refused.** The edition form refuses a number
below 1 (`refusalsOf` in `frontend/src/domain/EditionDraft.ts`) and sends a
language's ISO 639-1 code from its list, so the refusal changes no flow of
the screen.
