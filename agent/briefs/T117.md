## Goal
When Libris starts on this release, Flyway runs `V013`, which asks the BnF
for each stored edition with an ISBN and no summary and writes the summary
`BnfSource` answers, already cleaned by T116's `summaryOf`. The editions
stored before the summary spec, in production too, then show the summary
of their BnF record, and T118 draws it.

## Risks and decisions
**Fit.** One run: one class of about forty lines, one slice test of four
cases, three un-skips. No SQL migration, no contract, no dependency.

**In `bibliography.infrastructure.persistence`, a `@Component`.** D02
gives that package the SQL of every update of the bibliography, and the
migration is an update of `edition`; from there it sees `EditionLookup` of
the domain and nothing of `infrastructure.lookup`. Flyway's own scanning
instantiates a class without arguments, so the port arrives only through
Spring Boot, which hands every `JavaMigration` bean to Flyway. Rejected: a
new `infrastructure.migration` sub-package (a layout no document states);
the default `db.migration` package (outside `fr.amory.libris`, no
injection); a `@Bean` in `LookupConfig` (the lookup package would then
know a persistence class).

**The name `V013__summary_for_stored_editions`, `BaseJavaMigration`.** D11
names the class as the SQL files; the description mirrors `V008`'s.
`BaseJavaMigration` reads the version and description from that name.
detekt's default `ClassNaming` refuses the underscores, hence the
`@Suppress` on the class and its test. Rejected: implementing `JavaMigration`
with a version written by hand under a Kotlin-styled name (against D11);
a detekt pattern for migrations (a config change for one class).

**The BnF alone, by its `source`.** The migration takes
`List<EditionLookup>`, as `LookupEditionByIsbn` does, and asks the one
whose `source` is `BNF`; step 4 proves it. Rejected: one `EditionLookup`
parameter named `bnfSource` (resolved by the bean's name, invisible and
fragile); `LookupEditionByIsbn` (it merges Open Library and answers a held
edition from the database).

**Its SQL on Flyway's connection.** The rows change in the migration's
transaction and commit with its history row. The migration takes no
`JdbcClient` nor `DataSource` bean: Spring Boot makes the JDBC beans wait
for Flyway's initializer, a cycle at start; a `JdbcClient` over a
`SingleConnectionDataSource` that does not close `context.connection`, or
plain JDBC, is the implementer's. Rejected: `EditionRepository` (its SQL
follows today's schema, where a migration is frozen at its version).

**A port that throws is caught per edition.** `BnfSource` answers `Failed`
for what it knows to fail on, but D02 says the migration never refuses the
start, and a mapping fault on one record would otherwise keep Libris down
(T116 met one). Step 7 proves it, as T071 did for the cover worker.
Rejected: trusting the adapter alone.

**One edition after the other.** With the BnF down, the start waits up to
`LIBRIS_SOURCE_TIMEOUT` per stored edition, minutes for a household's
catalogue, once. Accepted; the PR body says it, for Tophe's staging check.
