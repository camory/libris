## Goal
The rule that an ISBN never makes a second edition, and that a new edition
awaits its cover, belongs to the bibliography, in `HoldEdition`; the
library's `AddBookToBookshelf` keeps the bookshelf's rules and the copy.
T110 then gives `HoldEdition` the series' find-or-insert without touching
the library.

## Rules in play
- D02 — `HoldEdition` and `NewEdition` live in `bibliography.application.edition`
  and import nothing of `library`; `library.application` may call them, as
  `LookupIsbnForReader` calls `LookupEditionByIsbn`; the boundary is
  `TransactionOperations`, never `@Transactional`.
- D07 — `application` is proven by plain JUnit over the in-memory fakes; the
  scenario classes and the scenario DSL are not touched; the contract
  verification runs the same number of cases as on `main`; each guard's
  mutation is run, reverted and listed in the PR body.
- D10 — a use case named by its sentence, `@Service`, `operator fun invoke`
  alone public, held in a variable `holdEdition`; a `NewEdition` is called
  `newEdition`, never `book`; the files read top down; no `@Suppress` left
  on `AddBookToBookshelf`; no rationale and no `D##` in code.
- D11 — `HoldEdition` mints the new edition's `EditionId.new()`; the edition
  takes it.
- D12 — each use case reads its aggregates through their own repositories:
  the add the bookshelf and the copy, the hold the edition and the awaited
  cover; the add's one transaction keeps edition, awaited cover and copy
  together.
- `CLAUDE.md` — TDD; one step, one cycle, one commit; nothing outside the
  task.

## Risks and decisions
**`HoldEdition` and `NewEdition` sit in a new `bibliography.application.edition`**,
mirroring `domain.edition` as `application.cover` and `application.lookup`
mirror theirs. Rejected: the root of `bibliography.application` — the two
sub-packages there set the layout.

**`HoldEdition` answers the `Edition`**, the aggregate the add needs the id
of. Rejected: an `EditionId` — T110 and a later add answering the edition
would widen it again; rejected: a result type — the hold refuses nothing.

**The join is Spring's, the proof is the fake's**: `HoldEdition` runs its
writes in `transactions.execute…`, and the add calls it inside its own
block over the one `TransactionTemplate` Boot configures, whose
`REQUIRED` propagation joins. `HoldEditionTest` proves the hold's block,
`AddBookToBookshelfTest` that the hold runs inside the add's (its hold over
`withoutTransaction()`, so one block is recorded). No test proves the
propagation itself. Rejected: one `TransactionsObserving` for both — it
records two blocks and cannot tell a join from two commits either.

**The parameter is `newEdition`**, D10's words naming the type; the PR body
proposes D10's example `addBookToBookshelf(readerId, bookshelfId, book)`
read `…, newEdition)`. Rejected: keeping `book` — *book* is an *Avoid* of
PRD §3 for the edition.

**The case *the ouvrage without an ISBN awaits no cover* is dropped**, not
moved: `AwaitedCover` takes an `Isbn`, never null, so no mutation of
`HoldEdition` that compiles can await a cover without one; a case nothing
can redden is weaker than its claim. The PR body says so. Rejected: moving
it as a guard with no mutation.

**Each test class keeps its own `onePieceTomeOne()`.** Rejected: a shared
`NewEdition` fixture in `bibliography.fixture` — a file for two private
helpers.
