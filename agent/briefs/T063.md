## Goal
For an ISBN the house holds, the card shows the house's cover with no dot and
no name under it, or the stand-in while that cover is not stored. The lookup's
`id` is what tells the card the choice is over; nothing reads the candidate's
source name.

## Risks and decisions
**The card is given the answer's `id`, a required `string | null` prop.**
The spec says the id tells the card the choice is over, and the card's props
already mirror the answer's fields, so the view passes it through and
interprets nothing. Required, so a new caller cannot forget it and draw dots
over the house's cover.
- Rejected: a boolean such as `chosen`, computed by the view: the view would
  interpret the answer, a second place that knows what an id means.
- Rejected: hiding the dots when the candidate's source is `Libris`: the spec
  says no side reads the name; step 6 guards it.
- Rejected: hiding the dots for a single candidate: an edition the sources
  offer with one cover still shows its dot and name, as S2 and the fast
  entry's card do.

**A held card still gives out the source of the cover it shows, `Libris`,
or null for the stand-in.** U06 says the card gives out the source of the
cover it shows, and the contract says the add ignores `coverSource` on an
ISBN the house holds. Giving it out unchanged sends the name back without
reading it, and adds no branch.
- Rejected: giving out null when an id is given: a branch for a value the
  backend ignores, which no scenario asks for.

**Only the dots' row and the name depend on the id.** The images, the
failures and the stand-in are the card's as for any answer: a stored cover
that fails to load gives way to the stand-in, which draws neither dots nor
name either way.
