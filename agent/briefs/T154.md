## Goal
`PUT /api/v1/books/{id}` writes the fields sent over the held edition and
answers it as stored, with the reader's copies. The write lives in the
bibliography, where T156–T158 build on it.

## Rules in play
- D02 — `CatalogueController` calls `SaveEdition` (library, it answers the
  copies), which calls `EditEdition` (bibliography, it writes the edition),
  as `AddBookToBookshelf` calls `HoldEdition`; `bibliography` never depends
  on `library`; no controller touches a repository.
- D07 — the four scenario methods named below are un-skipped and nothing
  else in `HeldEditionEditScenarios` changes; behaviour is proven in plain
  JUnit over the fakes of `bibliography.fixture` and `library.fixture`; no
  hand-written test of the controller; the contract stubs match exactly
  the id and the body each key fixes.
- D10 — `EditEdition` and `SaveEdition` expose `operator fun invoke` alone,
  held in `editEdition` and `saveEdition`; `EditionDetailsRequest.validate`
  turns the body into `EditionDetails`, the controller maps nothing; `when`
  arrows aligned; no `!!`; no rationale and no `D##` in code; both
  `@Suppress("UnusedParameter")` of T153 go.
- D11 — no such edition is a result, not an exception; a refused body is
  `400` `/problems/validation` with `errors: [{ field, code }]`, as the add
  answers it; no optimistic locking: the last save wins and nothing checks
  what was there.
- D12 — `EditionDetails` is a value refused through `of` (`null` for a blank
  title), its public constructor `require`s the same; the edition keeps its
  id, ISBN and cover name; its series is the one `SeriesRepository.findOrInsert`
  answers, never the one built; its authors stay values written through
  `EditionRepository.update`, whose author rows keep the house's spelling;
  the series and the edition are written in one `TransactionOperations`
  block, the test proving the boundary.
- PRD §3 — a series or an author named as the house holds it, whatever its
  case, accents and end spaces, lands on the house's row and its spelling:
  the unique indexes already decide it, and nothing in Kotlin folds a name
  for it.

## Risks and decisions
**Fit.** One run: no migration, SQL, dependency or contract change; four
small classes and four test classes, each mirroring one the tree has.
Rejected: a split by layer (a use case with no caller).

**The write in a bibliography use case, `EditEdition`.** T158 has the add
of a held ISBN write the fields "as the save does", from `HoldEdition`,
which cannot call a library use case (D02, rule 4); written in
`SaveEdition`, the write would move in T158 with T156's and T157's rules
inside it. Named after PRD §4.1, *View and edit an edition*; `SaveEdition`
stays the act of the screen. Rejected: the write in `SaveEdition`.
Rejected: `CorrectEdition` (`correctEdition` reads as an adjective).
Rejected: a method on `Edition` taking `EditionDetails` (the domain cannot
see an application type).

**`EditionDetails` beside `NewEdition`, no shared shape yet.** The value
the save's door takes, named after the contract's schema. The reviewer of
#381 noted that `EditionDetailsRequest` repeats `NewBookRequest`'s fields;
`NewEdition` composing `EditionDetails` would reshape the add, its tests
and the add's contract stubs, which is T158's. The refusals may be shared
between the two requests in a refactor step if `NewBookRequestTest` stays
unchanged. A PROPOSED item, *Backend: `NewEdition` and `EditionDetails`
repeat the edition's fields*, hands the question to T158. Rejected: the
save taking a `NewEdition` with no ISBN and no source (it is no new
edition).

**The answer read back.** The contract answers *the edition as saved*, and
S4 shows what Libris answered: an author sent *rene goscinny* reads *René
Goscinny*, which only the author row knows. `EditEdition` answers what the
repository holds after the write, and step 12 proves it with a private
double, since `EditionsInMemory` matches no names and 24 tests use it.
Rejected: teaching `EditionsInMemory` the index's matching.

**The series name answered by `SaveEdition`,** read through
`SeriesRepository` as `FindCatalogueEdition` reads it (D12: a read that
answers a series' name reads it there). Rejected: `Edited` carrying the
series (a second shape for what the repository answers).

**Contract stubs on the example's body.** Both keys send `EditOnePiece2`,
so both stubs name its `EditionDetails` exactly, as the add's stubs name
`NEW_ONE_PIECE_1`; a body that differs answers `null`, seen as `403`.
