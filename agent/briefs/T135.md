## Risks and decisions
**One state, `unavailable`, for every failure.** A rejection, the
validation problem and an unknown type all draw the same sentence, as
`useChooseDefaultBookshelf` and `useAddMemberToBookshelf` read their
refusals the screen never provokes, which TASKS.md's question to Tophe
records for this `400`. Rejected: a `failure` code per cause (one sentence
on screen, a branch no test tells apart).

**The not-found problem runs `afterRemoval` as a removal does.** S7: the
reader's intent is true; the page asks the ouvrage anew, the new copies
close the question, and T136 then reads what is left. Rejected: a status of
its own (nothing on screen differs from `removed`).

**A failure asks nothing again.** Asking again would hand the card new
copies, which close the question the spec keeps open for another try.

**`removalFailed` is a prop, beside `removing`.** As `failed` reaches
`DockedAdd` and `failure` `NewBookshelfRow`: the view owns the state, the
card draws it; optional, so `EditionForm` and `IsbnView` pass nothing; a
name the card's other props cannot be taken for. Rejected: one `removal`
prop replacing `removing` (T134's interface rewritten for no case).

**The message belongs to the question it answered.** U04 has the cross
put the row back as it was and U05 has one answer replace the previous: a
question opened after *Annuler* or another trash has had no answer yet, so
the card draws no message on it, while the view's state stays
`unavailable` until the next removal. How the card tells the two apart is
the implementer's. Rejected: the view resetting the state on *Annuler* (an
event the card does not hand up and no scenario needs).

**A new tap on *Retirer* clears the message**: the view passes
`removalFailed` false while `removing`, the spinner then in the check's
place, as T134 drew it.
