## Goal
An edition the house holds, once saved, is found by the words of its title,
subtitle, series' name and authors' names as they now stand, and never by
the words it no longer holds. T165 wrote `edition.search_text` on insert
only; this task writes it on update too, which every change of a held
edition goes through.

## Rules in play
- D03 — `edition.search_text` is written by the persistence adapter on
  every insert **and update**, from the title, subtitle, series' name and
  authors' names; the domain never sees it; `search_vector` stays generated
  from it.
- D02 — the write lives in `JdbcEditionRepository`'s `UPDATE_EDITION`,
  hand-written SQL over `JdbcClient`; no domain type, port, use case or
  controller changes.
- D12 — no `Series` aggregate is read to write the text: the statement reads
  the name of the row its `series_id` names, as `INSERT_EDITION` does; a
  respelled author or series is not rewritten into the other editions'
  text.
- D07 — the one `@Disabled("search")` of *S5 …, an edition whose title a
  reader changed* removed, nothing else in `SearchScenarios`; the search
  over what the update wrote is tested in the JDBC slice
  (`JdbcCatalogueEditionsTest`), where it is found; no use-case, web or
  controller test; Given / When / Then on every case of two statements or
  more.
- D10 — SQL keywords and functions in upper case; no `!!`; no `D##` and no
  rationale in code or SQL; fixtures below the class, in the order reached;
  no member widened.
- D11 — no migration: `search_text` exists since `V016`, and no merged
  migration is edited.

## Risks and decisions
**Fit.** One run: one statement gains one assignment, one slice file gains
six cases, one scenario line goes. Rejected: a split (nothing to split).

**`UPDATE_EDITION` sets `search_text` itself, from the same expression as
`INSERT_EDITION`.** The update is one statement over the whole aggregate
(D11), so the text is written in it, with the series' name read by its
`series_id` and the authors' names passed as a parameter, as the insert
does. Whether the two statements share the expression through a `const`
part is the implementer's refactor. Rejected: a second `UPDATE` after the
contributions (two statements, a moment with a stale text); a trigger
(the text built outside the adapter D03 names). Traps:
`JdbcEditionRepository` holds ten functions and detekt's `TooManyFunctions`
reports eleven; a `const` template cannot reference a `const` declared
below it.

**The add of a held ISBN gets no case of its own.** Held-edition-edit S2
writes that add through `HoldEdition`, which calls `EditEdition`, whose
write is `EditionRepository.update`, as the save's (`SaveEdition`). The
update's text is proven in the slice, and `HoldEditionTest` already proves
the add writes the fields sent through the repository. Rejected: a
scenario case (S5 has two cases, and a scenario test changes only with its
spec).

**A respell rewrites nothing beyond the saved edition.** A name respelled
for the house differs from the stored one only by capitals, accents and
the spaces at its ends (held-edition-edit S5, the unique index on
`BTRIM(name)` under `ignoring_case_and_accents`), all of which the search
configuration ignores, so the other editions' text keeps finding them
(step 7). Only the author is cased: `update` itself respells it, where a
series is respelled by `JdbcSeriesRepository` before the update, under the
same index and the same ignoring. Rejected: rewriting every edition of a
respelled name (a statement per respell for no change the search can see);
a series case beside the author's (the same proof twice).

**No re-fill.** `V016` filled the editions stored before it; from this task
every insert and update writes the text. An edition saved on a deployment
that ran T165 without T166 (staging only: no release tag since `v0.1.3`)
keeps its earlier text until saved again. The PR body says so. Rejected: a
migration rewriting `search_text` (a file no test motivates, for staging
rows).
